## What actually crosses each model handoff

- For `NAVIGATED_SOURCE`, material construction gathers every body-present method and every supporting source (`BusinessMaterialBuilder.java:661-680`), verifies the persisted UTF-16 span text against frozen source (`:683-695`), and requires enough chunks for every span or returns no material (`:590-613`). - Activity DRAFT receives the whole model packet: context, every entry key, every technical observation, every allowlisted source snippet, and every limitation (`ActivityExplainer.java:306-318`). - Each process-group DRAFT/REVIEW receives every business narrative field of each reviewed activity plus its source refs (`ProcessExplainer.java:449-477`); REVIEW also receives the complete actual draft (`:105-118`). Technical material snippets are not forwarded beyond Activity.
- Repository consolidation receives all reviewed activities, all processes, coverage counts, unexplained-entry summaries, and the activity source-ref allowlist (`ProcessExplainer.java:193-219`). ## Profile fields that can yield a formally published but scope-reduced report

- Material: `maxSourceRefsPerMaterial`, `maxLinesPerRef`, and `maxMaterialChars`. For JDT navigated material, insufficient refs/chunks or chars fail the whole entry rather than partially clipping a method (`BusinessMaterialBuilder.java:590-638`), but the outer fallback records it as not materialized and the workflow can continue (`:145-183`). `maxEntriesPerMaterial` does not combine JDT navigated entries because their grouping key is per entry (`:266-269`).
- Activity: `maxMaterialsToStart` marks all later materials `NOT_ANALYZED_EXECUTION_CAPACITY`; `maxModelInputBytes`, `maxModelOutputBytes`, `maxActivitiesPerMaterial`, and `maxValuesPerField` can mark a material `NOT_ANALYZED_*` before a call. None stops downstream report publication (`ActivityExplainer.java:122-160,179-189`). For complete scope, require every activity coverage record to be `ANALYZED` or an explicitly accepted `ANALYZED_WITH_GAPS`, not merely a successful report.
- Process: `maxActivitiesPerGroup=1` makes every group unmatched without a model call; `maxProcessGroups` puts unscheduled activities into `unmatched`; `maxRepositorySummaryItems=0` disables the repository summary, and a positive value below the process count marks every process not consolidated (`ProcessExplainer.java:99-128,162-190,316-378`). `maxProcessesPerGroup` and `maxValuesPerField` bound the response, but review validation does **not** require `process activityIds union unmatchedActivityIds == group activityIds` (`:697-743`), so a schema-valid review can omit an activity silently.
- Report: `maxValuesPerField` limits each section's paragraphs/items and each item's refs; `maxTextCharsPerValue` and `maxModelOutputBytes` further constrain narrative size (`BusinessReportPublisher.java:317-377`). The validator enforces exactly the fixed nine slots/titles, but permits empty paragraphs/items and does not prove that every activity/process/ref is represented (`:287-315,387-403`). Therefore `validation.status=VALID` means shape/citation/render validity, not semantic completeness.

## First-package capacity traps and acceptance gates

- Activity has a conservative preflight: `cleanPacketBytes + maxModelOutputBytes + 1024 <= maxModelInputBytes`, in addition to entry-count/output minimums (`ActivityExplainer.java:179-219`). A large output allowance therefore also requires a larger input allowance.
- Activity checks REVIEW input size (`ActivityExplainer.java:142-149`). Process group REVIEW does not check its input size before provider invocation (`ProcessExplainer.java:105-118,479-509`); report REVIEW likewise lacks that check (`BusinessReportPublisher.java:84-100,255-285`). Repository-summary DRAFT and REVIEW do check (`ProcessExplainer.java:511-543`). Allow headroom for `actualDraft`, and treat a provider failure at either unchecked review as a capacity suspect.
- Codex CLI is invoked `--ephemeral`, `--sandbox read-only`, with the chosen model/reasoning and an output schema, in a private temp directory (`ProcessCodexSubscriptionCommand.java:20-50`). Login preflight runs before every call, the same timeout is applied separately to login and generation, there is no retry, and output byte limits are enforced by the callers only after generation (`:52-90`; `CodexSubscriptionStructuredProvider.java:27-45`).

Before spending model calls, require the zero-model material result to have: denominator-complete entry coverage, no `NOT_MATERIALIZED`, every intended entry in `NAVIGATED_SOURCE`, and material count not exceeding the explicit `maxMaterialsToStart`. After the run, require: no unexpected Activity `NOT_ANALYZED`, no unexpected `unmatchedActivityIds`, empty `notConsolidatedProcessIds`, a non-null repository summary, and a manual/report-side reconciliation that every reviewed activity/process appears in the nine sections. Those checks close the places where the built-in final `VALID` flag is intentionally weaker than whole-repository semantic completeness.

## Active corrected JDT scan: timeout, publication, and repeated-query audit

Reported observation only: at about 55 minutes the main process `31969` remained `RUNNING`, JDT LS `32768` was using about one core, and Step03 had no publication. No process/JVM was attached, signalled, restarted, or otherwise inspected by this audit.

### Confirmed timeout and failure mechanism

- Runtime configuration fixes JDT startup and each query at 30 seconds, and shutdown at 10 seconds (`EngineConfigurationLoader.java:16-18,60-71`). The 30 seconds is **per future/request**, not one deadline for an entry: `awaitQuery` waits that duration for each future and converts timeout/interruption/execution failure to `JDT_QUERY_FAILED` (`JdtLanguageServerClient.java:416-431,534-540`). It does not explicitly cancel the timed-out future.
- Collecting one method can issue multiple separately bounded requests: prepare call hierarchy plus outgoing calls (`JdtLanguageServerClient.java:161-195`), then definition and implementation for every owned call (`JdtNavigationResolver.java:37-73`; `JdtLanguageServerClient.java:198-215`). Therefore an entry has no 30-second total bound; it may complete many requests before one fails.
- The distinct entry-collection budget is 30 **minutes**, with depth 128, 100,000 methods, and 100,000,000 source characters (`CollectionBudget.java:5-19`). This is a soft callee-expansion stop checked only when the next pending method is dequeued; the root method is still included even when a stop reason exists (`EntryCodeCollector.java:90-119,543-556`). It is not a hard interrupt for an in-flight JDT request.
- Step03 processes admitted entries through a sequential `stream().map(...)`. A `CodeEngineException` from `session.collect(seed)` is caught for that entry and converted to an in-memory `EntryCollection.notCollected(seed, code + message)`; the next entry is then attempted (`ProgramGraphsExecution.java:300-322`). Thus repeated 30-second navigation timeouts can indeed accumulate as per-entry `NOT_COLLECTED` outcomes without an immediate public artifact.
- Only after the complete entry list exists does code construct `JavaCodeIndex` and call the one Step03 publisher (`ProgramGraphsExecution.java:323-338`). There is no per-entry checkpoint/publication. When publication is eventually reached, each outcome is emitted as an `ENTRY_MEMBERSHIP` record with `collectionStatus`, `reason`, method/call keys, sources, and limitations (`JavaCodeIndexPublicationSpecifier.java:308-335`). Any missing context makes Step03 `SUCCEEDED_WITH_GAPS`, with one stable `java-code-index-gap:*` receipt ref per affected entry (`:406-420`).
- The per-entry catch is deliberately narrow. `session.catalog()` runs before it and is outside the catch (`ProgramGraphsExecution.java:298-305`); an `IllegalArgumentException` or other unexpected runtime from `collect`, index construction, or publication aborts Step03 rather than becoming `NOT_COLLECTED`. In contrast, a navigation timeout is a `CodeEngineException(JDT_QUERY_FAILED)` and takes the per-entry path (`CodeEngineException.java:7-18`; `JdtLanguageServerClient.java:422-431`).

So the precise answer is: **yes, the described delayed-visibility pattern is possible for navigation query failures, but “one 30-second timeout per entry” is not the actual limit model.** The first failed request aborts that entry; preceding successful requests may already have consumed substantial time, and the whole repository has no global timeout in this path.

### Confirmed repeated work and retained caches

- Syntax/project indexing is shared. `EntryCodeCollector.index()` builds and caches one `ProjectIndex`; each admitted source is described once during that build, and declarations/method bodies remain cached for all entries (`EntryCodeCollector.java:183-233`). The full technical route uses one `JavaCodeSession` for Step02 discovery and Step03 continuation (`PersistedTechnicalRunExecutor.java:115-124`), and Step02 explicitly calls `javaCodeSession.catalog()` (`ApplicationDiscoveryExecutor.java:60-67`). Hence the already-published Step02 proves that this run completed the shared catalog build; Step03 is not intentionally reparsing every source for every entry.
- Open-document notifications are also deduplicated by URI (`JdtLanguageServerClient.java:58,141-148`). This avoids repeated `didOpen`, not repeated navigation requests.
- Navigation results are **not cached across entries**. Every `collect(entry)` creates fresh `included` and `rawCalls` collections (`EntryCodeCollector.java:82-98`), and every included method calls `navigation.resolve(...)` again (`:120-159`). Within one entry, `included.containsKey(methodKey)` prevents expanding the same method twice (`:98-103`); across two entries that reach the same service/helper method, call-hierarchy, definition, and implementation requests are reissued. The caller has no method/call result cache. JDT LS may have internal indexes/caches, but neither this code nor the existing run log reveals whether a particular repeated request was served from them.
