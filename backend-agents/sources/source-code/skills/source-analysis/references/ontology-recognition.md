# Scoped ontology from saved entry evidence

Use this route for a declared local ontology scope, not Activity or business-process generation. Read the owning [configuration](../../../docs/modules/ontology-recognition/configuration.md), [workflow](../../../docs/modules/ontology-recognition/workflow-and-prompts.md) and [machine contracts](../../../docs/modules/ontology-recognition/contracts.md) for exact fields and current implementation maturity. A design target or an old PoC file is not an installed formal result. The historical local O0–O3 route passed bounded formal acceptance, including a rejected relation task and partial publication; that does not certify a newly installed version. The business-link route below requires an actual corpus-v2 and corresponding new policies/readers. Report actual failures and limitations, not autonomous repository coverage, arbitrary small-window compatibility or guaranteed model semantics.

## Inputs and responsibilities

- Use an accurate saved R4 from the entry-evidence-v1/v2 family and its actual prepared R0. Old Packet, M10, Activity, process Markdown and chat conclusions are not ontology evidence.
- Use an absolute `ontology-config-v1` path. The application must already be built; invoke the same `bin/source-analysis` launcher with explicit Java 17 and `SOURCE_ANALYSIS_CLASSPATH`, as in the source-preparation route. Do not compile, install global skills or invoke customer Maven/JDT as a hidden ontology step.
- Java restores and validates the saved source, generates stable E/U/K aliases, reads complete selected units and forms compact model inputs. Do not replace this with an Agent-authored summary, source excerpt, alias correction or hand-filled ontology.
- A scope/selection file chooses questions, task kinds and actual saved references; it contains no business definitions or expected answers. Obtain E/U/K from the exact O0 Corpus, never assume that a remembered E1/U1 belongs to the current Corpus. `EXPLICIT` means declared selection, not autonomous discovery. `MODEL` requests bounded tool-assisted selection and is not proof that it selected all necessary material.
- The user may replace business Prompt files and communication wording or choose supported source/model/limits. Prompt changes cannot alter schemas, source/version rules, alias ownership or projection algorithms. Reorganizing evidence through new code is a development change, not normal operation.

## Commands and continuation

Use the returned full run IDs. Do not substitute “latest” or infer success from a directory or exit code alone.

### Joint endpoint/link route (scope-v3, policy-v4)

For a supported connection overview, use [LINK configuration](../../../tools/repository-run/ontology-link.example.yaml), [scope-v3](../../../tools/repository-run/ontology-link-scope-v3.example.json) and [direct publication selection-v3](../../../tools/repository-run/ontology-link-publish-selection-v3.example.json). These are templates, not valid customer selections: replace all paths, run IDs and E/U/K with the exact saved values. Use `ontology-artifact-policy-set-v4.json` for new stages and the accurate old owners for historical upstreams. Do not relabel an old result or policy.

1. `prepare-ontology --evidence-run <R4>` creates the actual O0 without a model. Read `ONTOLOGY_CORPUS` to select a real K and its uses.
2. `identify-ontology --corpus-run <O0> --scope <scope-v3>` uses `purpose=SKELETON`. A LINK task has `readingMode=TECHNICAL_BUNDLE`, exactly one `anchorRefs` member belonging to that question's `clueRefs`, and actual optional `unitUses`/`requiredUnitUses`. Java forms a one-hop bundle and exposes selection, included groups, unread candidates and actual cost. QUESTION anchors are explicit choices, not autonomous discovery. DISCOVERY has no prefilled questions; its new priority response selects only each discovered question's own K anchors and records MODEL origin. Do not fill in a missing body or business answer yourself.
3. LINK returns endpoint objects and their connections in one EXTRACT and the original one REVIEW. The task's raw model object keys are not persistent cross-task IDs. Java maps valid final keys to source-bound IDs; rejected definitions remain rejected. Read actual `taskOutcomes` and `ONTOLOGY_TASK_RECORD`, including frozen material and `bundleDecision`, rather than inferring success from a draft. Lexical PAGE_CONTEXT material can belong to another entry but is not thereby a confirmed field binding. Capacity failure retains the full unexecuted scope; do not truncate, copy a PoC packet or silently change limits.
4. `publish-ontology --selection <selection-v3>` may select reviewed LINK O1 runs with `relationRuns: []`. A separate O2 is not required for a link whose endpoints were reviewed together. Publication selects complete stages and retains their failed/unprocessed obligations; it is **not** a taskId filter. Different tasks' similarly named objects remain separate unless a subsequent reviewed SAME_OBJECT decision explicitly unifies them. Do not draw a continuous chain by matching names.
5. For refinement or an O2 identity/relationship task, use scope/selection-v3 `objectSources: [{identificationRun, questionId, taskIds}]`. Every taskId names an actual reviewed OBJECT or LINK task in that exact question/run; no ACTION/ANALYTIC task or guessed producer is admissible. [Enrichment template](../../../tools/repository-run/ontology-link-enrichment-scope-v3.example.json) shows the exact shape. Include every actual upstream O1 when publishing the new result. Refinement creates new runs, never overwrites the delivered graph.

The public commands and query keys below are unchanged. New stage headers are identification/relations/coverage/review-v4; the ontology remains ontology-v2 and sources remain v1. Historical v1–v3 keep their own rules. The v4 review reports actual `taskReviewSchemaVersions`, including `ontology-link-review-v1`, rather than claiming every task used a typed OBJECT/RELATE review. The following scope-v2 route remains available for separate OBJECT/RELATE tasks; it is not the schema for a LINK bundle.

Complete templates are [skeleton scope-v2](../../../tools/repository-run/ontology-skeleton-scope-v2.example.json), [enrichment scope-v2](../../../tools/repository-run/ontology-enrichment-scope-v2.example.json), [RELATE selection-v2](../../../tools/repository-run/ontology-relate-selection.example.json) and [PUBLISH selection-v2](../../../tools/repository-run/ontology-publish-selection.example.json). Replace example E/U/K and all-zero run IDs with actual saved values before execution. Mode is QUESTION or DISCOVERY; selectionMode is EXPLICIT or MODEL; readingMode is EXPLICIT or MODEL. A QUESTION scope declares at least one question. DISCOVERY declares no questions and runs bounded discovery, not an Agent-filled answer. An `objectSources` question reference selects that question's **entire reviewed OBJECT task set**, not one unnamed object; narrow the source question if a smaller catalog is required. The framework does not infer which object a human meant.

1. Prepare O0 with `bin/source-analysis --config <absolute-ontology-config> prepare-ontology --evidence-run <exact-R4-run>`. O0 does not initialize a Provider or require model login. Query its actual `ONTOLOGY_CORPUS` for saved source bindings, preparation controls and the E/U/K mapping. Match those references to the exact saved R4; the mapping is not a business summary or a measurement of a future complete model request. Use actual saved reading/request observations for measured costs, and do not turn a byte limit into a claimed token-window guarantee. Optional `schemaSources` are same-R0 relative files; absent configuration means zero DDL parsing. A parser limitation is not permission to split or repair SQL yourself.
2. Identify O1 with `identify-ontology --corpus-run <exact-O0-run> --scope <absolute-scope-file>`. For a business overview, use `ontology-scope-v2`, `purpose=SKELETON`. Its root is `schemaVersion / purpose / mode / selectionMode / questions`. Questions carry `questionId / question / entryRefs / clueRefs / objectSources / tasks`; tasks carry `taskId / taskKind / readingMode / unitUses / requiredUnitUses`. Each use is an actual `{unitRef, entryRef}` pair. SKELETON permits only OBJECT tasks and empty `objectSources`; ask for supported business objects, their meaning and display roles, not all identity constraints or rules. Java supplies visible K meanings, exact uses and complete selected source; shared code alone is not a business relationship. Use MODEL reading when no exact units have been selected; do not label manually selected units autonomous. The historical scope-v1 shape remains a historical route, not a skeleton inferred from missing fields.
3. Relate O2 with `relate-ontology --selection <absolute-identification-selection>`. New execution uses `ontology-selection-v2`: `operation=RELATE`, exact `corpusRun`, explicit `identificationRuns` and the relation questions. Each question must declare nonempty `objectSources`, with exact `{identificationRun, questionId}` pairs; each run must be in the root list and no pair may repeat. Use the selected O1's saved question range: `scope.questions` for QUESTION, actual `selectedQuestions` for DISCOVERY, not DISCOVERY's original empty scope. Java loads all reviewed OBJECT tasks belonging to those questions, not other questions' accumulated results. Rejected ACTION/ANALYTIC does not by itself block a RELATE with reviewed OBJECT dependencies. Missing or unreviewed OBJECT dependencies produce an unprocessed relation task, not invented endpoints. An explicitly empty relation question set records a zero-model disposition, not proof that no relations exist.
4. Publish the skeleton O3 with `publish-ontology --selection <absolute-publication-selection>`. New execution uses `ontology-selection-v2`, with `operation=PUBLISH`, exact `corpusRun`, explicit `identificationRuns` and `relationRuns`. The O1 list must contain every actual O1 upstream saved by every selected O2 **and every selected enrichment O1**; independent additional O1 runs are allowed, missing ones are refused rather than silently added. O3 uses complete reviewed tasks and preserves the failed/unprocessed obligations of all selected stages. It installs `ontology.json`, `ontology-coverage.json`, `ontology-sources.jsonl` and `ontology-review.json` without model login or a WRITE call. Query the saved business overview before waiting for deep quantity, state or amount rules. Never write a replacement ontology file or remove failed tasks to satisfy publication.
5. If the user requested further detail, create a new scope-v2 O1 with `purpose=ENRICHMENT`. Each question explicitly selects its reviewed objects through `objectSources: [{identificationRun: <exact-O1>, questionId: <actual-question>}]`, or defines preceding OBJECT tasks in that same question. Only this small catalog is provided; do not give tasks all earlier questions or reuse another task's B1. Declared external sources apply to every task in that question, including an OBJECT refinement: missing/unreviewed source OBJECT tasks cause a saved dependency disposition and zero dispatch. A nonexistent question, wrong Corpus or invalid source receipt remains an admission error, not an invented task. Then run the appropriate new O2/O3 with all explicit actual upstream O1s. This creates a new publication and does not overwrite the delivered skeleton. Only an actual reviewed SAME_OBJECT decision can unify identities; matching names or tables do not. The overview draws one box per explicit canonicalObjectRef while keeping each original definition, name, source and unknown in the details; a refinement never replaces old evidence.

If no relationship question was requested, the supported empty-question O2 can preserve that fact for an objects-only O3 view; it is not proof that the objects have no relationships. Never replace a requested or rejected relation task with an empty O2 to obtain a success label.

Before any O1/O2 dispatch, confirm the authorized scope, configured Provider/model, finite per-run request allowance and permitted continuation. A request to prepare or inspect is zero-model, not authorization to identify. Honor the user's current authorization without asking again for every local rejection or already-authorized same-scope program fix. Every run remains bounded: one EXTRACT and at most the original one REVIEW, no third repair call, no automatic account/model fallback. Source/configuration and that task's actual capacity checks precede its Provider creation. Explain any token limit the adapter cannot enforce rather than calling it guaranteed.

Java enforces `maxRequests` per run, not an aggregate authorization database. If the user's current instruction imposes a hard total allowance across named runs, honor it using their saved observations; a new run does not renew that grant. If the user instead authorizes bounded same-scope defect repair and retesting, do not resurrect a superseded PoC total as a new permission barrier. Request counts remain audit/cost information. Changing scope, source, model or account requires the applicable authorization; this Skill grants none. Unknown request state is not an unused allowance: stop new dispatch on that Provider binding and inspect. Zero-model queries and admissible publication do not consume model requests.

If the user requested the complete local workflow, continue its admissible independent work within that authorization. A PARTIAL result or FAILED lifecycle does not automatically prohibit querying, source-specific O2 or explicit partial O3. Read the exact task dependencies and failure boundary first. Stop model dispatch for an affected shared source/configuration/authentication/storage fault or unknown remote result; do not stop unrelated valid tasks merely because one final model draft was rejected. End at the requested operation or O3. Do not expand to repository-wide identification, execute Actions/metrics or start the old MD route.

## Read actual results, including failures

Run `inspect --run <exact-run>` and use the actual advertised output/query keys. For each file use `artifact --run <exact-run> --key <closed-key> --max-bytes <explicit-positive-limit>`. Public keys are `ONTOLOGY_CORPUS`, `SCHEMA_EVIDENCE` when actually saved, `ONTOLOGY_IDENTIFICATION`, `ONTOLOGY_RELATIONS`, `ONTOLOGY`, `ONTOLOGY_COVERAGE`, `ONTOLOGY_SOURCE_INDEX` and `ONTOLOGY_REVIEW`.

For a new ontology-v2 publication, query `artifact --run <exact-O3> --key ONTOLOGY_BUSINESS_OVERVIEW --max-bytes <limit>`. It returns derived HTML with packaged offline Mermaid, not JSON or a fifth fact file. Save/display these exact returned bytes with host-supported file/browser facilities. The byte limit applies to the complete HTML including the framework's embedded renderer (roughly 3.7 MB before local definitions); a too-small query must fail, not truncate. Do not replace it with a model-authored diagram. MAIN objects form the main layer; support, unknown and isolated objects remain visible. Arrow direction is the saved relationship direction, not an inferred handling sequence. Solid links mean reviewed CONFIRMED with no corresponding saved assembly counterevidence, not machine-proven truth; unknown cardinality, state effects or other detail remain visible without downgrading a confirmed mechanism. Other links are dashed. Definitions, source mappings and limits accompany the graph. Historical ontology-v1 is not silently converted to this view.

Read coverage-v3 `recognitionLayers` separately for OBJECT, RELATION, ACTION and ANALYTIC. `NOT_REQUESTED` means not investigated, not absent from the system. `COMPLETE_FOR_DECLARED_SCOPE` only covers declared tasks; missed K is `MODEL_NOT_ADDRESSED`, not a negative business decision. Preserve the real failed/unread/capacity denominators. An omitted model answer never lets the Agent fill an arrow from common Service or table names.

For relations-v3, `selection` is the unchanged requested scope; `readingSelections` records each question's actual selected E/K, reading status and issue code. MODEL reading uses the same bounded reader with taskKind RELATE and shares the operation's request budget with extraction/review. Do not fill an empty MODEL `unitUses` by hand or describe it as completed reading. A failed or incomplete read can still have selected K; inspect these actual selections and O3 coverage rather than assuming the initial empty `clueRefs` means no investigation occurred. Historical relations-v1/v2 do not acquire this field.

For v2 O1/O2, read all `taskOutcomes`, not only successful `taskRecords`. Outcomes cover declared tasks: question/task/kind, REVIEWED/REJECTED/UNPROCESSED, exact dependencies and structured reason. Unprepared work has null `producingTaskId` and `jobKey`; it has no `ONTOLOGY_TASK_RECORD`. For an actual job, take its full `producingTaskId` from that exact run, then query `artifact --run <run> --key ONTOLOGY_TASK_RECORD --task-id <producingTaskId> --max-bytes <positive-limit>`. A local label, another run's identity or a guessed hash is not a substitute. The record exposes actual saved requests, Prompt/Schema, drafts, validations and stage observations; absence is not success, and private failure bytes are not exposed.

If public installation failed, `ONTOLOGY_TASK_INDEX` is a bounded private-record query, not an installed public file. Check its actual `schemaVersion`: v1 lists only verified terminal members; v2 additionally carries all declared outcomes, including unprepared dependencies. An unprepared outcome does not acquire a job record merely by appearing in the index. Historical v1 records are not upgraded by reading them. If an O3 structured conflict refused installation, use the advertised `ONTOLOGY_ASSEMBLY_DIAGNOSTIC` key to inspect its saved issues and exact selection provenance; this diagnostic is not `ontology.json` and contains no public receipt.

In v2 `inspect`, use `modelRequestCounts.reservedAttempts / confirmedStarted / confirmedEnded / outcomeUnknown`; the legacy `modelRequestsDispatched` field is not proof of remote execution. The queried task record's stage outcome fields `localProcessState=EXITED` with `remoteOutcome=UNKNOWN` mean only the local adapter ended, not that the remote request was cancelled; these are stage observations, not extra fields in the declared `taskOutcomes` array. Stop new model dispatch on that binding. Read-only inspection remains possible, and zero-model O3 is possible only with authorized, valid explicit selection and no source/storage integrity block. Use actual advertised `nextActions`; a saved SOURCE or STORAGE fault prohibits partial publication even if unrelated reviewed jobs exist. Query their task records instead. Never invent a next action or interpret an ended FAILED run as a background process waiting for a better model answer. Check all task outcomes even when the problem summary is shorter than that list; report any concrete query omission rather than filling its fields yourself.

Inspect saved results even after a nonzero exit. Distinguish a saved partial report from a usable completed stage; show which selected task or required unit failed and what was actually installed. If no result exists, return the concrete CLI diagnostic without inventing a receipt/run. New settings or Prompt text require a new run; never reactivate or edit an ended run. Queries use saved provenance and do not restart tools or models merely because original Prompt, Maven output or customer JDK files are unavailable.

An exhausted finite run allowance stops its new dispatch, not read-only inspection. If the user requested saving the valid local portion, zero-model publication may select those actual saved stages only when admission permits and all rejected/unprocessed obligations remain visible as INCOMPLETE; it cannot repair the failed task or claim a complete ontology. O3 coverage/review v2 inherited rows retain their original `runId`: identical local task labels in different O1/O2 runs are distinct obligations. Do not turn a planned nonempty relation task into a zero-question O2 merely to bypass its failure. Source damage, invalid receipts or unavailable storage still block publication. An inconsistent COMPLETE label does not override actual saved rejected/unprocessed obligations; report that concrete inconsistency rather than silently accepting it.

Historical publications reopen only through their exact saved policy owner. When configuration uses a new policy, provide the original verified policy document through the supported `storage.upstreamArtifactPolicyRegistries` list. Missing or duplicate owner matches are refused. Do not edit a saved policy/receipt, substitute a similarly named file or scan sibling paths to make it pass.

## Report to the user

Treat draft validation diagnostics and final review validation separately. In a private `reviewed-result`, the saved `diagnostics` may describe the actual EXTRACT candidate supplied to REVIEW; they do not by themselves mean that the final task was rejected. Verify the final review validation, saved success record and exact `taskOutcomes` disposition. Conversely, a stored draft or an intended request is not a completed reviewed task or evidence that a remote request started.

Report exact R4/R0 and O0/O1/O2/O3 IDs that actually exist, selected scope, installed outputs, actual new/reused requests, input byte costs, adapter limit status and concrete unknown/failed ranges. Keep three conclusions separate:

- Framework/material: whether complete selected original text, per-entry uses, constraints and source reversal survived preparation, saving and reopening.
- Model quality: what the actual reviewed definitions claim, what was corrected and what remains unknown or misread. Structural validation is not proof of business truth.
- Coverage: which declared obligations were disposed of. `SCOPED/COMPLETE` is not whole-system semantic completeness; `DRAFT_REVIEWABLE` is not human acceptance and `NOT_EXECUTABLE` is not an operational Action/metric.

The host Agent explains these real records directly. It does not call another model to fabricate a report or supply missing evidence. The workflow requires a shell, the packaged Java tool, shared Skill files, an available configured Provider and explicit inputs; it does not require Codex UI, hidden session memory or cross-chat messages. Availability in a particular host remains to be verified, not assumed.
