### 2.1 请购与采购订单确有连接材料

S688的原文724–727行：
```java
//如果关联单据号非空则更新订单的状态,此处针对请购单转采购订单的场景
if(StringUtil.isNotEmpty(depotHead.getLinkApply())) {
    String billStatus = getBillStatusByParam(depotHead, depotHead.getLinkApply(), "apply");
    changeBillStatus(depotHead.getLinkApply(), billStatus);
```

外层710行明确当前子类型为SUB_TYPE_PURCHASE_ORDER。因此它不是任意单据更新任意单据：**采购订单提供关联申请号时，会按对应数量逻辑更新关联申请状态。**

S1477的1226–1228行同时限制：
```java
if(StringUtil.isNotEmpty(depotHead.getLinkNumber()) && StringUtil.isNotEmpty(depotHead.getLinkApply())) {
    throw new BusinessRunTimeException(ExceptionConstants.DEPOT_ITEM_EXIST_REPEAT_NO_FAILED_CODE,
            String.format(ExceptionConstants.DEPOT_ITEM_EXIST_REPEAT_NO_FAILED_MSG));
```

可解释为“不能同时填写关联订单号和关联请购单号”。这里没有证明“必须填写其中一个”，不能因此把请购设为所有采购的必经前置。

### 2.2 关联入库/出库会更新原单进度

S688的694–702行：
```java
//如果关联单据号非空则更新订单的状态,单据类型：采购入库单、销售出库单、盘点复盘单、其它入库单、其它出库单
if(BusinessConstants.SUB_TYPE_PURCHASE.equals(depotHead.getSubType())
        || BusinessConstants.SUB_TYPE_SALES.equals(depotHead.getSubType())
        || BusinessConstants.SUB_TYPE_REPLAY.equals(depotHead.getSubType())
        || BusinessConstants.SUB_TYPE_OTHER.equals(depotHead.getSubType())) {
    if(StringUtil.isNotEmpty(depotHead.getLinkNumber())) {
        //单据状态:是否全部完成 2-全部完成 3-部分完成（针对订单的分批出入库）
        String billStatus = getBillStatusByParam(depotHead, depotHead.getLinkNumber(), "normal");
        changeBillStatus(depotHead.getLinkNumber(), billStatus);
```

这给过程模型的是：当前单据子类型、关联字段、计算与写回动作，以及分批完成含义。可以支持业务联系，不只是一句“有个linkNumber”。但不能据此断言所有出库都来自订单，或后端强制先审核再出库。

### 2.3 相同方法不等于相同规则

S1477的1232–1235行对“采购、采购退货、销售、销售退货”检查结算账户，条件没有包含“销售订单”。S688的最低售价检查也只在其特定“销售/零售”分支，不能写成销售订单创建的通用前置条件。

这正是新增rule.activityUseIds的目的：规则属于哪种业务用法须明确；模型仍要核对分支，Java只检查所选用法及引用合法。不能把有SourceRef当作业务判断已经正确。

## 3. 模块怎样一步步得到业务流程

### M1：重开已完成材料

程序一次打开326条ReviewedActivity及已映射的M10 SourceRef。新增、修改、审核的完整条件、规则、结果和来源仍在。此步不调用JDT或Activity模型。

当前corpus范围只包含Activity允许引用的已保存片段；不存在的源码不能假装取得。关键材料不足就明确列出需要哪项信息。

### M2：全仓目录发现不同业务用法

Java生成原字段卡片，补入已有businessRules，不编业务标签。模型看到通用新增活动中不同单据分支、审核限制和关联进度等线索后，应提出值得合读的业务候选。

**目标示意，不是本次模型输出：**
```text
候选：申请到采购履约
  新增活动，用法：登记申请
  新增活动，用法：形成采购订单
  新增活动，用法：办理关联采购入库
  审核活动，用法：处理有关单据审核
  查询活动，用法：查看关联和完成进度

候选：销售订单及关联出库
  新增活动，用法：创建销售订单
  修改活动，用法：修改未审核订单
  审核活动，用法：审核/反审核
  新增活动，用法：创建关联销售出库
  删除活动，用法：删除未审核订单
  查询/统计活动，用法：关联退货、进度和分析
```

关键是同一新增Activity可以有不同variant，不能解析时只保留一个。它不是复制源码或新建几个入口；只是在不同业务中解释同一实现的相关分支。

这些名称由模型发现，不能写进通用Prompt作为正确答案；目录若没发现它们，必须先修目录材料/指令，不能手工补候选后声称自动发现成功。

### M3：取回完整内容，选择核对原文

程序每个不同Activity只发送一份全文，用法分别引用。模型同时读到完整条件、步骤、规则、结果、公式和问题，而不是继续用卡片写过程。

来源目录包含S编号、所属局部Activity、原snippet前8行预览。DRAFT可请求S688/S689等完整片段；REVIEW前程序从保存内容取回它们。预览不代替完整源码，空请求不自动失败，已充分材料无需强制再查。

若关联逻辑确实不在当前允许片段中，输出“缺少关联字段写入或数量更新依据”等具体不足，不扩大检索或重扫。

### M4：生成并审阅阶段叙述和规则

DRAFT为每阶段写narrative，并保留详细结构字段。规则写具体when与适用用法，不是“状态允许”。

**局部结构示意：**
```json
{
  "name": "修改未审核订单",
  "narrative": "原单处于未审核状态（0）时，允许调整单据及明细；不是该状态则拒绝修改。",
  "activityUseLocalIds": ["U2"],
  "entryConditions": ["原单状态为0"],
  "rejectionConditions": ["原单状态不为0"],
  "certainty": "CONFIRMED",
  "sourceRefs": ["S1599"]
}
```
这是字段摘录，不是完整合法任务响应，也不是保存产物。

REVIEW核对：仅status为空才默认未审核；修改0；审核0→1；反审核当前1且purchaseStatus0；价格检查与结算账户条件适用哪种单据；入库/出库与原单如何关联。业务关系可推断，不能升级为强制入口时序。正文、结构字段、rule-use必须一致。

### M5：归并，不重写业务

候选过程可能重叠，归并只裁决KEEP、MERGE_INTO、REJECT及相关/替代/父子关系。即使共享新增方法，也不能把采购和销售合成一个“新增单据过程”。

合并保留不同规则、narrative及来源。不能无损保持顺序和分支时保留相关的独立过程，不把阶段数组连接成虚假的完整路径。

### M6：发布可读正文和来源

程序不再写业务。它将已审narrative排版为business-processes.md，规则附适用用法；详细字段可折叠保留。每阶段一个“查看依据”，点击过程来源索引中的“DepotItemService.java：380–738”即可打开sources.md中的S688全文。

这只是展示现有SourceReference，不增加证据采集。JSONL保持程序查询，sources.md供人读。覆盖页使用原Activity名称说明支撑、独立、未分类和未处理，不输出一墙ID。

## 4. 人工示范：目标销售正文应达到的具体程度

> 以下由已核实材料推演目标写法，不是Luna本轮输出；实际自动输出须在后续实现及小样本运行验收。括号来源用于本设计核对，未来发布器将改为点击链接。

### 销售订单及关联出库

**目的与范围：**管理订单的建立、可修改阶段、审核状态，以及与出库单关联后的数量进度。跨入口的业务顺序是材料支持的路径解释，不代表每次交易都会经过全部步骤。

**阶段一：创建订单。** 登记订单和所订商品、数量等内容后，系统保存销售订单及其明细。未指定状态时，订单默认处于未审核状态；这不代表所有创建方式都强制产生状态0。关联订单号与关联请购单号不能同时填写。（S1477、S688）

审阅备注：本例没有把其他单据分支的结算账户、最低售价校验写成销售订单创建条件，原因见§2.3。实际生成时应把适用规则放进对应业务，不需要在每个段落向读者解释解析器怎样工作。

**阶段二：修改或取消。** 原订单状态为0时可以修改单据及明细；不是0则拒绝编辑。删除另有未审核限制，因此它是可选取消路径，不是所有订单必经阶段。具体删除后的关联处理只按该分支保留。（S1599、S533）

**阶段三：审核或退回未审核。** 批量审核仅接纳当前状态0的单据，目标状态为1。反审核要求当前状态1且采购进度为0；采购进度2或3会拒绝。这里描述的是该独立操作的规则，不证明新增只能先保存为0，也不把它宣称为唯一审核方式。（S280、S1477）

**阶段四：办理关联销售出库。** 办理销售出库时，系统保存单据和商品明细；若填写关联订单号，会根据关联数量重新计算并写回原订单的完成进度，区分部分完成和全部完成。由此可合理理解为“订单可以分批出库并跟踪履约数量”。没有关联号时不会执行这条关联更新分支，不能把它说成所有出库都必须来源于订单。（S688、S689、S690）

**分支：查看关联退货。** 系统存在按关联单号及退货子类型查找退货记录的能力，可作为了解原单后续退货的入口。仅这些查询不足以确认退货创建的全部条件、库存/欠款冲减以及是否回写原销售订单状态；这些内容保持待确认，不假造完整“销售退货处理”阶段。（S1714、S2009）

**支撑查询与结束结果。** 完成数量、详情和统计属于查看/分析能力，不排成所有订单的必经后续步骤。这条路径可确认到关联出库数量及原单完成进度；真实付款、结算完毕或客户已签收不在已核实范围内。

这比“执行主动作及派生对象联动”具体，也比一律承诺“销售订单必经六阶段、最后全部结算”诚实。

## 5. 人工示范：请购到采购订单再到入库

**候选名称：申请驱动的采购与关联入库。** 这是受支持的可选路径，不代表所有采购都必须先申请。

1. **登记采购申请。** 通用单据材料及后续关联逻辑识别出请购对象；登记细节应使用该用法对应的完整Activity。若不能确认申请创建/批准条件，必须具体注明，而不能套用订单审核条件。
2. **根据申请形成采购订单。** 采购订单填写linkApply关联已有申请时，系统根据数量计算并写回申请状态。关联申请号和关联订单号不得同时非空。另一分支通过linkNumber处理销售订单转采购订单，不能把两条分支混成“既关联申请又关联销售订单”。（S688 710–731、S1477）
3. **办理关联采购入库。** 采购入库单有linkNumber时，保存明细后重新计算、更新原单完成进度；因此可解释为采购订单支持分批关联入库，而不是只说“调用更新状态”。具体数量计算来自S689，不能仅凭字段名称写结论。（S688 694–706、S689、S690）
4. **查看进度及相关退货。** 数量查询、关联单查询可支撑业务跟踪，但不自动代表入库后必定退货。退货创建与冲减效果材料不充分时独立记录缺口。

**该路径仍未确认：**哪类人员有权限申请/审批、所有采购的强制审批顺序、关联号是否保证唯一或外部事务结果。没有这些不能声称掌握企业制度，但不妨碍解释代码已经体现的申请—订单—入库联系。

## 6. 推演结论及下一次验收

现有材料不是完全没有业务联系：关联申请、关联订单、数量与状态写回确实在原片段中。失败主要是目录没有按业务用法组织、过程解释停留在技术模板，以及来源目录和正文不便核对。本次修正集中于这些位置。

这也不是“推演通了，所以自动实现保证成功”。后续必须分开验收：
1. 目录模型自己发现这些用法和跨活动候选，而非人工注入。
2. 过程模型看完整Activity及所需原文后，写出具体条件、联系、拒绝和结果。
3. 归并与渲染不丢规则、不混variant，读者能点击来源。
4. 换一个不同领域的fixture，仍使用同一Java和通用Prompt；无匹配业务不应输出本例名称。
5. 材料不足明确列出缺什么，覆盖CLOSED不能冒充业务理解完整。

不会为这次设计重做326个Activity、重跑JDT或新增第九步。先验证少量真实候选达到上述阅读质量，再扩大；本次没有新业务模型运行结果。
