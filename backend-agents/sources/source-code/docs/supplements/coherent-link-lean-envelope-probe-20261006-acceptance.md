## 实际结果与逐原文核验

### 采购：业务联系仍取得，但有来源指向错误

模型返回5个对象候选：采购入库单、采购订单、供应商、采购入库明细、采购订单明细；5条联系：

1. 入库单关联采购订单；
2. 入库单对应供应商；
3. 入库单包含明细；
4. 订单选择并传回明细；
5. 入库明细通过`linkId`引用来源订单明细。

人审可从S6的`this.linkNumber = record.number`及`$emit('ok', ... this.linkNumber ...)`、S13的表单写入及`info.linkId = info.id`、S5的`setHeaderId`／`setLinkId`核对这些静态联系。S11提交类型为“入库／采购”及rows，S12打开采购订单选择器；这不是代码实际运行成功的证明。

**模型仍有具体错误：**首条机制把“订单number写入linkNumber”归给S12，实际建立该值的是S6，S13接收并写表单；S12只打开选择器。未知段也将导航限制误称为`candidateDiagnostics`给出的结论，实际该机械诊断为空，导航限制在调用记录中。原请求确实有S6及限制，因此这些不是材料漏交；不自动修写已审模型JSON或再叫模型修第三稿。

本次模型保留4条未知，包括helper未读、HTTP关联未确认、唯一性和基数；程序的完整限制另存，不依赖模型是否重复。模型没有输出请购单，并明确当前未提交其页面建立端。本次只核验来源订单编号联系，不是全采购链实验。

### 调拨：引用闭合，但业务对象分类不合格

模型返回“调拨单据、调拨明细、第一仓库标识、另一仓库标识”4个候选及3条联系。审阅删除了两个目标之间无依据的联系、改正主表／明细关系方向，并保留仓库实体、调出／调入方向及成功保存未知。

S39实际支持明细设置`headerId`、`depotId`、`anotherDepotId`及调拨分支不允许两个标识相等。**后两项是标识属性，不应统计为两个独立业务对象。** 当前小Schema没有单列属性，也未给对象候选独立分类槽；Prompt虽要求业务对象，未专门约束标识值不能顶替对象。不能说这种形状强迫了模型，也不能说加一句Prompt就一定解决。

因此，程序材料和结构门禁通过，但本例业务对象图未通过。图保持原输出并标“候选”，不手工把标识节点替换成仓库，不将4个候选报告为4个有效对象。需要的正式调整是小而清楚的对象／属性／未知目标输出边界及提示词；Java仅根据显式字段投影和校验，不能按名字判断业务对象。具体仓库实体定义缺失仍保留未知，不以增加更多调用账本掩盖。
