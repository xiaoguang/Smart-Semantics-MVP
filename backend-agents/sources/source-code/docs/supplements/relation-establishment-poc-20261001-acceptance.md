### 3.1 超限包的精确离线构成

从`actual-read-map.json`的118项真实身份重新取固定R4单元，用同一个`OntologyReadingPacket.of`构造包；不调用Provider或阶段执行器。最终诊断退出码`0`，报告为独立`capacity-diagnostic.json`。

| 构成 | 字节 | 占原模型包 |

正文一行是方法单元的子集，不能与方法单元再相加。调用行包含每个实际调用的表达式、实参、目标、观察及状态等；不能因占比高就声称全部无价值或全部可删除。

自动附带调用分布：财务明细保存57条（36,206字节），财务新增52条（34,703字节），原查询Controller 4条（2,183字节），查询Service 1条（661字节）。模型并未要求读114个新方法，是驱动在读取完整方法时附入所属调用记录。

导航里`canonicalBytes`只标该单元的私有字节，未给出“读方法会附入全部调用”后的模型包增量。因而模型看到几个小方法标题时，不能据此预测完整封包成本。这是读取/容量合同缺口，不是业务关系推理失败。

本次先失败于包上限，尚未生成下一轮完整请求。下一轮还要携带查询页、调用目标导航、可读句柄和后续审阅稿；不能只把91,408字节与160,000字节封套上限相比，就宣称整个请求可容纳。

离线诊断也有执行失误，不能混为产品失败：两次工具调用未保留session/退出元数据，报告未产出，父代理确认无遗留JVM后接管；接管的第一次明确退出码1，因诊断百分比使用小数而被现有canonical codec拒绝。仅将诊断比例改为文本后，重新编译退出码0，最终诊断退出码0。错误日志与成功日志均保留，产品请求仍然只有2次；没有改driver、配置、原始请求或证据。

## 4. 原文核验

独立验收Agent及主代理核对真实请求、导航、选择与原文，不把人工金标准发给模型。模型自主请求的财务明细保存方法，确实是固定R4里包含业务单号查业务ID、赋给财务明细的实现；但该全文没有进入第三次产品请求。因此只能确认调查方向，不能确认模型已经理解了标识交接或建立动作。

人工另查R4能够解释该机制，不等于本轮模型输出。数据库唯一性、实际写入成功、金额与欠款均未获本轮结论；本次也没有最终稿可供业务验收。

## 5. 结论边界

**本轮未通过建立机制端到端验收。** 已观察到模型自主请求了正确的建立侧候选；没有让它实际收到完整实现，不能据此评判其解释该关系的能力，更没有产出本体、指标或维度。

最小后续问题是阅读封装：完整正文保留；调用对应关系、实参与形参、目标状态和限制以可逆、较少重复字段的方式表达，并给导航标出实际自动附入成本。先零模型检查完整性和所有后续请求容量，再讨论是否接续真实实验。本轮未实施该新投影，不承诺它已满足限额，也没有提高限额、截断源码或升级模型。

即使后续通过，也只证明既有20入口和普通财务问题下的一条局部机制，不证明全仓无提示发现、完整六类本体可组装或任意小上下文模型均能完成。
