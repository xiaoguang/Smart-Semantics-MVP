## 2. 两组业务联系核验到了什么

以下只说明软件源码定义的关系和条件，不宣称某笔实际入库、付款或数据库写入已发生。

### 请购→采购订单→采购入库

1. **来源单号和来源明细分开关联。** 采购订单页面选择请购明细，将来源单号放入主表的 `linkApply`，将来源明细自己的 `id` 放入后续明细的 `linkId`。采购入库页面则将来源订单号放入 `linkNumber`，仍使用来源明细 `id` 作为 `linkId`。主/明细插入XML分别保存这些字段。后端拒绝 `linkNumber` 和 `linkApply` 同时非空。
2. **分批数量有具体条件，不是任何时候都重新相减。** 订单页面在来源行 `preNumber` 为真值时，用来源数量减已办理数量；入库页面仅在 `finishNumber>0` 时重新计算，其余情况保留传入明细中的数量。只有操作数量大于零的行进入待保存列表。后台新增在有关联号且行提供原数量/已完成数量时比较“本次数量＋已完成数量”；超出且未开启超量关联配置时拒绝。编辑分支依赖另外的查询方法，本次包没有这些正文，不冒称已核验其全部统计口径。
3. **累计办理与状态回写按商品汇总。** 来源和后续明细均按 `material_extend_id` 汇总操作数量，排除已删除主/明细；后续汇总还按当前单据 `type` 及对应 `link_apply/link_number` 过滤，并不是按 `linkId` 逐行累计。没有后续汇总为状态1；有办理但至少一个非零来源商品不足或缺失为3；其余保持2。代码注释将1定义为审核、3为部分办理、2为完成。修改关联来源时，保存正文还包含重算旧来源的逻辑。
4. **请购进度与销售订单采购进度不能混为一谈。** 采购订单的 `linkApply` 分支针对请购来源写普通单据状态；其 `linkNumber` 分支注释指向“销售订单转采购订单”，写另一种采购进度。这不是要求全部采购必须先有销售订单。
5. **选择状态参数与真实查询结果分开。** 已保存选择器正文证明两处调用将 `"1,3"` 设置为 `queryParam.status`；`organType` 只用于列标题，不进入这些查询参数。请购调用没有传第五个 `purchaseStatus` 参数。包内没有列表请求的完整服务端筛选链，不能从参数赋值进一步宣称实际可选记录集合。

范围：P1和P2。P1审阅的主体事实正确；P2仍有选择器参数错误及部分条件/引用遗漏，见下一节。状态辅助方法来自同源补充，正式R4相关调用仍有 `NAVIGATION_CONFLICT`；原文能核对方法定义，不等于正式导航绑定已修复。

### 采购入库→库存→付款/结算

1. **库存是重新计算，不是直接“加上入库数量”。** 明细保存后调用当前库存处理；给出的辅助方法按商品和仓库定位未删除当前库存记录，以库存查询结果设置数量。库存查询把初始库存、盘点差量及各类入出库相加减。强审核配置开启时，普通汇总及盘点差量汇总均带审核状态与时间过滤；出入库管理配置开启时，普通入/出库项排除采购、采购退货、销售、销售退货。不能无条件说“保存一张采购入库单就增加统计库存”。
2. **审核是另一组条件。** 审核要求原状态未审核；反审核要求已审核且采购进度未采购。强审核开启时，状态修改后逐明细重算库存；库存不足拒绝主要针对代码列出的出库分支，不能套到所有采购入库。
3. **订金与本次付款不是同一个业务量。** 订单页面的“支付订金”绑定 `changeAmount`；入库页面的“本次付款”也绑定该字段，另有 `deposit` 表示扣除订金。因此解释必须保留页面/单据用途，不能仅按同名字段合并金额含义。
4. **扣订金校验与剩余订金汇总过滤不同。** 校验在有关联号且本次订金非空时，查询同一关联号、未删除、排除当前单号的累计值；该查询没有子类型过滤。仅原单 `changeAmount` 非空时比较“本次＋累计”是否超过原订金额度。剩余订金计算另只汇总未删除的采购/销售单据，按原订金额度减累计值写回。查不到原单会使校验金额为空，这是不能遗漏的分支。
5. **财务明细不是只靠查询接口关联。** 保存财务明细时，用业务单号查询业务主表，将所得业务主表ID写入财务明细的 `bill_id`；明细的 `header_id` 另指向财务主表。反查财务单号及汇总金额都使用该业务ID。未找到业务单据与查询发生异常是不同情形。
6. **欠款与财务累计的运算顺序明确。** 后端欠款公式为“折后金额＋其它费用－扣除订金－本次付款绝对值”，各空值按零。业务新增路径传入提交的 `debt`，不是在该入口重新调用上述公式；财务明细保存路径才按业务单据重新计算。财务SQL按业务ID合计有符号金额、排除已删除财务主/明细，Java再取合计的绝对值；最终欠款为欠款减该财务金额。财务明细路径在计算欠款非零时才请求更新，更新方法另检查必要金额非空。

范围：P3–P6。关联、库存口径和欠款汇总主规则可核验；金额校验和异常处理稿仍有重要错误。没有银行支付、总账记账、全局单号唯一性或完整运行时配置的证据，不补成完整外部结算闭环。

### 两个关键错误为什么不能忽略

多账户校验原文是：

```java
BigDecimal sum = StringUtil.getArrSum(accountMoneyList.split(","));
BigDecimal manyAccountSum = sum.abs();
```

同源 `StringUtil.getArrSum` 逐项相加，不逐项取绝对值。正确运算是 `abs(sum(x))`，不是 `sum(abs(x))`。即使常见页面输入同号，也不能改变后端实际规则。

财务异常处理原文是：

```java
JshException.writeFail(logger, e);
```

只读到这句不能猜成日志辅助；现有R4中的完整 `JshException.writeFail/readFail` 都有 `throw new BusinessRunTimeException(...)`。这些很短的方法没有被人工包附入，模型应报告未知，却作了错误控制流判断。辅助函数不是因为名字叫“日志/异常”就一定无关。

### 问题归属

- **取材缺项：**两个抛异常辅助方法已经在R4，缺的是本次阅读投影；状态/库存/剩余订金的六个辅助正文则确实没有进入正式R4。本次使用同源补充，不能关闭正式采集缺口。
- **模型/Prompt合同不足：**审阅仍写错运算顺序；某些包没有限制项却生成具名限制。现在的事实文字数组不足以确定性检验运算序列或未知项来源。
- **核验遗漏：**部分分支、查询过滤和引用没有保留完整。结构合法不能证明这些规则完整。
- **不是必然走不通：**主关联和多个计算条件在本次紧凑输入下被识别；但没有证据证明一次改Prompt或换模型就能完全修复。未做第二次实验，不将建议当已验证解决方案。

下一次薄修正应优先补入会影响返回/抛异常/数量金额的必要辅助实现，让计算式显式保存运算顺序，让具名未知引用输入中的实际限制，并逐条检查条件/过滤覆盖；不是重新取证、发送所有调用、建新的解释器或升级模型。需先讨论后续验证范围，不自动调用。

## 5. 结论与停止边界

1. **能核验到两组源码业务联系，不是“系统没有这些联系”。** 主关联和数量/状态/库存/财务机制都有实际原文。
2. **当前最小自动推理方案没有完全过关。** 取材缺项、运算/控制流错误及条件遗漏不能靠“12次都返回、字节够小”放行。
3. **尚未证明自主选材、全仓本体或通用弱模型兼容。** 本次材料是人工聚焦的；正式R4仍需后续修复具名缺口。输出为实验联系核验，不是六类正式本体定义。
4. **本次小实验到此结束，不全面修改、不扩大模型运行。** 所有原始输入、稿件和独立核验保留；后续最小修正及新验证另行确定。
