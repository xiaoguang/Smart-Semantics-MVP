# 两段业务联系的对象对应与组装：薄实验验收

## 当前结论

**本次定向组装可行：两个已经结束的局部识别结果，经一次对象类型提取和一次原文审阅，组成“采购入库单引用采购订单，采购订单引用请购单”的三对象、两联系骨架。** Java没有按同名自动合并，没有补造采购链箭头；模型明确确认两段采购订单属于同一种业务对象类型后，程序才统一节点并保留原有联系。

这证明的是已有两段联系如何接起来，不是重新证明全仓自主发现、完整采购生命周期、实例相等、数据库唯一性或任意小模型窗口。仍为可审阅实验结果，未注册新命令，也未安装成正式本体发布。

## 实际模型结论与原文核对

模型提取和审阅都确认`A:O1`与`B:O2`为`SAME_OBJECT_TYPE`。主要依据不是中文名字，而是两端实际业务类型条件和页面用途：

| 来源 | 完整原文中的实际内容 | 核对作用 |
| --- | --- | --- |
| A:S16 | `PurchaseOrderModal.vue`的`classifyIntoFormData`设置`billMain.type = '其它'`及`billMain.subType = '采购订单'`，返回序列化主表和明细 | A端实际准备提交的单据类型 |
| B:S12 | `PurchaseInModal.vue`的`onSearchLinkNumber`调用`show('其它', '采购订单', '供应商', "1,3")` | B端选择的来源类型 |
| B:S7 | `LinkBillList.vue`完整`show`方法接收并保存选择条件 | 静态实参与形参的连接依据 |
| B:S13 | 入库页面回调接收`linkNumber`并写入表单，接收和整理明细 | B端对象用途，不推断请求实际成功 |

模型还返回四项`DISTINCT`及三项未知；程序不因它们结构合法就宣称全部业务判断已经人工确认。核心相同类型依据经过上述原文核对。类型相同**不证明是同一笔订单**，不证明编号唯一、关联基数、请求路由或运行时存储相等。

旧A联系继续引用其原包中的A:S18/A:S19/A:S20及XML、getter和使用端；这些并未在本次类型任务里重读。旧B联系继续引用自己的原包。

### 已知旧稿误写不掩盖

B的详细机制仍把`record.number`写入`linkNumber`归给S12；真实赋值在B:S6的`handleOk`，S12只是打开选择器，S13接收并写表单。B:S6完整原文在旧B冻结包中存在。本次保留旧稿，没有手改成正确模型JSON，也没有额外第三次修稿。

旧B未知说明还把导航限制归到`candidateDiagnostics`，实际限制来自调用记录，机械诊断为空。这两项属于已提交材料的解释／来源归属错误；不会让实际编号关系消失，但不能把全部详细说明称为无误。辅助方法、数量、状态、库存和结算效果仍未获得新的证明。

## 确定性组装与实际图

Java只执行审阅明确返回的类型对应：原7个对象引用归入6个节点，6条原联系全部保留，端点闭合。其余对象和联系没有因主图只显示3节点而被删除。

审阅的`focusLinkRefs`实际为空：模型没有选出一个“跨组新箭头”。程序保存原响应，不修改它；主图采用一个明确的**显示规则**：从不同结果组的既存有向边中选择经过已审共同节点的连续两边。该规则只选择现有边，不推断新关系、办理顺序或业务语义。本次唯一得到：

```text
采购入库单 ──关联采购订单──→ 采购订单 ──通过linkApply引用请购单──→ 请购单
```

图中箭头表达“当前单据引用哪个来源”，不是时间上的办理顺序。因此，它使三个业务对象连通，但不能仅凭此图宣称全部采购业务规则已识别。

离线浏览器显示实际3个节点、2条边；脚本错误0，网页网络请求0，PNG已查看。浏览器首次在沙箱内启动失败，具体是macOS `bootstrap_check_in ... Permission denied`；获准在沙箱外启动同一个只读预览检查后通过，不是新增模型或业务重试。HTML复用已安装离线Mermaid资源，约2.64 MiB，其中包含工具资源；不是模型输入大小。
