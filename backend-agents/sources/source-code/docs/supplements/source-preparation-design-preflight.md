## 2. 排除不只是给文件加标记

**持续 backlog：SOURCE-PREPARATION-DOWNSTREAM-EXCLUSION，尚未实现、不得关闭。**

当前还有一条必须处理的实际路径：Step05 保存了方法正文和持久化资源原文，Activity 投影可直接使用这些保存内容；历史 M10 又含有保存的 SourceReference 片段。因此，只修改公共原文读取器，并不能阻止旧材料重新把被排除文件交给后续分析。

必须分别检查：

1. **新源码范围的读取：**被排除文件不能出现在返回的可分析文件集合或按路径读取结果中。
2. **旧材料用于新分析：**进入新执行前，比较本次选定的源码版本/范围与材料的来源。不能只比较仓库名称、Git 提交或“文件还能打开”。
3. **历史查看：**旧材料继续属于旧来源版本，允许只读查看；不修改、删除或伪装成新范围的结果。

用户已在本轮确认：**本次详细设计和实施计划包含这些必要检查；不修改后续分析算法、不拆后续 CLI、不运行后续分析。** 本项仍须保持为持续验收 backlog，而不是得到批准就标记完成。

本项最低关闭条件见[待办记录第19.1项](implementation-lessons-and-followups.md#191-持续验收项排除规则与旧材料版本检查)。只通过源码准备本身的测试不足以关闭。

## 4. 本轮已逐项确认的政策

### D1. 必要下游接线范围：已确认

本轮包含公共读取和派生材料进入新执行时的源码版本/范围检查；旧结果保留可查看。范围止于必要检查，不实施后续算法变更或自动重新分析。

### D2. 普通目录的默认范围：已确认

用户选择：除了 Git 元数据 `.git`，其余普通文件默认纳入；隐藏文件、依赖目录和构建输出不按名称静默过滤。用户可以显式配置排除，并在结果中看到对应范围。输出目录放在源码目录之外，防止把程序自己的输出再次捕获。

不得另行加入 `node_modules`、`target`、`build` 等名称的自动排除规则。源码目录里的压缩文件不自动解压；“不支持压缩包输入”不代表扫描时按后缀静默删除普通文件。

### D3. 不能列出的子目录：已确认

用户确认：继续检查其它可安全读取的目录，记录该子目录“内容未知”，不编造文件数。允许用户显式排除这个具名子目录及其全部内容，或修复权限后重新准备它。源码根目录不存在或完全无法列出时仍返回输入问题，不提供“排除根目录后继续”的操作。

该排除继承到以本版本为基础的后续版本；与独立NEW的明确新范围区分。

### D4. 固定 Git 提交的单文件重新准备：已确认

用户确认：同一提交只重新取得该提交保存的文件，不读取工作树修改；要采用工作树的新内容，改用普通目录建立新来源，或指定新提交重新准备 Git 来源。不混合不同提交文件后仍宣称它们全部来自旧提交。

普通目录允许从选定基础版本重新准备具名文件，其余内容沿用原已保存版本；必须在新结果中写明这是局部更新，并不表示已重新检查整个当前目录。

### D5. 新旧源码版本之间的材料复用：已确认

用户接受首版检查整份材料记录的源码版本/范围是否与本次输入完全一致，不计算文件依赖影响。一个文件重新准备或排除形成新版本后，旧 Step05/Activity 等仍可按旧版本查看，但不能直接作为新版本的分析输入；程序不会因此自动重新取材或调用模型。

若要求“自动识别旧材料是否真的受该文件影响，只重算有关部分”，需要新的依赖与跨版本复用设计，不能隐藏在本轮最小接线里。必须明确这个代价，不能只说“增加版本检查”而让用户误以为所有旧材料仍能直接接续新来源。

### 可由详细设计确定的实现细节，不要求用户逐字段批准

- 结构化问题字段、错误类别、状态名、退出码与诊断路径。
- 新版 schema/producer、不可变身份计算、严格历史读取和原子保存。
- 未处理问题的报告：保存结果，提示明确解决或排除；不擅自替用户跳过文件或启动后续分析。
- 安全路径、输入输出不重叠、非普通文件及不受支持输入的分类；禁止读取源码根之外的目标，用户不能用“继续”改变读取边界。
- Git submodule 不自动检出或读取外部仓库；必须具名列出不受支持范围，不能当作普通源码已准备。允许的进一步处置遵守最终确认的文件/目录排除合同。
- 诊断只记录可确认原因。权限错误、目录被删除、存储设备不可用等是可能情况，不能仅从“无法列出”猜具体原因。
