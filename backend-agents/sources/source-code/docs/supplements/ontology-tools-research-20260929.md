# 固定静态证据到企业 Ontology：现成工具候选研究

状态：2026-09-29 **一手资料与公开源码研究候选，非批准设计、实施计划或运行授权**。本轮未安装或运行候选工具，未运行客户源码、产品模型或 Ontology 生成；“可复用”均为接口与源码层面的判断，需以后用固定样例验证。公开仓库的 `main`/`master` 页面会变化，以下结论对应本次阅读，不替代版本锁定。

## 结论与当前输入边界

主要的技术组织入口是本 Agent 保存的 [`entry-evidence-v1`](../modules/technical-analysis/entry-evidence.md)：每个后端 HTTP `entryId` 一份自包含 JSON，含 Vue 请求用法、完整 Java 方法/物理调用、Mapper/XML/SQL、确定与候选关系、`sourceRefs`、`limitations`，另有入口索引和未匹配请求覆盖。同一冻结 R0 中已经验证、获准使用的 DDL 等资料也可作为并列原始证据；R4 未装入的内容不能说成入口 JSON 已包含。当前材料主要是**静态源码与数据库结构证据**，没有业务行、运行时动作执行、企业政策或 Foundry 对象实例。业务对象、性质、关系、动作和规则只能是待核验候选；尤其不能把表直接升为对象、外键直接升为业务链接、HTTP endpoint 直接升为业务 Action。Palantir 官方区分语义元素（object/property/link）与操作元素（action/function），并要求按业务用例验证本体设计，见[本体概览](https://www.palantir.com/docs/foundry/ontology/overview)、[Action 类型](https://www.palantir.com/docs/foundry/action-types/overview/)、[建模实践](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/)及[设计验证](https://www.palantir.com/docs/foundry/ontology/ontology-design-validation/)。

先复用已保存的技术身份、原文和 `sourceRefs`，按完整方法、调用点、XML statement 与依赖单元取材，再由模型提出、人工核对业务候选；不预设新图数据库、GraphRAG 管线或证据平台。Semantica 的模块接口值得以后用小样本逐项验证，**本轮不将其列为默认核心依赖**；它们不能直接消费原入口 JSON，也不会生成完整的 Palantir 式 operational Ontology。若经审阅后确需 RDF/SHACL 约束检查，Apache Jena SHACL 是边界清楚的候选，但当前 Jena 6 要 Java 21，需与本 Agent 的 Java 17 运行约束分开评估。Microsoft GraphRAG 更适合大语料探索与检索；OntoBricks 的 Databricks 服务和许可证约束使它不适合直接嵌入本 Agent。[Semantica 模块选择](https://github.com/semantica-agi/semantica/blob/main/docs/choose-your-module.md)、[Jena SHACL](https://jena.apache.org/documentation/shacl/)、[Jena 发布要求](https://jena.apache.org/download/)、[GraphRAG 数据流](https://microsoft.github.io/graphrag/index/default_dataflow/)、[OntoBricks 许可证](https://github.com/databrickslabs/ontobricks/blob/master/LICENSE.txt)。

本轮主任务对已保存固定源码作**只读人工审计**（不是 Ontology 模型输出，也不是本研究运行候选工具）：339份入口 JSON 合计153,083,646字节，中位数263,197字节、p95为1,573,607字节、最大3,530,376字节；`GET /depotHead/list` 文件3,053,567字节，含134个方法、487处调用和12条XML/SQL。跨入口的方法出现6,695次而唯一 `methodKey` 为1,788个，SQL statement 出现650次而唯一 `statementRef` 为260个；入口自包含造成的重复须按原身份处理，不能把出现次数读成对象或规则数。该入口的12条前端关系仍为未知 baseURL 下的 `UNRESOLVED_REQUEST` 候选，不能称为确认页面调用。技术运行与限制见[固定源码验收记录](technical-entry-evidence-acceptance-20260929.md)；这里的体积与重复统计仅为主任务当日保存产物的人工审计，不推论业务语义。

一个更接近业务 Action/规则的**人工源码审阅例子**是 `POST /depotHead/batchSetStatus`：对应 `entry-572a7d0add93cece17cac58b6c67aa4578c4ee78a04aa0dec93b7fafe583804f.json`，保存的 `DepotHeadService.java:741–822` 表明审核到 `status='1'` 要求当前 `status='0'`；反审核到 `status='0'` 要求当前 `status='1'` 且 `purchaseStatus='0'`，已完成或部分办理会拒绝；随后按配置检查库存、更新并记录日志。同源 R0 已验证但未装入 R4 的 `fixed-source-8c30ce7/jshERP-boot/docs/jsh_erp.sql` 含 `depot_head` 的主键、状态字段和注释，以及 `depot_item.header_id`，未见 `FOREIGN KEY` 声明。以上仅支持提出“单据审核/反审核”及状态前置条件候选，**不是已经生成的 Ontology Action/规则，也不证明运行执行、权限或页面关联**；该入口前端确认与候选调用均为0。DDL 中的 `header_id` 也不能机械升为业务链接。

## Semantica 源码与宣传之间的三个关键落差

1. **类/属性是明确输出，动作/规则不是。** `semantica.ontology.__init__` 确实导出 `LLMOntologyGenerator`，实际文件叫 `llm_generator.py`，而非 `llm_ontology_generator.py`。其 `generate_ontology_from_text` 一次调用 `provider.generate_structured`，提示样例仅有 `classes`、`properties`；`_normalize_output` 丢弃其它模型字段。确定性 `OntologyGenerator` 同样只构造类和属性，且默认 `min_occurrences=2` 会过滤只出现一次的类型/关系。因此不能以“有 action/reasoning 模块”推断生成器会产 operational Action/规则，稀有重要类型亦须单独审阅。[导出](https://raw.githubusercontent.com/semantica-agi/semantica/main/semantica/ontology/__init__.py)、[LLM 实现](https://raw.githubusercontent.com/semantica-agi/semantica/main/semantica/ontology/llm_generator.py)、[确定性实现](https://raw.githubusercontent.com/semantica-agi/semantica/main/semantica/ontology/ontology_generator.py)。
2. **`OntologyValidator.validate()` 不等于逻辑校验。** 当前源码明示 placeholder：字典缺少 `classes`/`properties` 仅产生 warning，consistency/satisfiability 分支为 `pass`，`check_constraint()` 恒真。实际 `run_shacl_validation()` 是另一个入口，要求 RDF/SHACL 字符串与 `pyshacl`、`rdflib`。不能引用概览中“HermiT/Pellet”文字来声称输出经过推理器验证。[验证器源码](https://raw.githubusercontent.com/semantica-agi/semantica/main/semantica/ontology/ontology_validator.py)。
3. **分块与治理模块存在，但不自动串成当前证据合同。** `TextSplitter` 接普通文本，offset 是投影文本字符位置，不是 R0 源码位置；语义分块引入 embedding，entity/relation-aware 引入提取模型。冲突检测要在合并前运行，官方参考也明确 `TEMPORAL`/`LOGICAL` 尚未直接实现。`ProvenanceManager` 等可承载来源，但入口 `sourceRefs` 到候选每条陈述的绑定仍须由调用方保存与核验。[分块参考](https://docs.getsemantica.ai/reference/split/)、[冲突参考](https://docs.getsemantica.ai/reference/conflicts/)、[溯源示例](https://docs.getsemantica.ai/concepts/)。

## 若以后做窄试，最小需本项目承担的部分

这不是施工许可或新平台设计，而是工具**没有代办**且当前证据合同需要保留的工作边界：

1. **只读取材与容量界限。** 从已保存 `entry-evidence-index` 按 `entryId` 读取，并允许同一 R0 中经验证的 DDL 等材料作为另一个来源。优先用已有 `methodKey`、`statementRef` 和 R0 源码身份消除跨入口重复，按完整方法、调用位置、前端请求、XML statement/依赖等语义单元组织有界阅读；保留 `entryId`、上游版本、原 `sourceRefs` 与精确成员ID。模型读不完时标明未读范围，不把文本 chunk 偏移当原始源码位置，也不让通用切分截断语义单元。Semantica/GraphRAG 的文本分块可作为将来实验对照，**不是默认取材步骤**。[当前入口合同](../modules/technical-analysis/entry-evidence.md)、[Semantica 分块接口](https://docs.getsemantica.ai/reference/split/)、[GraphRAG 分块配置](https://microsoft.github.io/graphrag/config/yaml/)。
2. **语义候选与归并审阅。** Object 是经业务问题确认的概念，property/link 是经代码链和业务语义支持的候选；仅把**已确认的静态边**当技术关系。前端 `candidateRequestUses`、JDT observations、未知 baseURL、动态 SQL 分支和 limitations 随候选保留，不升格为事实。业务候选可由模型对具名证据提出，由现有证据引用与人审核对决定归并或冲突；`methodKey`/`statementRef` 去重解决技术重复，不能代替业务同义归并。Semantica 的相似度/冲突 API 仅是待实测可选工具，不应在未核验前成为生产准入。每个最终陈述都须能返回原入口、同源 DDL（若用到）和具体源码范围。[入口状态合同](../modules/technical-analysis/entry-evidence.md)、[Semantica 去重](https://docs.getsemantica.ai/reference/deduplication/)、[冲突](https://docs.getsemantica.ai/reference/conflicts/)、[Palantir 建模实践](https://www.palantir.com/docs/foundry/ontology/ontology-best-practices/)。
3. **Action 与规则的证据门槛。** `batchSetStatus` 的审核/反审核分支能提供一个待审核的动作与前置条件候选；不能从 Controller route 或 SQL `UPDATE` 单独推断用户意图、对象状态机、权限或执行结果。规则要区分代码条件、SQL 条件、平台治理规则与业务政策，不从 if/where 文本直接批准企业政策。Semantica `reasoning.Rule` 和 Jena SHACL 只在**已定义规则/约束之后**执行或检查它们，不负责从源码判定组织政策。Foundry 运行实例、安全治理和动作执行不在当前静态证据内；候选产物也不保证可直接导入 Foundry。[Palantir Action](https://www.palantir.com/docs/foundry/action-types/overview/)、[设计验证](https://www.palantir.com/docs/foundry/ontology/ontology-design-validation/)、[Semantica 推理](https://docs.getsemantica.ai/reference/reasoning/)、[Jena SHACL](https://jena.apache.org/documentation/shacl/)。

## 决策建议与未验证项

- **首选研究路线：** 以入口 JSON 和同源 R0 的获准资料为证据，复用现有 `sourceRefs`、执行任务及其保存能力；先按稳定源码身份去重和完整单元取材，模型只提出 business Ontology 候选，审阅者按原证据和业务问题核对。无需为此先建设 GraphRAG、图数据库、证据平台或新恢复/审批框架。Semantica 的具体模块仅在具名问题显示价值后逐个小样本核验，不预置为核心依赖；若后续确需 RDF/SHACL，再评估独立 Jena SHACL。不得引用 Semantica 的普通 `validate()` 作为一致性通过依据。此处不批准实施或调用模型。[当前入口合同](../modules/technical-analysis/entry-evidence.md)、[Semantica 模块选择](https://github.com/semantica-agi/semantica/blob/main/docs/choose-your-module.md)、[验证器源码](https://raw.githubusercontent.com/semantica-agi/semantica/main/semantica/ontology/ontology_validator.py)、[Jena Java 要求](https://jena.apache.org/download/)。
- **不选为主路线：** GraphRAG 的语料检索/图摘要目标与对象/动作/规则候选合同不一致，且 LLM/embedding 步骤重；OntoBricks 强依赖 Databricks 且受专有许可限制；身份未确认的 `enterprise-ontology-builder` 暂不能评审。它们可以启发比较维度，不能替代具名证据验收。[GraphRAG 输出](https://microsoft.github.io/graphrag/index/outputs/)、[OntoBricks 许可](https://github.com/databrickslabs/ontobricks/blob/master/LICENSE.txt)。
- **仍须核验：** 当前实际入口全集的内容准确性和已保存 `sourceRefs`；某一具名业务问题能否从不同入口拼出对象边界与条件；Semantica 稳定版本的上述模块行为、依赖及大材料资源占用；Jena 的 Java 21 隔离或经许可的兼容版本；人审后的 RDF/SHACL 约束是否表达所需语义。研究结论不把官网能力、源码阅读或别处 release 数字称为本项目实测。
