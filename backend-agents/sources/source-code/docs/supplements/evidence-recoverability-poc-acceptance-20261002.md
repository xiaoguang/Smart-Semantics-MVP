### 金额错误如何定位，而不是相信新稿

新稿的 `amount.review.facts[2]` 引用S1；S1中实际是：

```java
BigDecimal sum = StringUtil.getArrSum(accountMoneyList.split(","));
BigDecimal manyAccountSum = sum.abs();
if(manyAccountSum.compareTo(depotHead.getChangeAmount().abs())!=0) {
```

S2完整helper中的循环实际是：

```java
sum = sum.add(new BigDecimal(strings[i]));
```

因此 `[100,-40]` 的两种算式结果是60与140，不能互换。这是独立核验的反例，没有送给模型。私有mapping将S1/S2分别带回固定源码和完整保存单元；S2也明确保存“同R0补充、非正式R4展开”的身份。**可以核对方法源码定义，不能由此把可疑调用升级为确定绑定。**

## 4. 残余问题与不能宣称的成功

1. **异常稿对限制的总结过宽。** 实际R4中S1→readFail与S2→writeFail均为LOCATED/BODY_INCLUDED；冲突属于另外的构造/查询条件调用。稿件未知项仍笼统说“正式调用目标绑定仍未确认”，没有指出具体调用，易让人误以为这两个helper也未确认。应根据保存的逐调用观察给出精确纠正，不能删除全部限制，也不需要第9次模型请求。

   **人工核验补充，不替换原模型稿：**“本组readFail/writeFail的调用已定位且完整正文已提供；它们记录日志后抛出异常。getDepotHead的另一些构造/查询条件调用仍有候选或冲突，本组没有解决那些调用。”这是利用保存的正文和逐调用状态得到的具名纠正，证明本例可以反查；不是程序或模型自动识别所有错误的证明。
2. **有依据的规则正确，不表示整份文字已经无歧义。** 库存稿对空值风险有概括性条件描述；第二项时间过滤的文字省略了明确左右操作数。原XML仍能核对；正式定义应保存明确的条件和引用，而不是只依赖散文。没有为此建设SQL/中文解释器。
3. **formal缺口仍在。** 新稿正确不关闭getArrSum正式绑定、前端选择保存单元或自主选材缺口。R4及同R0能支持此次人工核验，不等于仅R4已完整、也不等于框架已经自动补齐必需实现。
4. **不是受控消融实验。** 相对旧实验，同时缩小问题、调整材料并修改通用限制提示；不能把改善归因于某一个因素。四项核心问题在这次EXTRACT阶段已经答对，不能说REVIEW修好了旧批次那些错误，更不能保证再问一次仍答对。
