## 1. 要保留的成果与要纠正的问题

用户认可的是能按办理顺序读懂的业务正文：知道处理什么、怎样衔接、允许什么、拒绝什么、分批与回退怎样进行。不是要求列出所有实现细节，也不是要求证明每一句话。最新正文已达到用户认可的阅读水平；已审核误写为未审核、支付订金/本次付款混写为应付金额仍是具体准确性问题。

小实验提供三项有用事实：

1. 模型从 README、326 张 Activity 导航卡和冻结文件目录自行识别系统特征，并提出业务调查方向。指令没有预置行业类别或期望链。
2. 页面说明、后台实现和相关查询一起阅读，能解释跨对象办理联系；326 条已审 Activity 可直接复用。但自动包扩大到 80 文件、32 Activity，说明“找到有关材料”还不等于“按一个问题聚焦”。文件多本身不是失败，缺少关键内容或大量无关展开才需要处理。
3. 事实推理和业务写作分开，能够产出用户接受的文章；写作仍可能改错已核对事实。因此最后一次核对必须看到**实际写出的全文**，之后只做确定性保存、编号和排版。

不要求再次证明整个思路可行。本设计把这些经验变成明确职责；三例验收检查实际正文，而非再开新一轮工具选型或证据实验。

## 3. 什么时候判断系统类型

在 Step07 的**全局选材请求开头**判断，尚未展开候选大量源码时就形成初步认识。已有 JDT/Activity 的仓库直接到这一步，不为了认识系统再扫描。新仓库仍走已有前置链和首次目录能力；类型判断不改变 JDT、JavaParser、Spring 入口识别或源码冻结。

首次实际可见材料：根 README 等已冻结项目说明、已有目录（可空）、全部 Activity 的名称/目的/对象/入口导航、全部冻结文件的相对路径与行数。项目说明未保存时允许缺省；文件名只能作为查找线索。文件取回按已有读取器完成，Java 可以识别 README 这种技术文件名，不内置行业词表。

同一次 PROCESS_MATERIAL_SELECTION 返回：

```json
{
  "systemAssessment": {
    "description": "根据实际资料概括系统用途",
    "typeHypotheses": [
      {"label": "模型提出的类型，可多项或未知", "basis": ["实际观察"], "uncertainties": []}
    ],
    "businessHypotheses": [
      {"key": "H1", "name": "值得调查的业务方向", "hypothesis": "暂时认为哪些对象可能怎样衔接", "whyInvestigate": "材料线索或常识提示", "refutingObservation": "什么实际观察会否定或收窄这个猜想", "questions": ["需要原文回答的具体问题"]}
    ]
  },
  "candidateChanges": [],
  "oldCandidateDecisions": [],
  "changedActivityDispositions": []
}
```

示意不作为模型默认答案。类型是可多选的自由标签，没有 ERP/CRM/WMS 枚举路由，不设“超过某置信分才能继续”。一个系统可以混合多种能力，也可以暂时无法归类。模型必须同时注意与初判不相符的活动；类型不能限制召回范围。

业务常识用于**提出问题**，例如系统看起来有商品、订单、库存时，值得寻找对象交接和数量变化；不由“这是 ERP”推出财务、机构、采购一定实现。能力结论必须回到取回的材料。阅读发现假设不成立时在候选范围/待确认中纠正，不重跑全局判断、不启动循环调查。

没有稳定全仓信息或一次请求确实装不下时，保留全部导航与未执行说明；本轮三例不建设新的分层搜索框架。已有首次目录分片可继续复用，但不能把只看一个分片称为看过全仓。

## 4. 如何少重做材料

FrozenAnalysisCorpus 的接口和可信来源保持现状：重开 ReviewedActivity、coverage、M10 SourceReference 和冻结文本；按 ID、文件范围、整文件和字面量搜索读取。需要 SQL、Vue、mixin 或常量时，读取原文给模型，不新写这些语言的业务解析器，不执行 SQL 或客户代码。

复用层次要分清：

| 保存内容 | 本轮用途 | 什么变化才影响它 |
| --- | --- | --- |
| JDT 导航、冻结文件、M10、326 Activity | 原样读取 | 源码版本或上游取材任务明确变化；Step07 Prompt 变化不影响 |
| 原目录 | 资料起点，可沿用历史候选 | 不是已完成的新发现；不要求旧 Prompt 等于新 Prompt |
| 历史阅读包 | 三例可作为已有人选材料基准；可读范围依然同源 | 必须说明人工/历史选择，不能声称新自主选材成功 |
| 新选材/阅读决策 | 完整成功且输入及 Prompt 等匹配时显式复用 | 新问题、导航、范围或 Prompt 变化 |
| 最终三阶段结果 | 三次均完整且匹配时复用 | 实际包、任务序列、Prompt、Schema、模型绑定变化 |

完整 Activity 的原解释与新读源码不一致时，过程事实可依据原文纠正，私有核对说明记录差异；原 Activity 不被覆盖，也不触发重建。缺少一个来源链接允许为空。未找到关键规则则写具体未知，不能为了补链接启动新取证任务。

历史结果、失败记录、原始模型响应不可覆盖。判断字节损坏和错来源只在现有磁盘边界进行，不重复证明普通内部传递。

## 5. 聚焦选材：问题决定读什么

候选增加 `investigationQuestions`，每项是可由材料回答的具体问题；读取请求的现有 purpose 写明对应问题，可附局部 questionKey。它是阅读说明，不是新证据账本，不要求每句正文登记。

当前实现已将读取purpose保留到实际读取结果、决策和任务metadata。程序按首批请求顺序及实际返回片段顺序分配包内`R1…Rn`作为ReadingRecord ID；CHECK同时看ID、请求目的、实际范围、完整/预览标记和文本。一次搜索返回多个片段时，每个实际片段各有一个R，允许分别保留，不以整次请求作为不可分割单位。未命中只有原因，没有假造可读片段。先执行保留/補读选择，再按现有来源规则去重；相同片段来自两次请求时，保留任一记录就保留原文，合并其阅读目的。R只用于私有取材选择，不进入业务正文或变成新的Proof身份。

通用问题类别包括：业务起点、前后对象选择和关联、可选或必经、分批数量、金额用途、状态条件、拒绝/回退、配置例外和结束结果。没有数量金额的业务无需硬填。不要把“全面阅读所有有关文件”当作目标。

首批优先取完整关键业务方法、相关页面说明/操作、影响当前问题的查询语句。完整实现的条件/返回不能只剩搜索命中一行。日志、租户、权限、实体字段只有影响当前过程适用范围或具体拒绝条件时才继续展开；没有一张通用排除黑名单。

阅读检查要能**减少**材料，而不只是继续追加。新增明确的最终选择结果：

```text
final activityUses / contextActivityIds   保留现有完整集合语义
retainedReadingRecordIds                 首批实际读结果中继续进入最终包的记录
supplementaryRequests                    一次新增读取，可空
unresolvedQuestions                     仍未回答的问题及影响
selectionNotes                          保留/移出/补读的简短理由
```

Java 只执行选择，不猜哪些业务重要。最终包由保留的首批记录＋实际补读结果＋最终成员/context 的完整 Activity 构成。首次读取内容仍保存，即使从模型最终包移出也不删除历史。不得把“最终选材”误解释为抛弃全部首批原文；CHECK 必须明确列保留集合。

大文件首批请求可以先得到**明确标注**的目录/预览和实际搜索结果，由阅读检查选择完整相关范围。预览不标作完整实现，不作为最终业务结论的唯一代码依据。优先复用已保存定位信息；没有定位时让模型按真实行段选择，不加入研究脚本中的自研 Java 语法扫描作为生产依赖。

这部分的最小接线已实现：仅在`INITIAL`的`WHOLE_FILE`请求中，将超过120行的文件作为前120行的明确预览交给CHECK；较小文件照常完整提供。私有ReadingRecord记录实际行段、原文件`totalLineCount`、`complete=false`及`preview=true`，其它记录明确`preview=false`。120行只是首读导航预览长度，不是最终业务范围、文件数量上限或源码删除门槛。同文件已有M10来源引用以`ref/文件/完整行段/前8行原文`放入CHECK外层`savedSourceLocators`定位目录，不混入`readingPacket.sourceExcerpts`；未发送完整正文的来源不能被描述为已经阅读。冻结文件原文和已保存来源不变，CHECK可使用现有SOURCE_REF或FILE_RANGE请求补读完整相关实现；补读的WHOLE_FILE仍读取整文件，不自动再次预览。

一个R代表模型实际看见的片段。保留首读预览R只能保留该预览，不能在封包时悄悄恢复成原整文件。完整关键范围由模型的补读选择决定；仍缺材料则记录具体未知。不增加Java/XML/Vue语义解析、JavaCodeIndex读取、阅读轮次或隐式模型调用。CHECK v4提示词明确区分预览与完整材料，既有内容指纹包含实际预览、定位导航及新Prompt；SELECT输入/Prompt保持不变。启动前容量失败未消耗内容轮；保留诊断、修复并验证后，在已有三例范围授权和明确继续指令内显式启动新批次，不重复询问同一授权。遵循根AGENTS规定的最多两次修复后重启；真正已启动请求失败、业务质量问题、额外轮次或范围变化不适用这个例外。

包内源码去重、完整 Activity 一份、多业务用法分别保留。上下文 Activity 不因被读或引用就自动成为业务步骤。补读仍只有一轮，读完还缺什么就具体记录。大包不因为文件数量高就判失败；实际上下文容不下时明确停在取材结果，不静默截断或将费用预算作为业务范围限制。

## 6. 事实推理、写作和最终核对

### 6.1 DRAFT：把业务逻辑说明白

输入由现有完整 ProcessReadingPacket 和本次调查背景共同组成，明确使用下列外层任务输入，而不是给旧包悄悄添加字段：

```text
readingPacket：v1完整包，含真实Activity、原文、读取限制和可用引用
investigationContext：关注问题、系统判断、选中的业务假设、候选调查问题
readingSelections：实际读取记录编号、各自用途、保留/补读说明
```

后两项从本次已保存的选材/阅读决策取回，参与任务输入指纹，并实际发送给DRAFT；不能只在日志里保存。系统类型和业务假设是调查背景，不是确认事实。包v1保持不变；最终RULE_REVIEW使用同一外层输入，再附完整实际DRAFT和WRITE。无需新建证据协议或另一套材料台账。

调用 PROCESS_DRAFT，保留现有详细 Process 响应形状；阶段 narrative 此时可以是完整事实说明，不要求文学润色。无需另造一套 ontology 或规则语言。

输出保留目的、对象、用法、阶段、转移、进入/拒绝条件、状态变化、规则、公式、结果、支撑查询和未知。每条关键规则按实际业务场景解释：触发事件、对象用途、条件、动作、否则结果、配置例外。正文读者不需要记 status 数字；模型在已有字段中写清业务名称，必要代码值保留在原记录的技术说明。

相同字段在不同页面含义不同，必须按用途分别解释；如已有原文显示同一金额字段分别用于订金与当次付款，就不能统一翻译成应付总额。数字例子只为核对规则，明确是演示值，不是客户数据。正例和反例应能检查边界，而不是只列总能通过的数字。

DRAFT 可判断只支持片段、拆成多个过程或材料不足；不强填用户举例的链。不因为存在直接建单或分批办理，就否认材料已经支持的正常关联主线。

### 6.2 WRITE：把完整事实写成可阅读业务说明

输入：本次完整实际事实草稿，包含已解释的名称/用途、具体规则和未知。写作不再寻找材料，也不拿旧文章当事实。保留同一响应形状和稳定局部 ID；输出完整记录，使 Publisher 无需从另一份散文猜回结构。

写作按办理顺序组织：业务如何开始、各步办理什么、系统检查什么、形成什么、下一步如何接续。可选、分批、修改、撤销放在对应步骤，查询统计作为支撑。关键条件必须在业务段落中读得到，不只藏在结构字段或折叠区。

名称、目的和阶段用业务语言；不把“材料支持、可证明、入口、参数列表、执行派生联动”作为通用模板。确实分析接口管理等技术业务时可使用相应术语，Java 不设技术词黑名单。

实际规则保留对象和作用域，不再推导公式、统一不同字段用途或添加未读的岗位制度。实现明确保存业务记录时可以直接写“系统保存单据”；只有会影响读者理解的未知才集中说明，不在每段加运行时免责声明。

### 6.3 RULE_REVIEW：检查读者最后会看到的内容

输入：同一个完整原文包＋实际事实草稿＋实际写作全文/结构。调用新的 PROCESS_RULE_REVIEW。WRITE 是未最终核对结果，不能在它完成时标为 reviewed。

重点核对：对象交接、允许/拒绝及否定词、具体状态和默认条件、数量/金额/单位、字段的业务用途、配置范围、规则触发事件、分批回写和回退，以及正文与结构字段是否一致。原文优先于两份模型文本；Activity 仍可提供辅助背景。

返回`{processResult, corrections}`：processResult是现有完整候选过程响应，corrections是私有修改清单。finalizeCandidate取processResult交给既有过程parser及来源归一化，不把包装对象直接交给旧parser。每项只需过程/阶段定位、原句、改句和原因；来源用已有字段，不为每次修改建Proof。无错误时清单为空，完整结果仍须返回。DRAFT与WRITE保持原候选响应形状，阶段原始返回全部保存。

核对模型直接修正能确定的具体错误，同时修正对应结构字段。它保持已认可的表达和正常主线，不为了审阅重写整篇。无法确定的规则收窄或留具体待确认。确有重大矛盾可退为材料不足，不能明知错误仍作确定结论。

最终核对之后没有另一次模型润色。Java 只校验结构、实际引用、保存和排版，不负责判定中文蕴含；模型自查可能漏错，三例人工审阅仍应明确发现情况。自动检查发现的是 JSON/ID 等程序问题，不能冒称已经自动发现业务错误。

## 7. 保存、并行与版本：影响限制在过程任务

`BoundedModelJobExecutor` 仍调度一个完整候选 Callable；同一候选的三次顺序调用和保存占用一个已有并发名额，保持同一 Provider/账户/model/effort。其他候选可并行。Activity、首次目录和仓库归并仍用原有两轮协议。

过程私有记录已改成完整三阶段记录，不能在旧 pair 里把 WRITE 塞进 draft 后声称 RULE_REVIEW 已看过原始推理。实际字段：

```text
schema = model-job-reviewed-result-v3（仅新过程记录）
pipeline = business-reasoning-writing-rule-review-v1
input（完整实际DRAFT外层输入，含调查背景及选择metadata）
readingPacket / source mapping / inputFingerprint / runtime binding
draft（完整事实响应）
writing（完整业务写作响应）
review（完整最终结果与 corrections）
reusedFromModelBatchId（可空）
```

三次原请求/原返回、时间和失败均沿用 journal 保存。完整成功记录才可作为新协议结果复用；历史 v2 pair 严格只读，仍可作为研究输入或历史产物读取，但不当成完成三阶段。完整原始请求可独立落盘用于观察，单独成功 DRAFT/WRITE 不自动续接成新 reviewed job；保留显式新批次和无自动重试政策。

实际DRAFT/WRITE在fresh后及匹配复用接受前均按本候选实际响应Schema做结构校验（已有networknt2.0.1，本地$ref），类型/必填/enum等损坏不能被最后合法结果掩盖成完成。fresh报PROCESS_MODEL_SCHEMA_INVALID，损坏复用报MODEL_JOB_RESULT_INVALID；raw响应不改，不隐式重跑。这里不提前执行最终parseCandidate的覆盖/CONFIRMED依据或中文语义判断，合法INFERRED/UNRESOLVED仍允许，金额/状态等业务错误和最终收窄仍由RULE_REVIEW修正。

每次调用前检查真实序列化的input、Prompt、Schema及输出空间，沿用现有profile和容量函数。DRAFT前能容纳不代表最终核对也能容纳。如果WRITE完成后才发现`原文包+DRAFT+WRITE`超过上下文，保存两次实际结果和未完成原因，不删其中一份来强行调用，也不标为已审或自动重试。下一次显式执行如何收窄输入另行决定；不是重新扫描源码。该情况与费用预算无关。

某候选 fatal 时停止新派发，已启动且自身合法的候选可完成剩余阶段并保存。语义不足且合法返回保留不足处置；缺来源链接不等于 fatal。不得通过开新批次自动绕过失败或不断试写。

## 8. 归并、渲染与小样范围

全仓归并继续接收业务完整的已审结构，决定重复、父子、相关、替代关系；不得改写已最终核对的正文。不能无损合并时保留原过程，不拼接 stage 数组制造长链。需要真正新增衔接文本属于新的业务重建工作，本轮三例不执行。

Publisher 从最终 review 结构确定性生成业务标题、阶段正文、分支、规则、知识正文/公式和结果。producer v4及preview不输出 `<details>`/`<summary>`，阶段全部条件/动作/状态变化/拒绝/结果/转移仍完整可见，不向业务正文倾倒技术 Activity 名称和裸引用长串。来源放 sources.md，链接文字为“查看依据”，缺链接可空，不补证据。历史producer2/3按receipt选择旧renderer，重开及rerender保持逐字节一致。

新知识条目同一正文行原样展示最终certainty（CONFIRMED/INFERRED/UNRESOLVED），保留完整公式/文字和来源链接；不让推断或待确认条目看成无状态的确认结论。该展示仅读取既有字段，不重新判断确定性、不补证据、不修改条目text或历史2/3渲染。

三例预览不调用全仓归并，不关闭326条全仓覆盖，不安装伪造的正式全仓 publication。可复用现有确定性 renderer，在独立预览目录保存3份业务正文、来源和验收记录；若一个问题对应多个过程片段，则在该例中分开呈现。样本通过后仍停在样本，何时全仓、分组数量和正式 CLI 范围另行讨论。

内部`reconstructSelectedPreview(CatalogSample, List<String>)`已返回不可变选定候选结果：candidateId、原ordinal、disposition、reason及全部最终typed processes，并提供对应归一化sourceReferences。旧`reconstructSelected`只委托一次；`renderPreview(processes, sources)`输出全部片段而无全仓coverage结论。该接缝不是新公共Agent/API或正式publication入口；三例ignored driver的实际文件和manifest由验收任务产出。

## 9. 交互与停止位置

- 默认自主模式：没有行业答案，模型从实际资料提出调查方向；用户无需先选 ERP/CRM/WMS。
- 可选关注问题：用户可以问某项业务怎样办理；问题只是查找方向，不是期望结果或强制阶段。不给正确 Activity ID/文件清单。
- 执行前显示本次范围、复用输入、预计任务序列和输出位置。已经明确的同一授权不反复询问；出现真实歧义用一个简短问题澄清。
- 阶段更新报告选到什么、实际缺什么、完成哪几例，不以覆盖计数代替业务质量。
- 真实重要矛盾、需要新来源/重建 Activity 或扩大样本时说明具体影响和替代方案，等待新决定。普通未命中、可解释的不确定关系和空来源链接随结果保留。
- 三例结束交付原文与简短准确性检查，等待用户讨论全仓；不自动续跑旧27候选或326活动。

## 10. 直接测试与完成判据

生产实施只扩展实际受影响测试：任意 N 导航、混合/未知系统类型、无预置行业答案、保留/补充材料集合、完整正文去重、多用途、原始 Activity 不变；三阶段实际顺序、最终核对看见完整 WRITE、三阶段记录重开/精确复用、旧 pair 不误复用；最终文字/结构完整进入渲染、无新模型润色、半轮失败保留；JDT/Builder/Activity 调用均为0。

样本验收重点是人能否说明业务如何办理、重要状态/金额/条件是否准确、缺什么是否说清。数量、coverage、来源引用数或出现特定业务名称都不能代替验收。允许材料只能支持过程片段，不能要求凑成用户最初举出的链。

设计完成与实现完成分别报告。详细三例输入、已知核查点和当前验收状态见[三例推演](walkthrough.md)、[验收](acceptance.md)和[实施状态](implementation-status.md)。
