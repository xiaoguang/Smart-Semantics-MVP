# 三个业务的材料推演：从保存内容到可读过程

以下是**真实保存材料的核对 + 目标执行方式 + 人工示范正文**，不是新版 Luna 输出。本次没有生成任何新 Activity 或过程。固定来源见[入口](README.md)。相对路径和行号均指该冻结仓库，不能换成最新 checkout。

## 1. 先看程序会拿什么

三个已保存的 Activity 可作为索引起点：

| 名称 | 实际 Activity ID |
| --- | --- |
| 新增库存单据及明细 | `activity:c7f1d27630e7680d5f948fc0c256db863ad015312cc27299e417734e1ec190fa` |
| 更新已有单据及其明细 | `activity:119bcb8fb7153f61615cf71ce18434a0d8ae28affa57c4849733163fdbad7476` |
| 批量审核或反审核库存单据 | `activity:42fbaf76a57e2aaeb4faec474675d28779f853d246fe48f2024bb498d76f00f2` |

模型不预先得到“这三个就是正确答案”。全局选材能看到全部326张导航卡和旧目录，自行选择，还可以召回原来未进入候选的明细、完成数量、退货关联、统计和对账 Activity。程序读回的是原 `reviewed-result`/正式 Activity 内容，不重新解释源码。

同一个新增 Activity 可以在候选中出现三种用法，但只发一次完整内容：

```text
U1：登记原始需求
U2：形成后续订单
U3：办理关联入库
完整新增 Activity：一份
完整修改/审核/查询 Activity：每种一份
源码：模型选中的实际保存原文
```

U1/U2/U3 是说明用局部编号，不是实际模型结果，也不是 Java 写死的业务分类。新源码可以不属于旧 Activity 的 sourceRefs；它只须属于同一冻结仓库并确实进入本次包。

## 3. 请购 → 采购订单 → 采购入库

### 选材怎样发生

1. 全局模型从旧目录与全体卡片识别通用新增、修改/审核、关联数量查询值得共同阅读，提出候选和首批请求。这是待实测行为，不是程序直接注入这些名字。
2. 程序取回完整活动及选中的 `DepotHeadService`、`DepotItemService` 和相关页面原文。
3. 阅读检查模型看到页面传状态和后台关联更新，可能请求共享选择器、状态常量、`getFinishNumber` SQL或其引用片段；清单由实际首批材料决定，可以为空。
4. 程序补读一次，冻结同一包。DRAFT 和 REVIEW 都能读页面、后台和数量口径，不再在草稿写完之后首次发现这些条件。

### 原文能怎样改变结论

| 只有局部 Activity 容易写成 | 合读后应具体说明 |
| --- | --- |
| 可以关联申请 | 采购订单页面选择状态1/3的请购单，`linkApply`保存关联；与`linkNumber`不能同时填写 |
| 保存后更新原单 | 相关子类型在关联号非空时，按关联数量比较并回写原单进度 |
| 状态满足时允许办理 | 页面选择条件、后台编辑/审核条件分别说明，不把一方替换成另一方 |
| 入库完成订单也完成 | 原单数量进度与强审核库存统计口径不同，不能用一个“完成”混称 |

### 人工示范正文

**根据请购承接采购。** 使用者可以在创建采购订单时，从状态为1或3的请购单中选择原单，带入要采购的商品，并保留申请关联。这个页面选择路径不是全部采购的必经前置；所读新增实现没有要求每张采购订单必须填写申请号。关联申请号与关联订单号不能同时填写。

**分批形成后续单据。** 保存采购订单的关联明细后，系统按原申请数量与已关联数量比较，更新原申请进度。具体超量限制须同时核对该分支、提交内容和配置；本设计不把“可分批”推成“永不允许超量”。

**根据订单办理入库。** 采购入库页面可以选择状态1或3的采购订单。后续单据提供关联单号时，保存明细会参与原订单的数量进度计算和状态回写。没有关联的入库不自动属于这一订单链。

**核对数量进度。** 所读关联数量SQL不按审核状态过滤；所读库存查询在强审核模式下另有状态限制。因此“原订单关联数量已经覆盖”与“库存按审核口径计入”应分别解释，不能一律写为采购已全部完成、付款已结清。

### 数字推演（演示，不是客户数据）

假设同一单位、无其他关联记录且所需保存条件成立：请购10件，一次订单承接6件；订单先关联入库2件、再关联4件。关联数量达到该订单6件，可解释订单数量进度变化；请购还剩4件未被此次订单承接。示例不证明两次入库已审核、现场收货或付款完成。

还缺人员权限、强制审批制度、实际运行配置时直接列待确认。缺这些不妨碍说明已经有原文支持的可选申请—订单—入库联系。

## 4. 销售订单 → 销售出库 → 退货相关路径

### 同一算法如何取材

全局模型选择通用新增/编辑/审核、完成数量、退货关联和往来查询活动；首批读取相应原文。检查模型可补销售出库页面、共享选择器、最低价分支、退货保存分支/页面和数量SQL。程序不使用“销售”关键词写分组规则。

已经核实销售出库页面选择销售订单状态1/3、后台关联进度更新和最低价适用范围。**本轮未逐项核实退货页面完整写入及财务处理，因此以下只把核实的段落作为示范；退货的完整办理链须由后续实际补读确认。**

### 人工示范正文

**建立订单。** 系统保存销售订单和商品明细。在所读新增路径中，未传状态才默认未审核；不能省略这个条件。另一新增入口可能无条件设未审核，两个入口应区分。最低售价检查位于销售/零售子类型分支，不能当作所有销售订单的建单条件。

**修改、审核与回退。** 所读编辑入口只允许原单状态0。批量审核接纳当前状态0的单据；反审核对当前状态和采购进度有具体限制，采购进度2/3会拒绝。应按对应源码保留具体值和分支，不用“状态允许即可”代替。

**办理关联出库。** 销售出库页面可以从状态1或3的销售订单选取原单。保存有订单关联的出库明细后，系统按关联数量重新计算原订单的进度。因此可以解释订单支持关联出库及分批进度跟踪；不能据此声称全部出库必须有订单，或出库已完成收款。

**退货与后续查询。** 已存材料存在按关联单号和退货类型查记录的能力。这能说明查询关联，不足以单独证明完整退货创建、退款或订单重新开放。后续包若实际读到退货页面赋值、保存分支和计算范围，模型再扩为办理步骤；否则保留为支撑查询与具体缺口。

### 为什么这次信息接力更完整

原来退货/数量查询可能不在候选中，文件原文又只在REVIEW晚到。本方案允许先召回它们并读原文，再决定是主线、可选分支、支撑还是未知。不会因“读了退货查询”就必须产出一个确定退货阶段。

## 5. 仓库调拨 → 两仓账面核对

### 选材与实际依据

通用新增/库存活动之外，模型可读调拨查询 Activity、页面和库存SQL。完整原文能看到：普通调拨拒绝启用批次或序列号管理的商品；调入/调出仓库不能为空且必须不同；所读SQL按两种仓库字段计入调拨入/出量，强审核时还限制状态。

### 人工示范正文

**登记调拨。** 使用者登记商品、数量、调出仓库和调入仓库。系统要求两个仓库都有效且不同。当前普通调拨分支不接受启用批次或序列号管理的商品，不能把源码提示的替代操作写成自动生成另一套单据。

**保存并反映账面变化。** 系统保存单据明细并处理两仓库存记录；库存查询分别把数量计入调出仓库与调入仓库，强审核参数会限制计入状态。这描述软件的账面计算，不表示目标仓已经现场签收。

**查看与核对。** 如果所选完整查询 Activity 支持调拨明细与仓库筛选，可作为查看和核对能力，不强行排为每张单据的必经后续步骤。尚未读到在途、签收、差异赔付或财务关账实现时，明确不能确认这些闭环。

这例的成功不是一定连出更长流程，而是读者看清已经支持的动作、规则与真实停止位置。

## 6. 推演结论

所需核心材料多数已经保存：完整活动用于导航和业务细节；页面/SQL/后台原文补对象选择、关联和计算范围。新取材路径可以把它们在DRAFT之前聚到同一个包，现有过程字段和Publisher足以保留这些内容。

**仍不能由纸面保证自主发现率或完整性。** 必须独立测量有/无提示两轮，检查模型是否自己请求了关键材料、是否保留具体条件、是否区分推断与未确认。不重跑上游，不靠补引用数量或更强硬的Java规则弥补语义质量。
