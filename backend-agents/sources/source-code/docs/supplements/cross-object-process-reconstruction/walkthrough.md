# 三个业务的材料推演：从保存内容到可读过程

以下是**真实保存材料的核对 + 目标执行方式 + 人工示范正文**，不是新版 Luna 输出。本次设计更新没有生成新的Activity或过程；最新三阶段的实际验收另见[验收记录](acceptance.md)。固定来源见[入口](README.md)。相对路径和行号均指该冻结仓库，不能换成最新 checkout。

## 1. 先看程序会拿什么

模型不预先得到“这三个就是正确答案”。全局选材能看到全部326张导航卡和旧目录，自行选择，还可以召回原来未进入候选的明细、完成数量、退货关联、统计和对账 Activity。程序读回的是原 `reviewed-result`/正式 Activity 内容，不重新解释源码。

同一个新增 Activity 可以在候选中出现三种用法，但只发一次完整内容：

```text
U1：登记原始需求
U2：形成后续订单
U3：办理关联入库
完整新增 Activity：一份
完整修改/审核/查询 Activity：每种一份
源码：模型选中的实际保存原文
```

U1/U2/U3 是说明用局部编号，不是实际模型结果，也不是 Java 写死的业务分类。新源码可以不属于旧 Activity 的 sourceRefs；它只须属于同一冻结仓库并确实进入本次包。

## 3. 采购：从已有原文到业务说明

本例调查采购如何办理，不能把示意的“请购→订单→入库→付款”当成强制答案。除旧Activity外，后续采购小实验已经读到请购、采购订单、采购入库、付款页面和相关实现；旧A采购包没有这些Vue页面，二者不可混称。

### 各模块实际接力

1. **系统认识与候选。** 全仓导航中的单据、商品、库存和往来等描述帮助模型认识系统；项目README提供用途背景。模型可以提出“前一对象可能被后续单据承接”的假设，调查是否可以直接建单、怎样分批、如何回写。程序不注入正确文件或关系。
2. **取回与聚焦。** 完整新增/修改/审核Activity和模型请求的页面、后台、查询原文进入首批。阅读检查补齐状态常量、原单选择和数量/金额处理；不因整个Service里出现权限/日志而全部追下去。源码仍来自原冻结集合。
3. **事实DRAFT。** 根据页面说明和实现识别可关联的对象；明确订单关联请购、入库关联订单、分批进度、订金/付款用途及后台限制。它须保留直接办理路径，不能把“可以不关联”解释成“不存在业务主线”。
4. **WRITE。** 将上述完整事实变成按办理顺序的业务段落。原单选择、默认状态、付款用途等关键规则在对应阶段可读。
5. **最终RULE_REVIEW。** 对照实际正文和原文检查。若WRITE把状态1/3写成“未审核或部分办理”，应修正为“已审核或部分办理”；如果把订单订金和入库本次付款合成“应付金额”，应按页面用途分别纠正。这是验收侧检查点，不把正确答案预置进通用Prompt。
6. **渲染。** 使用最后核对结果，不再让另一个模型改写。独立来源页保留原位置；小样范围明确，不发布全仓coverage。

### 应能形成的业务说明（人工推演，不是新模型原文）

**提出采购需求。** 请购单登记需要采购的商品及数量。采购订单可以关联请购单带入商品，也允许直接录入；关联时从已审核或部分办理的请购单中选择。

**建立采购订单。** 订单记录供应商、商品、数量和价格等信息，可以登记订金。关联请购时，后续保存的数量参与请购办理进度；订单关联号和请购关联号不能同时填写。修改已有库存类单据时，原单须仍未审核。

**分批办理采购入库。** 入库可以从已审核或部分办理的采购订单带入明细，也可以直接办理。关联订单的入库数量用于更新原订单办理进度。是否允许超过原单数量要同时看超量配置和实际分支，不能只写“只能一次全收”。

**登记付款与后续结算。** 采购入库页面可以扣除订金并登记本次付款；剩余欠款可以通过付款单处理。订单页面的“支付订金”与入库页面的“本次付款”分别解释，不能统称成一个应付总额。实际支付渠道和银行执行不在这些单据操作中凭空补出。

上述是根据已读页面与实现组织的正常办理路径，并不要求每张单据必经所有步骤。具体审核、库存计入、编辑和回退规则仍随阶段解释。

### 数字与条件推演

演示值，不是客户数据：原单数量10、已办理7时，在实际分支执行关联数量检查且不允许超量的情况下，本次3可通过数量上限检查，本次4被拒。启用允许超量时不能仍写为必拒。

订单订金100、已抵扣30时，相关累计抵扣检查允许本次70，不允许70.01。它不是“所有付款都不能超过70”，规则对象和动作必须限定为本次订金抵扣。通过上限检查不代表其它保存条件也已通过。

## 4. 销售：共享Activity如何形成另一种用途

本例仍复用通用建单、修改、审核和关联数量Activity；不会把采购结果换个名。原文中的销售出库页面、商品价格分支、退货页面和相应查询才决定具体规则。

### 各模块接力与能够确认的内容

- 全局模型提出订单与后续出库可能有关，既可从原目录召回，也可跨旧组读取明细、数量、退回和往来活动。已有设计核对了销售出库页面选择状态1/3的销售订单。
- 阅读检查要回答“如何带入订单、分批数量如何回写、哪些对象才做最低售价校验、退货究竟是查询还是写入”。第三个旧A包只是混合退回材料，不能拿它冒充完整销售生命周期。
- DRAFT按具体用途解释同一新增Activity：销售订单与销售出库不是同一个业务动作。所读最低价判断适用于销售/零售子类型，不能自动加到销售订单建单上。
- WRITE围绕“建立订单—允许状态下修改/审核—关联出库—材料确实支持的后续处理”组织。某个阶段不成立可以移除，缺资料则写清已经解释到哪一步。
- 最后核对检查实际文字：未传状态才默认未审核不能丢掉前提；编辑要求原单未审核；反审核须核对当前状态和采购进度限制；查询到退货不能写成已经自动退款。

### 应能形成的部分正文（人工推演）

**建立和确认订单。** 系统保存销售订单及商品明细。所读新增路径在未传入状态时将单据设为未审核；未审核订单可以修改。审核与反审核按对应状态条件办理，已进入受限采购进度的单据不能直接反审核。

**根据订单办理出库。** 销售出库页面可以选择已审核或部分办理的销售订单，带入商品并保留原订单关联。关联出库的数量参与原订单办理进度，因此可以说明分批出库及订单进度跟踪；不能把它写成所有出库必须先有订单。

**退回及后续处理。** 现有材料能支持按原单号查询退货关系。是否可以从原单直接创建退货、退回怎样影响库存、金额或原订单，须以实际选入的页面和保存分支解释。材料不够就保留这段缺口，不能从查询接口补造退款步骤。

销售例的验收不是强制出现六个预定阶段，而是把已读规则用到正确对象，并解释实际可确认的联系。统计或详情查询可以作为支撑，不强排为最后一个办理步骤。

## 5. 调拨：可以较短，规则须具体

### 各模块接力

模型从两仓/库存相关导航提出调拨问题；首批读取完整相关Activity和方法。阅读检查重点选择仓库、商品限制、数量方向和强审核口径，不要求发现订单或付款。

DRAFT应说明登记对象、两仓条件、拒绝商品范围、库存计入与审核；WRITE把这些放到办理步骤；最终核对检查“保存、审核、库存查询”是否被错误混为一件事。缺在途或签收信息，不妨碍说明已经实现的调拨登记。

### 应能形成的正文（人工推演）

**登记商品和调拨仓库。** 使用者填写调拨商品、数量、调出仓库与调入仓库。两个仓库都必须填写且不能相同。所读普通调拨路径不接受启用批次或序列号管理的商品。

**保存和审核。** 系统保存调拨单及明细，处理两仓库存记录。强审核配置会影响库存校验和计入状态；已读某个保存分支跳过库存不足检查，不应被写成所有调拨都永不检查库存。

**查看两仓库存。** 库存查询分别计算调出和调入方向。已有审核状态过滤须明确解释；页面未实现或材料未包含的现场签收、在途和差异处理，不填成必经步骤。

这个过程可以比采购短；不能为了保持样例格式而添加不存在的财务结算或订单生命周期。

## 6. 设计走读结论与实际验收区别

三例共享同一个框架：全仓认识提供问题方向，完整Activity与冻结原文回答问题，事实推理形成具体关系和规则，写作让业务可读，最后对实际成稿核对。共用方法可参与不同用途；核心条件与对象范围不能因共享方法而混用。

材料已经保存，读取新行段是使用现有资料，并非重新运行JDT或Activity。原文不足时记录具体问题，范围由实际证据决定。不能因为纸面接力完整就宣布模型已经正确执行。

原设计的采购/销售/调拨，与已交付的采购联动/两仓调拨/订单退回是不同样本集合。实际执行选定哪一套须明确记录。最新3阶段结果尚未生成时，本文件只能称“材料推演”；不得把这些人工示范放进模型输入或作为新模型输出。
