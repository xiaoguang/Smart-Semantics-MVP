# 验收、实施差异与交接

状态：设计验收说明，未执行新模型实验。本轮只写文档；后续代码和产品调用必须另列实施计划。326 条 Activity 始终复用。

## 1. 不重复开发的能力

| 当前已有 | 后续只补什么 |
| --- | --- |
| Activity/M10 reader、完整字段、statement handle | 注入同源冻结文本 reader，开放定向读/字面量搜索 |
| 保存的目录 DRAFT/REVIEW/merge | 显式重开为资料输入，复用既有处置规范化 |
| 完整 Activity 组包 | 跨旧候选召回、context、DRAFT 前加入选中原文 |
| 两级 job pool、Provider、日志与 pair 保存 | 两类单次决策记录，不伪装成 DRAFT/REVIEW |
| Process 详细结构与完整审阅 | 新包、新 Prompt/响应，不重写生命周期类型 |
| 无损归并、失败合并保留、覆盖 | 增量成员处置接线，不造第四套账 |
| 五文件 publisher、reader、来源页 | 新来源统一编号后原样发布 |
| 唯一 source-analysis/Agent | 显式旧目录参数、可选关注问题及输入引用接线 |

不是重新运行目录六分片、326 Activity 或 JDT，也不是重开已完成的清理计划。

## 2. 开发直接测试

Luna/xhigh 写明确 RED，Terra/xhigh 最小 GREEN，Sol/xhigh 调试；设计偏差由 Sol/ultra 或 Astra/ultra 裁决。每个编辑 Agent 先建自己的临时 progress；不运行无关全仓测试。

1. 真实保存目录可重开，旧目录模型、JDT、Builder、ActivityExplainer 调用均为 0；旧产物字节不变。
2. 任意 N 的导航包含全部已审 Activity；候选能选择旧组外/原支撑 Activity，不硬编码 326 或业务词。
3. 未涉及的候选与 Activity 处置承接；新增/移出的成员按最终候选更新；读取 context 不强行加为成员。
4. 首批取回完整 Activity/源码，每候选恰一次阅读检查；空补读无需取额外源码，非空最多执行一轮，不递归第三次。
5. DRAFT 的实际请求已含所选 Java/XML/Vue 原文；REVIEW 含同一完整包和完整实际草稿。未知引用拒绝，合法新源码不因无旧 Activity owner 而被拒。
6. 真实上下文超限不静默截断。完整文件请求未完整返回、搜索未命中和仍缺片段都有说明；不因此重扫。
7. 完整 pair 与单次 decision 分别保存/读取/匹配。旧目录能作输入；旧过程不能误当新包的已审结果。
8. 不同候选局部 ref 同名不串源；实际相同片段去重，所有来源字段重映射后五文件重开/渲染一致。
9. 无法无损合并仍保留完整过程；非法 ID/引用失败。Activity/候选/过程三个分母闭合，coverage 和语义质量分开。
10. 静态冻结文本内含命令/提示语只作数据，不执行客户代码或外部读取。纯查看/重渲染零 Provider。
11. 旧批次下游失败但目录pair有效时可读；未知或损坏目录拒绝。QUEUED run在Provider前绑定所选检查点与问题，输入变化不能复用该绑定。
12. context可以提供实际statement/source引用，但过程不得静默把它变成成员；ActivityUse和stage/rule引用统一遵循已封包成员及实际阅读allowlist。

测试不要求补每一个来源链接，也不新建证明或中文含义校验。运行构建前声明范围，真实产品调用不进入自动测试。

## 3. 两个独立的真实实验

### 有关注问题

从原始旧目录和固定 326 Activity 开始，输入[推演](walkthrough.md)的三个业务问题。不给正确 Activity ID、源码路径或预期阶段。模型自己选材料、补读并解释。先检查少量候选输入/输出有用，再扩大；不因输入一个问题就认定该完整业务必然存在。

### 无行业提示

新独立批次，使用**同一份原始旧目录、同一 326 Activity 和同一冻结源码**。不继承上一轮候选、选材清单、定向片段、阅读包或模型答案；也不以有提示轮为 reuse 来源。原始旧目录本来已有的业务名允许存在，这是输入事实，不是提示泄漏。

两轮可以共用原始文件字节/确定性读取能力，但无提示模型只能看到自己请求的原文。两轮结果、调用量、业务质量分别报告；有提示成功不证明自主发现成功。

真实模型拟用既有 Pro、Luna/high、并发4。**本次文档授权不启动这些调用。** 如需重跑 Activity，先讨论原因、受影响范围和替代方案，不把它藏在实验里。

## 4. 验收看什么

| 读者问题 | 检查材料与产物 |
| --- | --- |
| 有哪些业务，范围是什么？ | 目录不只按 CRUD 分类；未改/未识别范围如实保留 |
| 前后对象如何关联？ | 过程指出对象、标识/字段、选择条件、可选/分批及回写 |
| 什么状态允许、什么状态拒绝？ | 已有具体谓词保留，页面条件与后台校验不混淆 |
| 每一步实际做什么？ | 业务段落能复述动作和结果，不靠 Controller 名或参数模板 |
| 规则适用于谁？ | 通用 Activity 的不同 variant 不复制全部分支规则 |
| 补读有何帮助？ | 能指出某段原文补齐或纠正了哪项判断，而不是只统计引用数 |
| 还缺什么？ | 明确哪段联系未知、缺哪个条件/实现；不凑完整生命周期 |

销售不出现某个名字本身不是失败；认出很多标题也不是成功。不要要求系统识别客户全部制度。现有材料支持的对象交接应尽力讲清，无材料的制度和真实执行结果不猜成事实。

## 5. 调用数与时间

旧目录已保存、全局输入能一次容纳，且无复用时：

```text
1 次全局选材
+ N 次候选阅读检查（即使补读清单为空也算）
+ 2 × N 个实际重建候选（DRAFT + REVIEW）
+ 2 次唯一仓库归并
= 3 + 3N
```

例：实际有 2 个候选并执行仓库归并时是 9 次；只做 2 个样本、不归并/发布全仓时是 7 次。例子不是预定候选数。容量或合法不足使部分候选没有进入过程 pair 时，分别报告 planned/started/saved/skipped；不能照公式声称都已生成。

新仓库首次目录的调用另外计算；本次原目录读取为 0。完整 Activity/原文读取、保存、渲染为 0。显式匹配的 decision/pair 可以减少实际请求，但有/无提示实验不互相复用。

编码、磁盘读取、队列、模型各类调用和人工审阅分别测量。当前未实施、未测量，不给虚假的精确结束时间；后续计划依据模块差异估算，先从样本取得选材、检查、DRAFT、REVIEW 耗时再估算全量。

## 6. 失败与范围

- 合法原文不足/搜索未命中：保存具体 reading gap，过程可为片段或 UNRESOLVED；不假装完整。
- 固定源损坏、越界请求、未知 ID/ref、坏 JSON/Provider 失败：保留已完成结果并停止新派发，无自动重试、换服务、API 回退或下游伪成功。
- 阶段仍是技术模板或原文足够却规则空泛：停止扩大模型调用，检查此次输入/Prompt/响应；不回头重建 JDT。
- 第二次阅读选择已用完：保留未解决问题，不能由次数推导 COMPLETE。
- 容量不足：记录未处理范围，不新增费用预算门槛，也不静默减材料。
- 过程合法 UNRESOLVED 沿用原语义状态合同，不因单个未知联系使所有结果 fatal；coverage CLOSED 也不意味着已识别全部业务。

产品内容改进轮次沿用现有具名问题/显式授权纪律。阅读选择不是第三轮修稿，显式新批次也不是无限替换已定候选的许可。

## 7. 设计闭环结论与未验证项

路径可在当前基础上接通：已审 Activity 提供全仓导航和详细活动，冻结文本补页面/SQL/共享代码；新选材解除旧分组限制，完整原文提前使模型可以在 DRAFT 阶段建立跨对象联系。原阶段/规则结构与五文件出口足以承载结果，无需新证据体系。

尚未证明：模型在无提示条件下会召回多少长链、首批搜索能否选到关键片段、一次补读后仍有多少缺口、整个阅读包的实际容量和语义质量。三个[纸面推演](walkthrough.md)只说明材料与接力成立，不冒充这些实验已经通过。

不纳入：重建 Activity、JDT 扩展、全仓 SQL/Vue 语义扫描、业务硬规则、九章生成、通用代理式无限浏览与恢复系统。`more-findings.md` 原文及其未纳入议题保留。
