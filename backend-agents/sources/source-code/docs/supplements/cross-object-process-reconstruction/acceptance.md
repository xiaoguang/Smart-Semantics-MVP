# 三个例子的最小验收

状态：最新目标已写为[详细设计](business-reasoning-and-writing.md)。旧阅读链程序验证及历史模型运行见[交付记录](delivery.md)。本轮只验三个例子，之后由用户决定是否讨论全仓；不会因样本通过自动启动剩余候选。

## 1. 验收目标

用户已经认可最新采购正文的阅读水平。三例检查的是能否用实际材料解释业务办理、保留关键条件，并让最终规则核对检查实际成稿。不得因未出现用户举例的完整链就凑造步骤，也不只看标题、阶段数或coverage。

三项结论分别报告：

- 可读性：用户能复述业务起点、步骤、分支和结果。
- 准确性：重要对象联系、状态、金额、数量、配置条件有无错误；最后模型核对发现和修正了什么。
- 选材范围：使用了模型自主选择、用户关注问题引导，还是已有人工/历史材料包。后两者成功不能当作自主发现率。

本轮不再做工具选型、JDT能力、Activity重建或整条路线的额外可行性验证。

## 3. 最小执行方式

若实际范围采用原设计的采购/销售/调拨，则全局选材看到这三项**问题范围**、全部导航和冻结目录，自行找对象与资料；不提供正确Activity ID、文件答案、预期状态或阶段顺序。每例一次阅读检查完成包，然后每例DRAFT→WRITE→RULE_REVIEW。最多3个候选job并行，仍遵循已配置的全局/Provider上限。选材返回不同片段或一例拆为多个过程，均保存在该例中，不为满足用户例子伪造一条长链。

若用户选择直接复用旧A三包，只执行三阶段，明确没有重新验证自动选材。历史采购包不够解释请购起点时，按包报告范围；如希望补全，先选用真实已保存原文，不能靠调整文章掩盖材料缺项。

样本复用既有内部有限候选接缝或薄研究驱动，保存输入、实际三阶段结果及小样Markdown。不新建公共命令或运行框架，不伪造全仓处置，不执行仓库归并，不自动恢复旧B27候选。正式代码尚未实现时，薄驱动生成的是设计验收样本，应标明不是生产全链接线完成。

## 4. 每例如何验收

| 例子 | 可以检验的具体问题 | 不预定的答案 |
| --- | --- | --- |
| 采购 | 原始需求是否、怎样被订单承接；订单如何关联后续单据；分批数量如何推进；订金/当次付款/剩余欠款用途；状态筛选和后台限制 | 不要求所有采购必须先申请；不把付款记录当实际支付执行完成；按原文决定是否可描述完整链 |
| 销售 | 建单、修改和审核的实际条件；订单与后续出库如何关联；最低价规则的具体对象；退回与原单的实际关联/动作 | 不把销售/零售最低价校验复制到销售订单；不凭退货查询推断退款或重开订单 |
| 调拨 | 两仓怎样选择；商品、数量怎样登记；仓库相同/为空怎样处理；批次/序列号限制；库存与强审核规则 | 不强行增加在途、签收、分批收货、差异赔付或财务关账 |
| 订单退回（仅选择旧A三包时，替代销售例，不增加第四例） | 原单关联是否可选；退回数量是否纳入原单汇总；不同退回类型的方向和适用分支；财务是否需要独立操作 | 不把关联查询写成已经退款或调整库存；不按销售订单完整生命周期验收；原文不足时保留具体未知 |

已核对原文和人工推演见walkthrough。验收检查清单不作为模型答案输入。状态名与代码值应在材料中能相互对应；页面选择、输入事件、后台条件和查询口径不能相互替代。

最后RULE_REVIEW需对照实际WRITE，检查至少：肯定/否定、状态、默认值、适用对象、金额名称和公式、数量边界、配置例外、可选/分批/回退。缺材料可以留下具体未知；重大误述不能因为读起来流畅而从验收报告隐去。

已知采购错误只作验收方回归检查：1/3应对应已审核/部分办理；同一changeAmount在订单和入库对应不同金额用途。不要把这两个正确答案直接塞进通用Prompt，借此伪装模型自主核对通过。

## 5. 输出与查看方式

每例独立保存：

```text
input-manifest.json
reading-packet.json
draft.json / 原始响应
writing.json / 原始响应
reviewed-result.json / 最后原始响应
business-processes.md
sources.md / source-refs.jsonl
acceptance.md
```

这是本地样本目录，不是新增正式artifact清单。已有原文、范围、局部引用和日志保留；产物可比较且不覆盖旧文件。每个例子的验收记录写清实际处理范围、未确认关系、模型纠正项及人工发现问题，不把326条覆盖计数搬过来冒充全仓完成。

若薄研究驱动输出Markdown而非正式JSON，必须如实标注研究产物和对应原始响应；正式接入后仍按现有结构化字段确定性渲染。

## 6. 调用数、时间与边界

| 方式 | 请求数（没有失败/复用时） | 说明 |
| --- | ---: | --- |
| 复用3个已有包，只验新三阶段 | 9 | 不验证新自动选材 |
| 一次全局选材＋3次阅读检查＋3例三阶段 | 13 | 系统认识合并在全局请求，不再加分类调用 |
| 零模型材料推演 | 0 | 只检查设计接力，不能标为真实新模型验收 |

如果某例在阅读阶段发现合法不足，记录实际启动/保存的次数，不把13当必须用尽额度。全部样本结束后不追加全仓归并的两次请求。与用户确定本轮模式后，记录精确输入及输出目录再调用；沿用Luna/high、现有ChatGPT登录和无API回退。

前次三请求单例耗时约13分31秒，只能作为量级参考；新顺序和三例材料不同，不承诺同样耗时。准备、读取、模型等待、保存、人工核验分别记录。没有费用预算门槛，真实上下文容量仍需检查；不能静默截断关键内容。

每例初次执行形成一个新候选。没有自动重试、补救调用或第四次改写。失败保留结果；需要替换候选时按具体问题另行决定，不连带重跑其它例子。用户已有同范围授权不重复询问。

## 7. 离线测试与实现验收

沿用旧取材链有效测试，不为每个内部字段建立新证明系统。新增或直接受影响测试应证明：

1. 任意N导航、混合/未知类型、无行业硬编码；旧目录仍可作输入。
2. 首批保留/移出/补读集合实际生效；首批原文保存不被删除；最终完整成员/context和关键材料不丢。
3. 最后核对看到相同原文、完整实际DRAFT及WRITE；写作后不能直接标已审。
4. 三阶段完整保存、重开、指纹和显式复用；旧pair/半轮不误用，Activity/目录pair继续正常。
5. 业务正文和结构条件一致传入Publisher；最终来源映射不串包；无需Provider的重渲染保持零调用。
6. 出错停止新派发并保存已完成合法结果；JDT、Builder和ActivityExplainer调用数均为0。

样本外准确性、跨仓自主发现率和全仓扩展不在本次完成标准内。通过后提交三例原文与结果，交由用户讨论如何全部构建。
