## 5. 已核实的三个具体断点

### 5.1 搜索规则没有进入模型工具说明

驱动实际调用R4的`searchLiteral(query)`，R0则用`body.indexOf(query)`：整个query必须作为连续字符串出现，不是分词或语义搜索。但真实Prompt只称其为SEARCH，Schema的`query`也没有说明精确子串语义。

财务第1轮请求的实际query包括`accountHead addAccountHeadAndDetail detail business bill link`；后面换成类似`财务明细 写入 保存 业务单据 关联 单据ID`的整串。6轮均没有命中，模型没有改用入口单元导航。这个事实说明工具用法与实际查询不匹配，不能说明相关实现不存在，也没有证明只补一句Prompt就一定能成功。

### 5.2 后续请求丢失可重新选择的导航

两题第1轮均提供339张卡；之后`roundInput`直接设置`entryCards=[]`，只提供保留正文和上一轮查询页。Provider每次执行`codex exec --ephemeral`，没有传入上一轮对话，因此不能依靠模型记住第一轮目录。财务零命中后缺少可回到目录的实际导航；采购进入超限页后也没有其他候选可选。目录保存在程序里，不等于还在模型当前输入中。

### 5.3 单元本身超限，却只要求模型移出材料后重读

采购第2轮的N5候选是`DepotHeadService#addDepotHeadAndDetail(String,String,HttpServletRequest)`，实际导航已给出`projectedBytes=128174`，超过70000字节上限。**事后零模型核对R4**得到其原始方法正文6572字节、所属调用115条；这两个数字是审计得到的，不是模型已经读到的正文。驱动仍默认附入全部115条调用的多项技术观察及目标导航，因此“紧凑表”这个名称不代表实际投影已经足够小。

N5共请求读取7次，均未进入模型正文。程序返回的`READ_CAPACITY_RETRY`仅携带N5的ref/kind和“移出无关已读材料后重试”，不区分“当前保留包太满”和“单个候选本身就超限”，也没有再次给出实际大小、容量或不可重试说明。模型移出Controller之后仍重读N5，程序继续给同一页。这个容量处理缺陷已由实际请求复现；仅修编号、升模型或扩大窗口不能算解决。
