## 成熟工具的薄边界与真实限制

本仓 [POM](../../pom.xml:22)已经固定 `com.github.jsqlparser:jsqlparser:5.3`，持久化分析已使用 `CCJSqlParserUtil` 及 AST，[现有实现](../../src/main/java/org/sourceanalysis/app/analysis/persistence/DefaultPersistenceAnalyzer.java:594)。其 **5.3 标签源码**中，`CreateTable` 有表、`getColumnDefinitions()`、`getIndexes()`；`ColumnDefinition` 有列名、`ColDataType`、列规格 token。可直接薄投影**parser 实际识别**的表/列/类型及显式键、索引，并只从已解析的列规格读取 `NOT NULL`/`NULL`；规格缺失或方言不明应记 `UNKNOWN`，不能推出数据库默认。[CreateTable 5.3](https://raw.githubusercontent.com/JSQLParser/JSqlParser/jsqlparser-5.3/src/main/java/net/sf/jsqlparser/statement/create/table/CreateTable.java)、[ColumnDefinition 5.3](https://raw.githubusercontent.com/JSQLParser/JSqlParser/jsqlparser-5.3/src/main/java/net/sf/jsqlparser/statement/create/table/ColumnDefinition.java)、[官方解析用法](https://jsqlparser.github.io/JSqlParser/usage.html)。`getIndexes()` 不包含列内声明的键，故也要核对列规格；普通 `INDEX` 不提升为 `FOREIGN KEY`。

但现有[只读 DDL 走查](../modules/ontology-recognition/evidence-walkthrough.md#2-ddl能提供什么已经验证到哪里)报告：5.3 对**整份导出**的 `parseStatements` 在第 236 行 `UNIQUE INDEX` 附近失败；明确选定 133–215 行则解析了 2 张表（头 35 列/7 索引，明细 25 列/7 索引）。因此目前不能承诺自动枚举完整 MySQL dump、恢复失败后的所有表、或获得每列精确 R0 行号。新版官方文档描述的错误恢复会跳过坏 statement，其覆盖仍须按锁定 5.3 和该 dump 单独验证；不能把“解析继续”当“全量正确”。[官方错误恢复说明](https://jsqlparser.github.io/JSqlParser/usage.html#handle-parse-errors)。不写分号切分器、SQL parser 或 DDL 定位器，不连接实时数据库；数据 `INSERT` 也不是生产实例事实。

建议 O0 记录选定 R0 文件及 SHA、实际读取/解析状态、parser 版本、已识别表列/显式约束、未识别范围与原诊断；若整份失败，`schema-evidence.json` 仍可保存“原文可读、结构覆盖不完整”，**不能发布虚假的全表目录**。只有已有可核验范围的定向原文才给出行定位，parser AST 本身不足以证明列行号。后续若要自动全 dump 导航，先对锁定工具做有界实测并明确覆盖；无法取得完整覆盖时继续保持定向同源补读。

## 引用放在哪一层

R4 是冻结技术来源，长 `entryId`/`methodKey`/`statementRef`/`sourceRefs.reference` 继续作持久身份。现有 [`OntologyEvidenceCorpus`](../../src/main/java/org/sourceanalysis/app/analysis/ontology/OntologyEvidenceCorpus.java:31) 已持有这些身份和反查，[`OntologyNavigationView`](../../src/main/java/org/sourceanalysis/app/analysis/ontology/OntologyNavigationView.java:77) 已给调查/查询视图 `E/J/L/U` 短键和私有映射，[`OntologyReadingPacket`](../../src/main/java/org/sourceanalysis/app/analysis/ontology/OntologyReadingPacket.java:140) 则给选定完整单元另建包内短键；不是从零创建别名机制。建议把**可见短键及反查**稳定地作为 Corpus/证据阅读接口输出，在调查的第一页就出现；DDL 若可用也进入同一阅读接口的 scoped 映射。每个 `{viewId, ref}` 或 `{packetId, ref}` 只在自己的范围有效，私有映射必须保存准确 R4/R0、原身份、选材内容和范围；跨包 `S1` 不可直接比较。最终 `evidenceRefs` 只能解析已读原文引用，线索键不能冒充证据；现有[引用合同](../modules/ontology-recognition/contracts.md#91-私有选材合同与最终原文引用分开)已有此门槛。不要改写 R4 文件或新造全局短 ID。

为免形成黑箱，O0/O1/O2 的检查面应分别露出：实际选定文件/单元及未选范围、给模型看的投影/容量、Prompt 与 Schema、原始模型答复和 REVIEW 修正、短键到完整证据的私有映射。已有[第 26–28 项待办](implementation-lessons-and-followups.md#26-本体阅读包的实际成本与紧凑投影)要求必要原文完整、无关技术明细可逆移出、前端正式采集缺口与小上下文业务核验分层；DDL 不能替代缺失的页面选择/保存链，也不能据静态列定义批准业务关系。

正式设计已采用：仅明确配置schemaSources时保存可选`schema-evidence.json`，否则Corpus记DISABLED；允许用户明确选择且逐字核验同R0的完整定义范围，标EXPLICIT。整份dump失败不伪造完整覆盖或精确未解析语句范围。这是目标合同，尚未实现，不再列为未决取舍。

上段`{viewId,ref}`描述既有实验的严格读取规则，不是新生产目标。正式方案由请求绑定Corpus/轮次作用域，证据接口提前给稳定E/U/K键，实际正文包仍有S键；K线索不与业务Link的L混用。完整内部身份、确切变体、用途和映射保留；不改写旧R4或自动转换旧模型记录。准确合同以[材料短号](../modules/ontology-recognition/material-preparation.md#7-短-id-提前提供不替换稳定身份)及[定义作用域](../modules/ontology-recognition/contracts.md#72-id作用域跨题对应和纠正)为准。
