# 先连接业务再完善本体的详细设计

状态：2026-10-05，**正式工程及局部骨架/细化交付完成，业务覆盖、小窗口和浏览器呈现验收仍部分未通过/未验**。新合同、控制/页面反查、材料v5、准确跨运行对象和四文件/离线图已有129项直接回归及同代码质量依据。最终实际产出及20份请求成本由[正式验收](../../supplements/ontology-business-link-formal-acceptance-20261005.md)维护，接续状态由[执行记录](../../../progress/business-link-first-execution.md)维护。既有四命令及底座复用；实验与失败记录不改写成正式成功。

## 1. 要交付的结果

先回答“系统有哪些业务对象，它们怎样联系”，生成有来源的对象关系总览，再逐项完善对象身份、属性、操作、维度、度量、指标和详细规则。不能先花全部时间解释局部计算，却没有把已存在的业务联系连起来。

这里的“先连业务”不等于省略对象识别。关系必须有两个合法对象端点；第一阶段只识别足以表达联系的**最小对象定义**，不要求先查清全部属性、数据库唯一性、基数或整个状态机。这些未知不影响已经有依据的标识联系，但不得被默认为已知。

最终主要结果是业务图，而不是 Controller 调用图。方框显示实际识别的业务对象，箭头写清保存来源编号、包含、查询对应记录或改变某属性等机制。箭头不默认代表执行先后。操作挂在目标对象上；维度、度量和指标是独立分析层；数量、审核、金额等细节放在相应联系或操作的展开内容。

所有结果仍为 `DRAFT_REVIEWABLE`，指标仍为 `NOT_EXECUTABLE`。模型审阅通过表示该模型对所读静态实现的判断，不等于数学证明、现实业务已经发生或用户已经认可。

## 3. 范围及不做的事

输入仍为准确R4入口证据及其同源R0，按既有规则可使用R4已绑定的保存R2声明读取辅助原文。DDL保持O0可选输入，不新增必经R5、不追加数据库连接或SQL执行。

本设计不重新运行技术取证中的JDT/Maven、Vue parser或SQL分析，不修改旧Activity、业务过程、九章、Prompt、Schema及MD渲染。O0明确配置可选DDL时仍可按既有有限路径调用JSqlParser；这不重做R3。未配置DDL则零解析。不读取旧MD/Activity/过程稿或用户参考图作为事实或候选答案。支持范围仍是当前Java/Spring MVC/MyBatis和有限Vue静态模式。

不新增业务词典、行业流程模板、全仓两两相似度平台、向量/图数据库、通用Java/JavaScript/SQL解释器、自动修复/审批/恢复服务器。材料规则里不能写入请购、采购订单、linkApply、jsh_depot_head等客户专用词。

用户可以替换业务Prompt和宿主沟通模板，配置已有来源、模型、范围和容量。Prompt不能绕过来源、短号、Schema、容量或保存规则。宿主Agent不人工拼材料、不导入修好的模型稿；若用户明确要改变材料算法，则按代码扩展处理。

## 5. 总流程和四个命令

四个命令不增加、不改名，公共RepositoryAnalysisAgent也不增加方法：

```text
prepare-ontology：O0，准备资料、技术导航和可选DDL，零模型
identify-ontology：O1，按当前小题识别对象，或细化操作/分析定义
relate-ontology：O2，按准确已审对象核对联系与身份
publish-ontology：O3，发布明确所选已审结果，零模型
```

**执行次序分两段，而不是要求每题先填完所有类型：**

1. 骨架段：O0 → O1最小对象 → O2具体联系 → O3对象关系总览。
2. 细化段：按已有图和技术邻居选择下一处实现 → 新O1操作/分析或对象细化 → 必要的新O2身份/关系审阅 → 新O3扩展总览。

每次调用有新运行ID。多个O1/O2可属于同一Corpus，O3明确选择它们的准确集合。早期O3已发布的图保持不变；细化产生新图，不能覆盖旧发布或让旧结果自动变成新版。

O3发布骨架时，指标和操作可以为空；coverage-v3的 `recognitionLayers` 分别声明OBJECT、RELATION、ACTION、ANALYTIC的请求/处理范围，每项为layer/status/taskRefs，taskRefs保留原owner的runId/questionId/taskId。未声明层标 `NOT_REQUESTED`且无任务，不制造失败任务，也不当作已经完整识别。已声明层按全部任务处置标 `COMPLETE_FOR_DECLARED_SCOPE / INCOMPLETE`。骨架闭合不能标作完整本体覆盖。缺一个详细金额规则，不阻止展示已经有来源的订单引用关系；缺关系端点或有确定性组装冲突，则不能画该边为实线。

## 6. O0如何找出值得一起看的实现

### 6.1 输入和实际复用位置

输入为真实R4 receipt/index、准备版来源、有效排除范围、同源保存引用。复用 `OntologyEvidenceCorpus` 的 `aliases()`、`entryClues()`、`clueUses()`、`searchLiteral()` 和完整单元读取；读取已有 `controls`、调用观察、Mapper绑定、XML结构、SQL AST及页面上下文。**读取保存语法记录不是重新解析源码。**

当前Corpus仍在内存中物化集合。本设计不把它描述成低内存随机读取平台，也不顺带重建资料库。

### 6.2 候选共同项的规则

| 候选信号 | Java匹配规则 | 必须显示的限定 | 不能推出什么 |
| --- | --- | --- | --- |
| 共同方法 | 准确methodKey及来源范围，不按同名匹配 | 实参、入口用途、分支和目标定位状态 | 调用了公共方法就属于同一流程 |
| 同一Mapper语句 | namespace/id/databaseId和内容变体完全限定 | Java参数、XML条件、解析状态 | 查询相同表就是同一对象 |
| 共同表/列 | 已保存SQL AST或有效DDL中的实际限定名；未限定列保留候选 | SELECT/过滤/更新等已保存用途，SQL变体及未知 | 同名status代表相同业务状态 |
| 标识使用分支 | 保存controls中实际条件及getter/setter/字段观察 | 完整方法句柄、实际表达式和入口用途 | getter名称必然代表业务关联字段 |
| 页面/组件用途 | 同一实际来源单元和页面实例、事件、请求观察 | 候选/确定HTTP性质、参数及未传参数 | 共属页面就存在运行时因果 |
| 状态写读线索 | 只有原工具已保存可靠字段/表及用途时展示写/读对应 | 对象定位条件、常量、WHERE/Java条件及限制 | 构成完备字段数据流或状态机 |

只知道同名字段时可以字面搜索，不能冒称表列写读已经绑定。当前实验没有展示可用COLUMN组；新设计不能假称完整列级导航已实现。

按准确共同项建立倒排表，取一个K时返回它的真实U/E用法。记录扇出，不因高扇出删除公共方法；只是不把大量共享工具连接当业务结论。展示排序采用信号类别、实际扇出、准确键的稳定顺序，属于导航策略，不是置信概率。无需计算整仓所有entry对的分数。

### 6.3 分支查漏

对保存控制观察列出含实际标识访问的分支，让模型看到尚未处置的入口/分支。可机械生成同一已保存表达式的字面检索词；例如从getX生成x只是搜索建议，搜索结果仍须选择完整原文核验，不能因此把x认定为数据库字段。

分支使用既有K类别扩展，不沿用实验的B号：正式B已用于已审对象目录。E是入口、U是确切单元、K是调查线索、S是本次原文。新增 `CONTROL_REFERENCE` 线索类别须和Reader/Schema一起接线；不能由Prompt发明键类别。

每个线索页保存显示项、总项数、后续页和未展示范围。分页是传输约束，不是业务顺序；相邻entryId不组成业务。一个入口可以参加多个候选联系。

### 6.4 输出与消费者

O0保存原有Corpus及可逆别名，增加版本化的线索投影规则。调查模型消费小页，选出问题和E/K范围；阅读协调器消费U/E选单。O0不生成中文业务摘要、不批准任何对象或关系。

## 7. 从一条线索到一份联系材料

### 7.1 选择一个小问题

调查Prompt只问：“哪些实现之间存在值得核查的编号、字段、状态、数量或金额交接？一次提出一个具体联系，指出当前可见线索和需要核验的另一端。”不把行业常识写成应当存在的关系。

选择任务可返回实际E/K、问题、字面检索词和未知；由Java恢复准确范围。普通用户可以给业务领域或问题，但不能要求提供Controller、正确字段或预期流程。显式范围仍可用于调试，必须保留EXPLICIT标签，不能冒充自主发现。

### 7.2 Java取得两端候选

先从所选K取得实际用法、完整种子方法；沿已保存方法、Mapper、表列、页面单元倒排取得直接邻居；执行选出的字面搜索。候选目录显示每个U/E的完整读取成本及具体共同项，模型从中选择实际完整单元。

同一字面词命中多个不相关页面时，不能全部附入，也不能让Java根据业务名称暗选正确页面。目录保留冲突/变体；模型选单，Java验证身份后读回。

联系材料按已有事实区分以下角色，角色由选择或模型判断，Java不靠关键词自动裁决：

- 建立端：怎样产生或选择要交接的值。
- 保存/传递端：值通过什么参数、字段或映射保存/传递。
- 使用端：怎样用该值定位另一对象、查询或改变记录。
- 限制：目标不明确、动态条件、未读helper、地址未知等。

不是每个关系都必须填四种角色。例如完整实现直接表明明细保存headerId并按它查主单，就可以确认这一范围的归属；是否有数据库外键是独立未知。不能把“少一层细节”升级为整个联系不存在。

### 7.3 一次只核对一处交接

骨架问题不同时要求完整来源承接、分批数量、所有状态、库存重算、付款公式和权限证明。先识别有依据的引用/归属联系；若要确认数量或库存效果，再开具名小题。

先完整核对“编号从哪来、保存到哪、用来找谁”，与核对“多次承接怎样更新数量和状态”是不同任务。未读后者不应抹掉前者；前者成立也不能让Java补出后者。

### 7.4 有界扩展及漏项处置

O2审阅后可以提出待核查邻居。Java从实际使用的技术键取得一跳候选，再提出下一小题；每一轮仍需模型选题/原文，不无限递归自动塞材料。轮次沿用既有阅读上限，所有请求沿用同一运行派发上限及状态观察，不新建通用DAG或任务队列。

已选K必须有“已审支持联系、不是业务联系、需要补读、模型未处理、容量未执行”等明确处置。Java只能对照键集合记录遗漏，不能替模型解释分支。如果必要单元未入模，保存准确缺口；轮次结束不清空它。只处置选中线索，不宣称审完全部源码分支。

为避免Java反推模型含义，typed-v4的RELATE响应增加 `clueDispositions`：每项为 `clueRef / outcome / linkRefs / reason`。clueRef只能是本任务实际展示的K；outcome只允许 `LINK_SUPPORTED / NOT_A_BUSINESS_LINK / NEEDS_MORE_MATERIAL`。LINK_SUPPORTED引用本次实际返回的合法Link；其它两类linkRefs为空，reason必填。未返回的选中K由程序记 `MODEL_NOT_ADDRESSED`，未派发者按真实容量/失败处置，不伪造模型决定。其它任务的该数组为空。REVIEW核对并返回同一闭合字段；不是把K变为原文依据，Link的evidenceRefs仍只能用实际S。

已经成立且只想查细节的联系不自动重跑；新材料产生新任务版本。没有新单元、新线索或范围变化则记录无进展并结束，不重复READ或继续请求同一答案。

## 8. 简洁而完整的材料合同

### 8.1 稳定证据和模型投影分开

R4/R0及保存技术记录不修改。完整选中Java方法、Vue函数/模板单元、Mapper语句/XML依赖、SQL文本及解析限制保留，不能切几行代替完整实现，也不能用模型摘要假称原文。

模型不接收receipt、运行ID、哈希、绝对路径、重复声明、完整所有entry JSON或全部正常调用私有记录。私有映射仍保留原身份、来源及原始记录；移出输入不等于删除证据。

### 8.2 先选择，再压缩

调用选择沿既有formal v4规则：连接已选单元的可靠调用、被明确选中的调用，以及已选方法中候选/冲突/未知/查询失败的逐位置限制保留。正常未选调用细节留在程序侧，可以通过准确U读回。不能用logging类名或“看起来不重要”规则删除限制。

正文中已经存在条件、退出表达式时，重复便利字段可机械移出；保存控制位置和索引。不同页面实例、实参/形参或未传参数的用途不合并。SQL/XML两个树若确有不同语义，不因相似而只留一个；默认不同时选整份XML资源和其中已选statement，明确选取的完整资源不能悄悄删掉。

### 8.3 跨入口调用精确去重

这是本次新增的核心瘦身。正式材料v5已实现，直接测试验证精确解码与用途恢复；客户新批次的完整请求成本仍须实际测量。

1. 每个入选调用生成物理身份：同源文件/摘要、调用者声明、UTF-16 offset/length。再比较状态、实际参数、候选及其角色、参数对应、观察、展开结果等完整非用途字段。
2. 只有物理身份及这些字段完全相等，才共用一个调用正文。不同重载、嵌套位置、候选或入口展开观察不得合并。
3. `callRows` 保存共同调用；`callUses` 保存各E、调用者S、同入口目标S、原用途及原顺序。不可因E不同而丢记录，也不可把一个入口的目标投影到另一个入口。
4. 如果原行内selectedTargets引用的S不同，先按保存的稳定目标身份检查；作用域S映射仍分别放在对应use。任一候选或观察不一致则保留独立row，不用合并求并集掩盖矛盾。
5. target/observation字典沿用CT/CO；位置、实参、精确重复原因和XML/SQL节点用带固定列说明的编码。字典和技术C号不是可引用的S，也不是业务对象。
6. 解码必须恢复压缩前**当前已选投影**的完整有序行和用途，逐字段相等。该测试不要求未选私有技术字段全部入模，但它们始终可反查。

以下仅为调用编码字段的目标格式示意，未列阅读包的完整正文；不是当前正式产物或客户调用记录。`site`顺序固定为startOffsetUtf16、lengthUtf16、startLine、endLine：

```json
{
  "callEncoding": "EXACT_ROWS_WITH_USES_V1",
  "callRows": {"C1": {"site": [1300, 9, 42, 42], "state": "UNRESOLVED", "args": ["billId"], "targetRefs": [], "observationRefs": []}},
  "callUses": [{"rowRef": "C1", "entryRef": "E1", "callerRef": "S1", "selectedTargets": [], "order": 0}],
```

示例的E1/S1由所属完整阅读包声明；此处不存在悬空CT/CO。完整包仍须保存对应逐位置限制，此节没有列出限制形状。正式Schema使用上述固定列顺序，实际编码保留原状态值；当前调用状态UNRESOLVED与限制代码UNRESOLVED_CALL是不同字段，不互换。实现应从真实fixture生成完整合法示例用于直接测试。若某项固定列编码节省字节却显著增加误读，允许改用清晰字段；不能为了字节最小牺牲模型可读性。该选择以同材料A/B输入测量和引用任务为依据，不靠高端模型补救。

### 8.4 页面上下文的最小修复

当前正式 `frontendContextSources()` 已使用 sourcePath、文件摘要、范围和kind核对PAGE_CONTEXT里的unitRef与实际sourceUnitId。实验把两者当同名字段比较，未附入上下文；**不是已证明生产匹配算法坏了**。

正式新增反向索引“完整前端单元→同入口中的实际页面上下文”，用上述物理身份，绝不仅比较字段名或文件名。选择单元后：唯一相关上下文可附入观察；多实例并列展示并要求选用法，不能任取一个。没有保存上下文则记录UNKNOWN，不去当前工作目录解析补成功。

选择上下文会按既有formal规则附入其实际完整源码单元；容量按展开后计。不能以“只加上下文”之名偷偷加全部无关页面代码。不同E/实例保留独立上下文S，正文可以共用；候选HTTP、未知baseURL、未传参数和回调/保存间未证明的因果继续保留。

### 8.5 容量必须检查全部封套

导航显示源码字节、当前调用/上下文投影及去重后增量。冻结时检查实际Prompt、Schema、材料、小型对象目录和输出预留；EXTRACT返回草稿后，在派发REVIEW前检查包含实际草稿的完整封套。单元成本不是整个请求成本，字节不是token。

没有固定70KB阈值，也没有“压缩23.9%就够”的保证。先做精确去重、移出机械字段、拆独立联系，必要完整单元仍超出实际配置则停止该小题并保存准确成本/范围，独立题继续。不能截断方法、强行传巨大材料、升级模型或加窗口后把小模型目标记成通过。

目标模型有可靠token计数方式时复用现成计数器；无法可靠计数就写未知，不能自建分词证明系统。小窗口验收必须声明具体模型/窗口/输入和输出预留、实际完整请求及计数方法；本设计不承诺任意4k或8k窗口一定容纳。

## 9. 最小对象和关系怎样成为本体

### 9.1 第一阶段的对象不是空标签

O1的OBJECT业务字段沿用现有typed-v3定义，不新增一套轻量对象语言；本次新增展示角色后整体响应按§14写typed-v4。最小对象有业务名称、含义、读取范围、源码映射/变体及来源。身份已有依据就保存；没有依据则 `identities=[]`、`definitionCompleteness=PARTIAL`，按已有合同记录 `unknowns.field="identities"`。

不能把SystemConfig、Java事务类或表名自动当主业务对象。模型可以识别配置/权限等支撑对象，但主要图只显示模型已审选出的主对象；支撑对象另层展示，且总对象目录不能被展示过滤删除。若主对象无法语义区分，则保持待确认，不使用用户参考图命名。

### 9.2 联系先确认机制，不等待所有规则

O2 RELATE接收准确O1已审对象小目录和当前冻结原文。定义仍用既有 `fromObjectRef / toObjectRef / mechanism / conditions / cardinality / unknowns`；端点只来自真实目录，不允许用中文名称代替对象引用。

`readingMode=MODEL`必须复用正式阅读协调器，实际阅读输入的taskKind为RELATE，不能忽略选择方式而把初始空unitUses当作已完成材料，也不能伪装成OBJECT来复用提示。阅读、提取、审阅共享同一运行预算；EXPLICIT仍使用明确选单。原selection是请求快照，不因模型改变选择而改写。relations-v3另存每题`readingSelections`，记录准确questionId/taskId、实际selectedEntries/selectedClues、阅读status/issueCode；未启动者记录NOT_STARTED及原选单范围。O3对未完成关系任务继承实际已选K，不能只读初始clueRefs缩小分母。完整轮次、导航和正文仍由既有私有阅读记录保存，不建设第二套状态库。

联系可以确认“保存了来源编号”，同时把基数、状态联动或数据库外键留未知。若只知道共同表，没有对象记录对应，则继续是调查线索，不画实线。若存在合理但未完整确认的语义联系，保留INFERRED/UNRESOLVED及具体原因；没有任何语义判断则不强画边。

查询/引用方向、信息产生方向、状态影响方向与办理先后分别描述。例如订单字段引用来源请购单，图的引用箭头是订单→请购单；若展示请购→订单，应明确标“订单保存来源请购单编号”并说明这是来源视角，不据此声称执行顺序。本轮首版 renderer 采用定义保存的引用方向，不自行倒转。

### 9.3 细化操作、分析及身份

图形成后，再按对象或联系提出小题。ACTION只处理实际目标对象、条件、拒绝及效果；QUERY不伪称更新Action。ANALYTIC区分身份属性、筛选维度、分组维度、度量及组合指标，分别保存粒度、过滤、单位、时间、后处理及未知。

统计期间可以是维度；单据ID一般是身份属性，不因为可过滤就变成业务维度。金额字段不自动是度量；没有聚合及粒度依据不创造经营KPI。详细操作、状态、数量和指标规则分别取材，不把整张图再塞入一个全局模型请求。

对象细化使用新的OBJECT任务，保存新定义；只有后续O2明确审阅SAME_OBJECT时，发布器才统一它与早期对象。性质、属性或身份冲突必须保留，不能最后写入者覆盖。新定义不能静默替换原骨架的对象身份，旧关系仍引用自己的已审端点，发布器按合法明确对应映射。

### 9.4 实际需要补的跨运行依赖

scope-v1保留原本题依赖规则。新scope-v2已接通准确外部对象来源：同题声明的`objectSources`约束该题所有任务，包括OBJECT细化；有效已审目录进入实际EXTRACT/REVIEW及任务身份。已有来源题没有OBJECT时保存DEPENDENCY处置，不存在的题仍为来源准入错误；任一声明OBJECT未审通过时零Provider派发。新O1可以只使用明确选中的已审骨架对象执行ACTION/ANALYTIC，不从其它题累计对象猜依赖。

新执行scope-v2增加root `purpose`：SKELETON或ENRICHMENT；每题增加必需数组 `objectSources`。每项只含 `identificationRun / questionId`，与现有O2对象来源形状相同；程序恢复该题全部已声明OBJECT任务及其准确producingTaskId/reviewVersion/完整定义。不新增模型填写长定义ID的选择语言。保持现有questions/tasks/readingMode/unitUses；不新增公共命令或一般依赖DSL。

- SKELETON允许OBJECT任务，不声明ACTION/ANALYTIC，objectSources为空。细节未知不导致最小对象任务失效。
- ENRICHMENT允许OBJECT或ACTION/ANALYTIC。后两类必须有本题已审OBJECT或合法objectSources；两类来源都实际选择时取明确并集，重复完整任务机械去重，不因同名对象合并。
- objectSources必须同准确Corpus，同一运行/问题对不得重复，全部所需OBJECT、review及来源可重开且已审；来源题没有OBJECT或任一OBJECT未审通过则零Provider派发并保存依赖失败。不是只核对同一个R4。外部来源来自已结束的准确运行，不接受当前运行自引用；ACTION/ANALYTIC失败不使该题已审OBJECT失效。
- 模型只看所选对象，Java分配本任务唯一目录键并保存原owner映射。不同运行的O1/B1不直接拼接。
- 已审骨架关系可用于宿主选细化范围，不默认作为新O1事实包；本轮不新增累计关系目录接口或通用跨阶段调度器。

O2沿用selection-v2的objectSources及准确上游规则。O3同时核验O2原O1集合及细化O1的显式对象依赖，必须包含所有实际语义上游；不能仅检查O2而漏掉新O1依赖。过期对象或不同Corpus直接拒绝，不自动回溯重算。

## 10. 用实际请购关系走完整条路径

本节中的业务内容来自已保存实验，不是框架规则或完整采购链的标准答案。S编号只在该次实验问题中有效，正式运行重新分配。

1. **导航输入。** 已读保存方法的controls包含getLinkApply相关分支。Java给实际表达式和可读方法；模型自行提出“该标识连接哪类申请对象”，没有得到请购链答案。
2. **建立端读取。** Java按选出的字面词检索R4，模型选择PurchaseOrderModal.vue完整回调（424–478）。原文对查询结果判断 `subType === '请购单'`，随后 `linkApply: linkNumber`；来源明细的 `info.linkId=info.id` 另是一条明细联系，不能与主表编号混同。
3. **使用/保存读取。** 完整 `DepotItemService.saveDetials` 采购订单分支使用getLinkApply；完整insertSelective XML有link_apply与linkApply占位符。状态helper导航仍有冲突。
4. **最小对象。** 模型识别采购订单、请购单及各自业务单号/类型用途，不声称数据库已强制全局唯一。
5. **关系。** 实际审阅结果是采购订单通过linkApply引用请购单，支持来源S1/S4/S6；状态联动另记UNRESOLVED。
6. **发布视图。** 方框为采购订单、请购单；实线箭头写“保存来源请购单编号”，可展开完整原文与未知。不能因为状态细节未知删除该引用边，也不能补上未读入库/财务链。
7. **下游细化。** 若调查分批数量，另选完整数量实现；若调查状态回写，读保存目标与状态helper。它们扩展相应定义，不能改变已有关系的证据。

第二题的实际结果为同一调拨明细保存两个不同仓库标识。模型已把库存方向降为未知；这说明先展示“明细与两仓库有关”的骨架，与证明库存增减是两件事。它不是第二个真实系统的泛化验证。

## 11. Prompt合同

下面是配置示例及正式`formal-*-v2.txt` Prompt采用的通用语义要求，不含管伊佳答案。实际文本由配置读取并参与任务匹配；模型是否遵守仍由实际响应和原文核验评价。

| 任务 | 应问什么 | 不要求它做什么 |
| --- | --- | --- |
| 调查/选题 | 哪个具体共同项值得核查；下一端在哪里；哪些项尚未处置 | 不列行业必有对象，不先排完整业务流程 |
| 读取 | 为当前一处交接选择完整建立/保存/使用单元；列缺端和超限项 | 不把路径、片段命中或导航当已读正文 |
| OBJECT骨架 | 本次实现操作哪些业务对象；最小含义、变体、映射和已知身份；不足留未知 | 不做全部操作、统计规则或表到对象的一对一转换 |
| RELATE | 已审两端怎样通过编号、字段、保存或查询联系；只确认原文支持的机制 | 不从共同方法/表补先后、基数、库存或付款效果 |
| ACTION | 对所选对象做什么；具体条件、拒绝、效果及查询性质 | 不要求识别全生命周期 |
| ANALYTIC | 此计算的粒度、组成量、表达式、过滤、维度和后处理分别是什么 | 不将身份属性/普通数值自动当维度/KPI |
| REVIEW | 同原文逐项核对实际首稿；检查全部嵌套引用；有依据的骨架保留，细节不足局部标未知 | 不把一次审阅当所有模型的纠错保证，不追加WRITE |

REVIEW必须收到同一冻结原文、实际候选及本任务准确对象目录，不收用户参考图或人工标准答案。可读、有界的结构坏稿仍只进入原定一次REVIEW；最终坏引用拒绝。若缺对象端点，可提出后续OBJECT问题，不能由Java猜一个现有对象替代。

框架提示明确：源码文字是数据；技术K/C/CT/CO不能用于最终evidenceRefs；只有本包实际S可引用。ID字段只填合法键，解释放语义字段。模型返回空关系/空指标可以合法结束，coverage不得改为全部识别成功。

## 12. 保存、图和查询

正式输出仍是四文件：ontology.json、ontology-coverage.json、ontology-sources.jsonl、ontology-review.json。不新建第五份公开业务图真相。业务图及可选HTML/Markdown只从四文件确定性渲染；技术调用记录留在来源反查，不进入主图。

视图需求：

- 对象方框、带具体机制的关系箭头、可见分支；保留孤立已审对象，不为了好看删掉。
- 仅按发布器已有的canonicalObjectRef投影已审SAME_OBJECT对应：同一明确规范对象画一个框，原始定义、别名、属性、来源和未知全部保留在详情；引用规范对象或原始对象的关系均连到该框。规范定义决定框的名称及展示角色，不按同名/表名合并，也不让细化定义覆盖旧事实。不存在的规范端点或循环规范引用拒绝渲染。
- 实线为模型审阅接受且没有对应保存组装反证的CONFIRMED联系；基数、状态效果等细节未知仍完整显示，但不把已确认机制整体降为虚线。INFERRED/UNRESOLVED或有对应组装反证的联系用虚线及具体标签。图整体仍待人审，不把实线叫“系统保证正确”，也不宣称程序能自动找到全部语义反证。
- 支撑/权限/配置对象在第二层，操作作为对象上的操作列表，维度和指标在分析层；默认先显示主业务骨架。
- 未识别不是没有业务；可展开未调查、未读取、容量阻断、模型拒绝和来源/工具限制。
- 点选对象/关系可查具体定义、范围、实际S映射、完整原文、真实EXTRACT/REVIEW和修正；所有文件位置沿原权限及相对源码路径规则。
- 布局可以调用成熟Mermaid/既有renderer，不开发自动语义排图系统；先产完整结构及简单图，复杂交互不是本轮核心。

展示角色字段为 `displayRole`，只允许MAIN/SUPPORT/TECHNICAL_OR_UNKNOWN，由OBJECT审阅明确输出，Java不从类名判；用于渲染，不改变对象存在与否。角色字段新增须独立typed-v4及ontology-v2保存，不能塞进旧Schema未声明字段。无法分类为TECHNICAL_OR_UNKNOWN并可见，不默认MAIN；未审分类不得由renderer补成MAIN。

对应已有inspect/artifact增加只读导航及单任务投影查询，不新增公开Agent方法。准备、查询、重渲染和O3零模型；已完成结果读取不依赖Maven临时文件、JDK或客户当前目录。

## 13. 模型错了怎样结束

沿用已完成的失败隔离，不重写执行平台：

| 情况 | 行为 | 影响图及后续 |
| --- | --- | --- |
| 原文已提交，模型漏识别联系或分类错 | 原稿/审阅原样保存，结构合法部分按其真实状态发布；已知语义错误标待确认 | 不由Java补答案；可用新Prompt/新任务重查，不无限修稿 |
| 必要原文未提交、未读helper或上下文不明 | 保存缺项及具名成本/来源 | 对应细节未知；有独立依据的联系可保留 |
| 最终对象/关系引用非法 | 当前完整任务拒绝，不抽坏稿的一半发布 | 无依赖任务继续，依赖者未执行；保留原失败分母 |
| 同名对象身份冲突 | 未审SAME_OBJECT不合并；已审对应仍冲突则保存组装诊断 | 不最后覆盖、删条件或自动改端点 |
| 来源/配置/认证/存储故障或请求状态未知 | 停实际受影响范围，有限结束并报告 | 不返回假receipt、不换模型/账户，不自动重发未知请求 |
| 单题材料或完整REVIEW超限 | 记录未执行/拒绝及实际大小，继续独立题 | 不截断、不扩大容量掩盖失败；用户可另选范围 |

模型能力差不是重建资料框架的理由。结构合法也不是业务正确；发现具体语义反证时保留反证和原始模型结果，在视图标该定义待确认，不偷偷改模型稿。程序只检查有限结构和引用，不能承诺自动找到全部反证。

CLI不等待用户修改Prompt而长期RUNNING。每次运行返回完整任务处置、实际安装文件及支持的nextActions；原范围不完整与允许零模型部分发布分开。调用上限控制有界执行，不把历史实验累计额度当同范围缺陷修复的永久阻断。

| 私有决策/阅读状态 | decision-result-v5 / formal-reading-state-v2，reading-input/response-v4 | 保存选中K处置、上下文反向展开、准确调用编码/成本；不在旧协议暗改含义 |
| O1阶段 | ontology-identification-v3，producer v3 | 保存purpose、准确外部对象依赖及全部任务处置 |
| O2选单/阶段 | selection-v2保持字段；relations-v3，producer v3 | 复用现有objectSources，保存新typed家族及选中K的准确处置，不污染旧v2 |
| 类型化审阅/定义 | typed candidate/review-v4；ontology-v2 | 增加对象displayRole及RELATE的clueDispositions，其它业务定义形状沿用，不创建骨架专用语义Schema |
| 发布/覆盖/审阅 | Publisher producer v3，coverage-v3 / review-v3，source-v1 | 准确继承新O1外部依赖、purpose、recognitionLayers及展示角色；来源字段未变不升级 |

线索处置保存在现有私有阅读观察，并由O1/O2 coverage聚合准确已选K，不增加第五个公开结果。正式producer、Reader、Schema、policy、CLI查询和fixture同批修改。未知projection/typed版本拒绝；新封套、Prompt、地图或依赖变化不复用旧任务。

未列出的旧持久合同保持旧版本；不得为了省事把上述新语义塞进旧记录。新O0可以引用同R4，但其规则/别名身份和旧O0不同；旧E/U选单需按完整身份迁移，不能直接复制短号。

## 16. 验收要求

### 16.1 先零模型保证机械路径

1. 同一选单多次准备、输入顺序变化、导出位置变化后，正文/用途/别名及模型投影相同。
2. 压缩调用解码恢复完整有序行；同位置不同入口候选/实参/展开状态反例不得合并；不同位置同名调用也不得合并。
3. 全部所选原文、参数、未传参数、动态SQL状态及逐位置限制实际进入EXTRACT和REVIEW；REVIEW使用同包和真实草稿。
4. 页上下文按实际unitRef/物理身份反查；同一共享回调不同页面实例不串用；缺上下文和多候选准确报告。
5. SKELETON只有最小对象时可接O2/O3；身份未知或指标空不挡已有关系；坏端点仍拒绝。
6. 新ENRICHMENT准确引用原O1对象，来源错误/未审依赖零派发；O3漏选这些上游时拒绝，旧scope/历史结果行为不变。
7. 一题模型拒绝后独立题继续、没有进展有限结束、容量阻断不截断；完整任务与K分母不缩小。
8. scripted Provider走正式O0→O1骨架→O2→O3→O1细化→O3，安装、重开及查询贯通，生产模型调用0。

### 16.2 真实小范围先验材料，再评价模型

固定现有R4，使用同一正式材料路径；不向通用Prompt写采购链答案，不让宿主补选文件或业务JSON。先重查请购来源编号、调拨双仓库两个已实验联系，再用已有财务关联/期间统计验证图到操作/分析层。每项分别记录：

- 实际导航、模型选择、小题及未选范围。
- 原文是否全部提交、上下文与限制是否保留、真实封套/计数及大小对照。
- 模型是否识别具体业务联系、未知是否恰当；遗漏和错误单列。
- 图中每个端点/边、操作和分析定义能否追溯；不得只交定义数量。

大小必须按相同材料比较；跨任务选择更少单元不能冒称同材料压缩收益。单请求适合指定容量是材料目标，不要求所有模型业务答案一致。不能把仅字节减少当小窗口通过；不能因模型残余错误关闭或否定全部框架能力。

### 16.3 不过拟合的验证

非ERP fixture、业务词改名、相同表不同角色、公共Service假关联、共享组件多实例和合法多态均采用同一规则。程序不预置业务对象/关系数量或行业流程。直接fixture验证机械约束；要声称另一个实际系统质量相同，必须用独立同架构项目的真实结果核验，不能用管伊佳单例保证。

本轮不默认全仓本体验收，也不默认更多真实模型调用授权。后续实施计划应先列上述接线/材料验收，再列明确范围的真实运行。

## 17. 当前结论和剩余验收

确定采用：已有四命令及底座；共同项和保存分支查漏；Java完整取材和可逆瘦身；先最小对象/关系，再细化；图由实际已审结构渲染；错误及未知局部保留、独立任务继续。

当前正式接线包括控制K、精确调用/用途去重、页面反查、scope-v2及全部任务的外部OBJECT依赖、骨架/细化覆盖、四文件/图查询、正式Prompt及准确版本分派。129项直接测试、同代码质量及真实有限O0→O1→O2→O3已完成；最终19对象/22联系及财务/统计细化正式保存重开。实际模型未识别分立请购/订单/入库对象，来源关系接续选单没有Vue单元；不能把泛化来源编号联系写成完整采购链。

已经测量：相同选定内容调用编码与生产解码展开的完整封套节省0.4%–21.3%，139次单元出现/20份实际请求正文核验差异0；完整封套约77–329KiB，无可靠token计数。仍未证明小窗口、自主关系选材、全部业务发现、完整采购生命周期或跨项目质量。实际浏览器SVG布局未验，工具拒绝后未绕行。不得因机器终态COMPLETE抹去semanticExhaustiveness=UNDETERMINED。

本设计没有需要用户先补业务答案的步骤，也没有未定的大型基础能力。单联系必要完整原文如果始终装不下，应报告并讨论该联系范围，而不是偷偷把设计改为模型摘要或强模型依赖。

设计已同步README、材料、工作流、合同、差距清单和backlog32。最终Sol限定分支复审及Luna直接测试已有结果，不作为完整架构或跨项目审计。790保护文件不变，12前序暂存实验不混入交付，客户工具未重跑。准确版本、运行、缺口和测试对应见[正式验收](../../supplements/ontology-business-link-formal-acceptance-20261005.md)；backlog32只关闭工程/发布子项，第28长期硬约束保留。
