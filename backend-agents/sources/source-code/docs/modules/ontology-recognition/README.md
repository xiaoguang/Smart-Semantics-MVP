# 总体设计分支：新入口证据到业务本体

当前实现与业务验收分开：正式新结果已经保存采购入库单→采购订单→请购单的来源编号骨架，聚焦建立端核对使用正确PurchaseIn原文；这不是完整采购生命周期。联合骨架采用[连贯材料与联合LINK详细设计](coherent-link-material-design.md)：Java围绕真实技术锚点取得连贯原文，同题识别对象和联系，再以已审对应统一跨题身份。新正式结果、实际输入、失败和容量结论见[连贯路径验收](../../supplements/coherent-link-20261005-acceptance.md)，不以结构合法或图有箭头代替业务质量。

状态：工程、正式保存/重开和离线图接线通过；最新O3保存32份对象定义（29个canonical对象引用）、28联系、7操作、3规则、6维度、2度量和3指标。9项已审、2项拒绝保留，结果PARTIAL、覆盖INCOMPLETE；调拨拒绝、统计分类瑕疵、小窗口及总图简洁度未全部通过。最终quality-12和14项解析复用直接回归通过，固定两包四份输出逐字不变，98份本轮旧MD保护摘要不变。相关改动通过现有[PR #35](https://github.com/xiaoguang/Smart-Semantics-MVP/pull/35)交付，运行数据及原暂存PoC排除。前版19对象/22联系结果见[前版有限验收](../../supplements/ontology-business-link-formal-acceptance-20261005.md)，不混称最新结果；不宣称全仓自主识别、跨项目同等质量或已经合入main。

## 1. 先讲结论：本次设计解决什么

目标是从已保存技术证据识别：**对象类型、身份、属性、关系、操作及规则、维度、度量和指标**。不是把全部入口JSON交给一次大模型，也不是先写业务文章再把文章转换成本体。

采用四个正式操作，沿用唯一 `source-analysis`、公共Agent和存储。最新路径是**先形成业务对象关系骨架，再细化身份、属性、操作、维度和指标**，详细顺序及接线由[业务联系优先设计](business-link-first-design.md)维护。正式局部骨架及细化已产出，覆盖和容量缺口仍按验收记录保留。Java负责确定性取原文、去重、短引用、技术邻居、容量、保存与组装；模型通过小任务提出和核对语义定义；Skill负责按用户目标调用CLI、读取实际结果、解释问题和询问范围。**模型选错、误读或遗漏与程序丢材料、丢状态、错误引用分开报告。**

首版交付识别结果，不是Foundry可部署包，不创建实时对象实例、不执行Action、不计算生产数据库指标。Palantir本体连接对象、属性、关系和操作，本项目识别的是静态实现支持的类型和行为。[官方概览](https://www.palantir.com/docs/foundry/ontology/overview)、[Action说明](https://www.palantir.com/docs/foundry/action-types/overview/)。

### 最新实验究竟证明了什么

2026-10-05已完成[自主选材业务总览薄实验](../../supplements/ontology-business-overview-poc-20261005.md)：Java提供准确共同项、模型自行选主题和39个原文单元，展开为52个单元后提取及审阅，保存实际对象关系图。采购订单到入库、入库到退货等主要联系可反查；请购和通用财务对象存在遗漏，约354KiB阅读材料仍偏大。只证明有限自主骨架路径可以运行，不宣称完整采购链、小上下文或跨项目质量通过；此实验不是新正式CLI。

随后完成[紧凑材料与遗漏联系补查实验](../../supplements/ontology-compact-link-probe-20261005.md)：同一材料可逆编码降到269.7KiB、减少约23.9%；模型从通用源码分支自行选中linkApply，Java从R4取回页面建立端，提取及审阅补出采购订单引用请购单编号的关系。另一个自行选择的调拨两仓库联系保留方向和库存未知。两题提取封套仍约164/140KiB，未通过小窗口目标；新读前端的页面实例上下文尚未验收。仅是增量薄实验，不是正式CLI修改或全仓识别。

正式分离任务仍丢失来源端点后，完成[连贯包联合识别薄实验](../../supplements/source-link-envelope-thin-probe-20261005.md)：Java核验失败稿的实际线索、组织完整原文，联合EXTRACT/REVIEW补出订单引用请购单。相同选材224,186→119,695字节，减少46.61%；完整两请求约119.35/120.17KiB。只证明一条联系恢复及表达改善，不证明完整采购链或小窗口。新正式设计采用同类联合路径，不用该实验覆盖现有正式失败。

较早的[辅助两联系PoC](../../supplements/assisted-two-link-concept-poc-20261002.md)保留为材料基线，不把它写成自主选材成功，也不以其当时缺口覆盖后来的正式验收：

## 2. 输入、输出与透明边界

### 输入

- 新R4入口证据发布集合、真实receipt及准备版来源 `PREPARED_V1`。
- 由R4取得的同源R0有效文件；可按明确配置提供项目说明或DDL原文。
- 明确业务问题，或用户选择的无提示调查模式。
- 模型、容量、调查范围及可替换的Prompt配置。

不接受旧M10、Packet、326/418条Activity、旧过程稿/目录、九章或参考HTML作为模型事实输入、候选种子或复用来源。公共运行/Provider底座可以复用，不表示旧内容兼容。历史材料不删除、不改写。

### 输出

正式发布为 `ontology.json`、`ontology-coverage.json`、`ontology-sources.jsonl`、`ontology-review.json`；可选Markdown/HTML只读取这四项，不另做模型改写。识别状态为待人审、不可执行；完整文件集合不代表业务语义全对。

面向用户的主要视图是业务对象关系图，不是Controller调用图或定义数量汇总。其展示及跨项目验收要求见§8；当前有限样例的发布成功不表示已通过业务总览验收。

**稳定证据与流程结束是框架责任。** 模型原稿、审阅及校验不写回R4/R0或冻结材料。最终坏定义拒绝并保存；无依赖任务继续、依赖缺失者明确未执行、命令返回全范围处置已有直接测试。真实采购关系拒绝后统计关系继续已验证；O3保留九项处置并发布八项完整已审任务。不等待模型总有一次答对；共享来源、存储、认证或远端状态未知仍停止受影响范围。最后边界修复和PR的状态按验收记录读取。

每项定义带来源、适用范围、确定性及未知。系统建议的分析维度/指标放在 `ANALYTIC_EXTENSION`，不默认进入已实现集合。数据合同详见[contracts](contracts.md)。

### 对用户Agent开放什么

运行ID、具体操作、状态、来源、真实产物、问题和支持的下一动作必须可查询。可以查看实际阅读包、原始完整证据、纳入/移出清单、短号映射、Prompt/Schema、原始模型稿和审阅修正；不要求用户只能相信一段总结。

用户可以修改任务Prompt和沟通Prompt，也可以配置已有的来源、模型、范围与容量。**“只改Prompt”是无代码定制语义行为的边界，不是禁止必要配置。** Prompt不能改变来源校验、有效范围、引用、Schema或容量规则。确需新证据投影/工具行为时，属于用户明确要求的代码扩展，不由宿主Agent临时拼证据后冒充框架结果。

## 3. 技术操作与本体操作分开

```text
R0 源码准备
  ├─ R1 前端采集 ───────────────────┐
  └─ R2 后端采集 → R3 持久化分析 ────┴─ R4 按entryId组装证据
                                               ↓
O0 prepare-ontology：资料库、技术导航、可选DDL投影；零模型
  ↓
O1 identify-ontology：调查/选材 → 局部类型化提取 → 对照原文REVIEW
  ↓
O2 relate-ontology：跨入口/跨题身份及关系 → 对照原文REVIEW
  ↓
O3 publish-ontology：确定性检查、组装、保存；零模型
```

R0–R4已有正式技术能力。O0–O3四命令经正式Agent、保存、查询和发布完成三个固定客户局部样例；显式范围、DISCOVERY及QUESTION＋MODEL另有scripted直接回归，不代表真实自主发现。统计完整辅助正文确实入模并保留调用冲突；O1全部已审、O2采购关系拒绝、O3有效部分保存并可查。它们只使用repository-knowledge的独立模块槽位，不增加第九个固定步骤，不调用旧Step07过程执行器，不重新设计Activity。

## 4. 最新目标：先连业务，再完善本体

下表是业务联系优先的实施顺序。跨运行OBJECT来源、骨架发布及细化已有正式Agent/store直接测试与真实局部运行，最终质量通过；具体业务遗漏、自动关系选材及小窗口不足单列，不以任务终态覆盖。四个命令保持不变，可以按同一Corpus建立多次O1/O2和新O3；早期发布不被后续覆盖。

| 步骤 | 输入 | 谁做什么 | 输出及实际下一消费者 |
| --- | --- | --- | --- |
| ①准备资料 | 准确R4/R0、可选说明/DDL配置 | Java核对来源、去重完整正文、保留入口/页面用法；按已保存方法、表列、语句和前端身份建立技术检索；不批准业务关系 | O0资料集、导航、来源映射、覆盖；供②③④取材 |
| ②认识系统与选题 | 小型技术导航、共同项及用户问题/调查模式 | 模型提出可修正系统假设和调查问题；Java保留全范围分母和已选入口，不因移出正文丢掉待读另一端 | 系统假设、调查问题、首批读取选择；供③，不是已确认ERP对象目录 |
| ③联合骨架（已接线，真实验收待完成） | 一个真实K、Java组织的连贯完整实现、页面用途及限制 | O1 LINK同时定义对象和具体联系，再用同包原文REVIEW；Java只核验及编号 | 同任务闭合的对象/联系给⑤；不会因旧目录没有新端点而先删边 |
| ④跨题联系与身份 | 精确选择的已审OBJECT/LINK、必要原文 | 有需要才做O2 RELATE/SAME_OBJECT及一次REVIEW | 准确对应及未知给⑤；不按同名同表合并，单个LINK不强制空O2 |
| ⑤发布骨架 | 对象、关系、处置/覆盖及来源 | O3零模型检查和原子保存，确定性渲染业务图 | 可查看对象关系总览；未调查操作/分析层明确标记，不冒称完整本体 |
| ⑥分题细化及新发布 | 准确骨架对象依赖、下一处完整实现 | 新O1做对象细化、ACTION或ANALYTIC及一次REVIEW；必要的新O2显式身份/关系审阅；新O3组装 | 新版本操作、规则、维度、度量和指标；旧骨架不覆盖，指标不可执行 |

行业类型只是假设。模型可认为是ERP/CRM或混合/未知，但不能据此补出“必然有财务、采购、完整生命周期”。Java按共同线索组织阅读范围，再按容量分页；页次不是业务顺序。高扇出共享工具/表不构成业务关系，未展示范围不得消失。

### 为什么跨Controller可以连上

辅助财务实验已核验的是：保存端取得业务单据ID并存为财务明细的 `bill_id`，查询端使用同一字段过滤财务单号。两Controller无需互相调用；连接依据是**标识交接机制的完整两端**，不是名字相似。

辅助采购实验已核验的是：页面来源明细 `info.id` 被放入后续明细 `linkId`，保存端写入 `link_id`；另有单据编号 `linkNumber → link_number`。这些支持局部联系，不自动证明全部分批数量、状态回写或付款过程。[完整实例及限制](implementation-delta.md#3-实际例子材料怎样成为业务联系和本体)。

## 5. Java材料组织必须怎样做

[材料详细设计](material-preparation.md)拥有具体算法和状态合同，这里只列责任：

1. 完整证据与模型阅读投影分开。模型不默认收到entry JSON、全部所属调用、receipt、长ID和重复声明。
2. 选中的完整方法/XML/前端实现不截断；必要辅助方法可另选，未读实现不能被解释为正常返回或无条件成功。
3. 保留不同入口、页面实例的参数用途；选入的调用用紧凑记录，相关可疑边、外部/未知/失败状态逐位置保留。
4. `selectedEntries`、待读句柄、已读历史和当前正文集合分别保存；移出正文不删除调查范围。
5. 从同一投影计算导航读取成本、实际阅读请求、提取以及含实际草稿的审阅成本；字节不是token。必要完整实现仍超限则报告，不静默加容量或换强模型。
6. 程序准备不调用LLM、不读取中文来猜业务。锚点选择记为显式或模型选择；选定锚点后的技术扩展由Java保存实际派生依据，不能将自动机械展开称为模型选材或完整业务召回。

**简短指不送无关机械字段；完备指当前结论的必要原文确实提供，而且错误能反查完整保存证据。** 不能证明任意单个方法都适合任意4k窗口；一次问题材料足够，不等于全仓取材完成。

## 6. DDL、短ID和计算定义的取舍

### DDL：可选O0材料，不新增必经R5

最新两联系PoC没有使用DDL，不能说“本次成功依赖DDL”。同R0确有 `jshERP-boot/docs/jsh_erp.sql`，约91.9KB；已有JSqlParser5.3可解析所试两段CREATE TABLE，但整份dump曾在方言语句处失败。[核实与成熟工具研究](../../supplements/ontology-ddl-and-reference-research-20261002.md)。

配置明确DDL文件时，O0用现成模型解析器生成可选 `schema-evidence.json`，保存原文引用、实际表列/约束和未解析范围；未配置记关闭。它可以补数据库主键、空值、类型、唯一性依据，**不能代替业务对象、关联机制或指标语义**。普通索引不当作FK，没有约束就保留未知。不执行SQL、不把dump的INSERT当生产实例、不增加自写方言恢复器。本轮不要求新技术R命令；以后若有独立数据库来源，再单独设计。

### 短ID：前移到证据读者/资料库，保留稳定身份

支持你的方向，但不把持久entryId/hash改成裸 `E1`。完整内部身份保留，证据读取时提供资料库作用域内稳定E/U/K别名；页面显示和后续查询使用同一编号，模型不再抄长viewId。模型原文阅读包仍需局部S编号，因为它引用的是本次选中的具体原文/用途。定义编号另带任务作用域，不与源编号混用。

映射保存、可逆、参与指纹；不同资料库的E1/S1不可混用。**本次先做读取适配，不改写已保存R4，不因缩短模型编号重跑技术取证。**

### 指标与维度不是强制填空

对象身份、属性、关系两端、操作目标/条件/效果、计算粒度/过滤/单位/空值、维度来源和指标组成引用用类型化字段表达。数值属性不自动是Measure；金额计算可先作为派生属性或操作效果，只有明确聚合口径才建Measure；企业KPI要有明确依据。普通筛选参数不自动成为维度。缺少定义可留空、未确认或分析建议，不补答案。尚未实测的维度/指标不能由两联系PoC代替验收。

机器主格式是类型化JSON，不要求只存三元组。关系可投影为三元组视图，但身份、条件、规则、计算和来源仍保留完整字段；不为展示三元组引入RDF平台。

## 7. 模块、Prompt及宿主Agent

五项内部职责复用现有底座，不是五套运行框架：

| Module | 输入 → 输出 | 不能承担什么 |
| --- | --- | --- |
| EvidenceCorpus/MaterialPreparation | R4/R0 → 导航、完整单元、紧凑阅读包及映射 | 不判断业务关系、不写新解析器 |
| Recognition | 问题/材料 → 已审对象、操作和分析定义 | 不因类型名推导系统必有业务 |
| Linker | 已审定义/两端材料 → 已审关系和身份决定 | 不按同名自动合并、无全仓两两比较 |
| Validator | Schema/引用/来源/范围 → 结构检查及诊断 | 不做中文真假裁决 |
| Publisher | 封闭已审集合 → 正式产物及查询 | 不润色、不执行指标/Action |

业务Prompt包括调查、读取、OBJECT/ACTION/ANALYTIC、RELATE及REVIEW。替换的是提示文本，不替换固定响应Schema、工具或来源规则；实际文本和模型身份保存，变更使语义任务复用失效。宿主Agent另有沟通Prompt，只读实际CLI结果报告和询问，不能偷偷改原始输出或补业务事实。

正式模型调用通过框架已有Provider完成；不要求Codex独有上下文或界面能力。现有Provider不等于任意模型产品均已验证；各适配器必须准确转换字节、token及模型上下文配置，不能把byte字段直接当token。非结构化输出不能凭主持Agent“整理一下”变成已审合法结果。

## 8. 验收和待实施边界

- **证据审阅是框架验收的核心：**逐项从已保存的实际模型请求确认建立端、使用端、条件、后处理及限制是否提交；EXTRACT与REVIEW须收到同一冻结原文，REVIEW另收到实际草稿。Java零模型准备、原文未截断、实例/范围/限制不丢、短引用可逆、非法最终定义拒绝、保存重开及透明查询同样属于框架验收。有R4原文但没送进本次请求，仍算材料缺口。
- **模型质量另列：**已提交证据仍被误读、遗漏或错误分类，不倒算为材料问题。调整Prompt可以改善，不能保证模型零幻觉；结构化输出合同反复使模型制造无效引用时，单列合同可用性，不靠猜测改写语义端点。
- **业务覆盖：**已调查、未调查、未读、失败和建议分别保存；局部联系通过不等于全部对象/维度/指标覆盖。
- **自动取材：**独立评价，不拿显式选择样例冒充成功；本次辅助PoC证明材料格式与Java机械路径，不是这项证明。

### 业务总览的展示与跨项目验收

以下是已确认的目标约束，不是当前代码已完成自主总览的声明：

1. **主图先表达对象与联系。** 方框使用有依据的业务对象名称；箭头写清两端怎样联系，例如保存来源标识、包含明细、读取状态或影响某项属性。不能只写“相关”，也不能用Java类名、HTTP路径或长ID代替主要业务标签。箭头含义是关系或影响，不默认表示执行顺序；支持分支和多对多关系。
2. **其他定义分层展示。** 操作挂在实际目标对象上；维度、度量与指标另列关联分区；详细条件和规则可展开查看。先让人看清对象骨架，不要求先证明全部规则才显示已有联系；没有依据的层允许为空，不强行填满。
3. **图中结论能反查。** 每个对象和关系保留结构化结果身份及实际来源。已有原文支持且审阅接受的联系用实线；仍有待确认的语义候选用虚线并注明具体未知。仅有技术共同项、不足以提出业务联系时，留在调查线索中，不强画业务箭头。模型审阅接受不等于已证明业务绝对正确，识别结果仍标为待人审。
4. **参考图片不成为答案。** 用户图片只约束展示形态和可读性，不进入调查、选材、提取或审阅输入；图片中的对象名称、采购链条、关系标签不成为候选种子、提示词标准答案或Java业务规则。图由实际识别结果生成，不从图片复制内容来宣布识别成功。薄实验只从自己的已保存结构化结果和来源生成图；正式路径从O3四文件生成同类视图。
5. **材料路径不能在实验和实施间偷换。** 薄实验的导航、选中原文、用途、限制和来源映射由Java产生。宿主Agent不能人工补出业务链或修改模型结论后再画图。验证可行后正式CLI复用经验证的材料组织与识别路径，不把人工选材成功当成自主能力证据。
6. **相同架构使用相同规则，不保证模型答案相同。** 当前目标限定在受支持的Java/Spring MVC/MyBatis与有限Vue2静态模式内。共同方法、Mapper身份、真实表列、调用参数和页面实例使用技术身份匹配，不按管伊佳类名、字段名、中文业务词或预期采购流程编写专用判断。缺材料或不支持的模式必须披露，不用业务常识补成功。框架应保持同一取材、校验、来源和展示标准；业务识别完整度仍受实际代码及模型能力影响。
7. **泛化须分层验证。** 使用非ERP fixture、业务名称及路径改名、共享工具造成的假关联、同表但不同业务用途等直接测试，验证程序没有依赖测试项目的特定词和顺序。这只能证明机械路径及反过拟合约束；要声称另一个实际系统也有相同业务识别效果，还须对独立同架构代码运行同一流程，并分别核对材料完整性、模型结论和可读总览。管伊佳单例不构成跨项目质量保证。

本轮薄实验的最低交付是可查看的实际业务总览、结构化识别结果、来源映射和实际输入成本；不能用“调用完成”、定义计数或局部规则报告代替。框架漏材、输入不必要膨胀及联系被程序丢失需要修正；原文确已提交而模型误读或遗漏应单列，不以无限修稿维持成功表象。
