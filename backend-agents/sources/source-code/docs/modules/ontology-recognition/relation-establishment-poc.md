# 关联如何建立：有界阅读薄实验详细设计

状态：2026-10-01，设计与零模型门禁已完成；一次真实实验在第2次请求后因完整阅读包超过70,000字节停止，尚未提取或审阅，建立机制验收未通过。详见[本轮实际记录](../../supplements/relation-establishment-poc-20261001-acceptance.md)。本文保留本次执行合同，不把失败后的设想写成已实现。只验证财务联系，不发布正式本体，不覆盖[旧关系实验](related-evidence-poc.md)。

## 1. 问题与成功含义

目标不是证明“两个入口可能相关”，而是核对两个对象之间的关联值从哪里来、如何传递或转换，以及在哪个动作、什么条件下形成关系。

给模型的唯一普通问题：

> 财务记录如何与业务单据建立关联？请选择一条实际机制，核对关联标识的来源、传递或转换、建立关联的动作及条件。只读到查询时不能宣称建立机制已经确认。金额、欠款及其它联系不在本次范围内。

不能预先提供正确 Controller、字段、路径、阶段答案或人工走查。问题是财务范围提示，不称无提示发现。候选仍来自既有人工限定20入口，不能宣称全仓自主发现。

只见共同方法/表、接口名称或查询条件，均不能作为建立机制通过的依据。持久化关系、临时参数传递、消息关联的机制可以不同；合同不预设必须有外键、SQL写入或固定业务顺序。

## 4. 导航与完整阅读

初始只展示20张紧凑入口卡、可读单元标题/大小及少量具体共同项。取消向模型发送190对全量14通道矩阵；完整统计留在程序侧。

具体共同项由既有方法身份、XML语句身份等集合求交得到，不新解析源码。展示真实名称、涉及入口、不同入口使用数和可读句柄；受限展示必须报告总数/未显示数。公共方法频繁出现不等于业务有关，低重合也不自动排除候选。

每轮均允许：

- `READ_UNIT`：读取本轮已显示的准确单元句柄。
- `ENTRY_UNITS`：按准确入口及明确单元类型取一页候选。
- `LITERAL`：按模型提出的实际字面词查询，返回片段及完整单元句柄。

查询片段只是导航。读取方法附上已保存的所属调用及必要目标导航；正文与条件保持完整，不递归无条件读所有调用目标。

表列反查只覆盖已有SQL AST中的表列，不宣称所有动态SQL均被索引。字面检索用于补充候选，不自动把不同拼写认作同一字段，不自动标为READ/WRITE。必要新解析器不在本次范围内。

每次查询最多25项；每轮最多两页、合计50项；累计完整读取请求最多12个。限额及未读数量进入实际模型输入。已读引用只能保留；导航引用只能请求读取。空阅读包的保留集合必须为空。

本实验入口短号统一使用 `EN1…EN20`，导航单元使用 `N1…`，已读证据保留现有Packet的 `J/C/X/…` 短号。入口上下文与查询目录必须使用同一份入口映射。现有Packet内部会按所选入口另编 `E1…`；薄驱动只重映射其结构化入口上下文和 `entryUses`，不能把这套局部号拿去查询全局目录，更不能全局替换源码字符串。`SOURCE_REFERENCE`证据本身可以有 `E1`，不与 `EN1` 入口混用。私有原文及原始Packet不改。

模型读到新的标识后，可在后续阅读轮提出新的查询。程序将结果与新短号送入下一次请求；不能在同一次尚未看见结果的响应中引用未来编号。到末轮仍只有候选目录而无正文，停止为阅读未完成。

## 5. 顺序及调用上限

```text
SELECT：选择联系、首批读取/查询
→ READING_1：对照首批原文，保留、移出、继续查读
→ 可选 READING_2：对照新增线索/原文，最后查读
→ EXTRACT：从实际封闭原文提取建立机制或明确局部结果
→ REVIEW：同一完整原文＋实际提取稿，直接返回修正结果
```

最多3次选材/阅读决定＋2次提取/审阅。中途材料足够可少于5次；超限或合法失败停止，已派发数按实际记录。

阅读“可尝试提取”不是语义通过。查询-only原文可保留准确局部结果，但最终不得标为建立机制通过。最后补读的正文实际进入EXTRACT及REVIEW，不能只以模型请求的标题宣布已读。

## 6. 结果合同与结束检查

提取与审阅至少保存：

- 两端对象及必要中间对象的描述；暂非正式全仓对象ID。
- 标识来源、传递或转换、建立动作、条件，各自的具体原文引用。
- 其它直接支持的查询事实和限制。
- `establishmentStatus`：建立机制有原文支持／仅查询用途／未确认。
- 未解决内容；审阅另有纠正说明。

Java检查每项结构、引用存在于实际已读包、映射不串源，以及“建立机制有支持”结果所需字段与引用非空。Java不通过中文或SQL关键词判业务真假，字段填齐不等于结论成立。

`QUERY_ONLY` 是允许保存的诚实局部结果，但不算建立机制验收通过。程序只能拒绝缺字段或非法引用，不能仅凭结构检测“文字写成建立、实际来源只有查询”这类语义错误；后者由原文REVIEW及人工验收检查。

最终REVIEW必须确认：身份是否来自正确对象；值的转换/赋值是否有完整实现；建立动作是否被实际代码支持；条件与未知是否保留。不能从两个同名参数、同表或接口用途补成完整关系。

最终输出标为实验结果。模型执行结束、协议通过和人工业务验收分别记录。只查询成立时交付局部稿，但建立机制验收不通过；不伪装成正式ontology.json。

## 7. 容量与模型依赖

完整包上限70,000字节，实际请求封套上限160,000字节，输出余量20,000字节，沿用已有POC配置。逐次记录输入/Prompt/Schema/输出余量，审阅含实际提取稿。任何原文超限明确失败，不静默摘要或截断。

上述字节限额不是token容量证明。实验只检验Luna/high实际处理这条联系的表现，不声称任意小上下文或弱模型都能完成。降低负担依靠一条联系、具体候选、短引用、完整少量实现和固定问题，不靠模型从全仓巨型JSON自行推理。

## 8. 离线门禁及人工验收

真实执行前零模型验证：

1. 空包保留集合为空；查询返回新导航、下一轮才读取对应完整正文。
2. 读到原文中新词后可再次查询；新句柄不得与已读引用混用。
3. 方法/XML正文、调用参数、条件与限制不截断、不丢失；不同入口用法保留。
4. 查询-only输出不能通过建立机制结构门禁；未知/错误引用拒绝。
5. 末轮无正文停止；最多5次请求；失败无自动重试。
6. 旧原始记录和受保护材料摘要不变；所有离线Provider调用来自scripted，不启动业务模型。

人工金标准只在验收侧使用[固定原文走查](evidence-walkthrough.md#4-重点跨controller的业务联系)：检查本轮是否自主找到相关完整实现、正确解释标识交接及可选条件。额外金额、欠款、运行时付款和数据库唯一性未调查不判关键错误。

实验通过只证明有普通业务问题提示时，这条局部关联可被自主取材并核对。不证明全仓无提示发现、全部本体类型可组装或新方案优于旧方案；本次无严格A/B。

## 9. 交付与停止

交付完整实际导航、查询、阅读包、可逆映射、提取稿、修正审阅稿、调用数/输入大小/请求间隔及人工验收记录。旧21次额度记录保持原样，新记录明确本次追加及累计。

设计与离线通过后只运行一次具名财务实验，随后报告结果。不扩大全仓，不启动采购第二题，不重复实验，不升级模型或继续正式化。

## 10. 当前实际结果及未通过边界

- 编译、scripted查读门禁和主代理独立预检通过；实际产品派发2次，累计旧21次合计23次，无重试。
- SELECT自主选择财务新增及按业务单据ID查财务单号的入口；READING_1进一步请求财务查询Service、财务新增Service及财务明细保存实现，没有预先提供正确字段或答案。
- READING_1实际收到的正文只是查询Controller及其调用。其后读取请求形成的新增实现，因封包超过限额未进入任何产品请求。不能把尝试读取集合当作模型已读集合。
- 包增长不仅来自模型选择的完整方法；驱动还自动附入这些方法的全部所属调用记录。实际失败集合为4个方法、114条调用：原始方法正文7,453字节，完整方法模型单元16,942字节，调用单元73,753字节；模型包合计91,408字节，EN重映射后91,536字节。导航单元大小未表达自动附入调用的增量成本，详见验收记录。
- 没有EXTRACT、REVIEW或建立机制结论。已找到正确调查方向不等于最终业务推理成立；本次不能宣布局部本体或全仓本体成功。

仍需决定的最小问题是如何将完整正文、必要调用对应关系及限制以更紧凑方式交付，同时准确标出自动附入成本并测量所有后续封套，而不是提高上下文要求、截断正文或再次取证。精确诊断已结束，新投影尚未实施；不擅自修改合同、提高限额或追加实验。待办见[第26项](../../supplements/implementation-lessons-and-followups.md#26-本体阅读包的实际成本与紧凑投影)。
