## 1. 结论、实际断点和本次边界

Java可以从已保存JSON中找出“引用同一个方法、Mapper语句、已解析表”的入口。这是字段分组和反查，不需要LLM，也不需要新分析器。**是否属于同一业务对象、是否有对象交接，必须读相关原文后由模型提出并审阅。**

本次修正的是选材职责：

```text
R4中现有技术身份 → Java生成可分页线索
→ 模型提出并选择一个具体问题
→ 模型选择少量首批完整单元，或先请求线索详情
→ Java查询、取回原文
→ 同一个有界READING循环保留、移出、补读
→ EXTRACT/RELATE → 原文REVIEW
```

当前P2的实际断点：

| 已核对的行为 | 为什么需要调整 |
| --- | --- |
| SURVEY仅看到HTTP方法/路径、Controller处理方法、组装状态和限制数量 | 看不到已保存的共同方法、语句、表等查找线索 |
| P2d从六页调查的39个问题选2个；上限来自实验配置 | “最多2个”不是业务优先级依据；响应没有比较为什么先做这两题 |
| 驱动将每题列出的全部入口Controller方法自动读入 | 6–8个候选入口被等同于6–8份必需首批正文；模型未单独选择首批 |
| 第一题8个方法原文共34,855字节，完整单元共69,712字节；初始包69,836字节 | 70KB是包上限，不是“每入口约10KB”的固定大小；几乎没有补读空间 |
| 两题补读均超70KB，未进入EXTRACT/REVIEW | 证明选材/封包未完成，不能证明模型已读原文后仍推理失败 |

完整测量与旧请求保存在[实际验收记录](../../supplements/ontology-recognition-poc-acceptance.md)。旧结果不改写；G1仍未通过。

本次只复用现有Corpus、决策runner、阅读协调器和私有保存器。**不做**：技术重扫、旧Activity输入、全入口两两组合、向量/图数据库、Java/SQL解释器、行业规则分类、一个问题多包摘要归并、宿主Agent代写答案。本页不能保证调整后P2必过，必须另做实际验收。

## 2. 分工：谁找，谁判断，谁执行

| 负责者 | 做什么 | 不做什么 |
| --- | --- | --- |
| Java / Corpus | 验证R4/R0；按准确字段建立反向列表；分页、字面搜索、读完整单元；保存映射、大小、限制和实际响应 | 不从同表/同方法批准业务关系；不根据中文问题猜业务范围 |
| Java / runner | 按有界请求调用已配置StructuredModelProvider；执行允许的查询/读取；校验Schema、引用与容量 | 不调用任意shell工具；不替模型删除规则、补答案或静默截断 |
| 模型 | 认识系统并提出假设；比较调查目标；选择阅读目的及原文；提取身份、操作和口径；原文审阅 | 不直接访问磁盘或把导航线索当已审事实 |
| Skill / 宿主Agent | 按用户目标和授权调用四个操作，读取真实报告，解释断点和可选范围 | 不暗中挑正确路径、导入P1答案或自行扩大全仓/调用预算 |

产品模型由Java Provider调用。Skill不是另一个语义生成通道；宿主Agent可编排，但工具仍需已支持的Provider。当前正式四命令及共享Skill本体路由已经接通并有直接工程验证；三个具名局部样例已经正式O0–O3运行及证据核验；任意宿主产品、真实自主选材和全仓语义覆盖仍未验收。不能把工程接通说成模型定义已通过。

## 3. Java从哪些现有字段找共同点

Corpus先严格重开整份R4。反查只在同一已验证资料集内进行，索引成本按实际引用条数增长，不预先展开所有入口对。

| 线索 | 准确来源与比较方式 | 模型可以据此请求什么 | 不代表什么 |
| --- | --- | --- | --- |
| 同一Java方法 | `java.methods[].methodKey`；保留声明、源码路径及入口用法 | 方法完整单元、使用它的入口页 | 相同业务对象、必经步骤、方法曾运行 |
| 同一Mapper语句 | `persistence.bindings[].statementRefs[].statementRef`及已有`databaseId`；SQL记录使用其实际语句身份 | 绑定记录、XML、SQL分析及相关入口 | 静态匹配等于运行时执行证明 |
| 同一表 | `persistence.sqlAnalyses[].ast`内实际`TABLE`节点 | 哪些语句引用该表、完整动态XML/调用上下文 | JOIN基数、对象同一性或业务时序 |
| 列线索 | 只取AST实际`COLUMN`节点；同时保留节点是否有表限定 | 具名SQL单元；未限定列仅作为候选命中 | 同名`id/status`是同一个业务字段 |
| 入口单元清单 | 已保存的`unitsByEntry`和单元种类/身份 | 分页查看有哪些完整方法、绑定、XML、SQL、前端单元 | 目录项全部都应读入 |
| 字面搜索 | 在允许资料中查实际字符串，保存命中单元和未命中 | 读命中原文；进一步核对字段用途 | 未命中即系统无此对象/关系 |

调用目标的确定/候选性质、前端地址条件、SQL解析状态和原技术限制全部继承。方法清单中的出现只证明“本次材料包含该方法”；沿不确定调用收集的内容不能升级为确定调用链。

### 3.1 当前必须修正或披露的实际问题

1. 原`OntologyEvidenceCorpus.statementUses`把`statementRefs`元素当字符串。真实R4元素是对象，字段在`statementRef`；本次已按真实形状修复，并由一项先失败后通过的直接测试覆盖。新增变体及全链回归仍须分别核验，单项通过不等于自主选材通过。
2. 部分SQL的`ast=null`；部分列只在`EXPRESSION`文本中，没有`COLUMN`节点。目录须注明解析覆盖，零命中不等于不存在。首版不从表达式文本再写SQL解析器；必要时读完整XML/SQL或字面搜索。
3. 同语句不同`databaseId`的用法不得静默混为一个确定语句。当前`statementUses`返回绑定句柄，XML/SQL还须另取；`read`按原身份返回第一份匹配，不能直接用于歧义变体。绑定到语句仅在唯一时可读；存在多个变体时以已保存的`statementRef + databaseId`建立可逆读取句柄，无法区分则记录具名不可读，不猜变体。按真实字段形状处理，不接受测试外围先填好答案。
4. 本次薄实现已将`methodUses/statementUses/tableStatements/columnStatements/entryUnits`接到READING查询及下一轮模型请求，49项直接测试通过。独立P2g在PRIORITIZE前超限，READING实际调用为0；不能用scripted消费链通过代替真实选材或语义验收。

### 3.2 高扇出与不完整线索

每条线索记录实际使用入口数、总命中数、当前页范围和未显示数量。共享工具或基础表可能命中很多入口；Java不猜“它没业务价值”，也不按高频自动批准或排除。模型须说明某次读取能解决哪一项问题。分页和未读范围保留，不能只取前几个后宣称全部核对。

## 4. 先给薄导航，再允许查详情

本次下一步按用户最新选择先做[相关证据轻量POC](related-evidence-poc.md)：可用已有重合或LLM粗估，不先开发完整相关分组和评分系统。实验只检查受控范围的选材与原文关系，不能当作全仓发现或六类类型化本体通过。下面仍描述正式选材目标与当前实现，不将POC视图冒充已接通生产行为。

当前限制：SURVEY仍按R4目录顺序切成入口页，尚未在首次调查前按共同方法、Mapper或表组织相关入口；已有反查主要供后续READING使用。分页覆盖不等于跨入口关系已被发现。用户提出按技术重合与状态读写信号调查后，已完成20个真实入口、190对的零模型测量；各维度重合及公共项频次可计算，但低重合也存在状态读写线索，不能以分数替代原文核对。采购页面的不同参数用法还可能共用一个entryId。该测量没有替换生产调查，也没有完成真实模型对照；实际规则、反例和限制见[定向测量](../../supplements/entry-overlap-probe-20261001.md)。

目标导航有两层，不把几千个句柄再次塞入一次请求：

1. **入口卡：**原有HTTP/处理方法/限制，加可请求的Controller单元短键、已存方法/语句/表线索数量及有限线索短键；同时给未展示分母和详情页入口。不含完整正文或业务结论，有限展示不表示没有其它共同点。
2. **线索页：**种类、准确声明或表名、相关入口短键、来源性质、用法数、解析限制、完整单元大小及后续页。超本页记录/字节上限时显式给出未显示数量和下一页，不隐式丢弃。

目录按稳定技术键分页；排序不是业务重要性。每页只呈现其确实包含的线索，未显示部分仍可通过入口单元页/反查取得。导航容量使用既有页及字节上限，不引入“每入口最多几个业务对象”的硬规则。

SURVEY的问题同时保存实际选中的`clueRefs`。**历史P2g实现**的PRIORITIZE接收全部调查问题及其引用并集的入口卡、Controller单元和线索投影；41个问题仍引入184张卡、307条线索，实际封套247,900字节，超过160,000上限。此前六页SURVEY分别能容纳，不代表其汇总能容纳。

**现行已实现合同**：全局选题只比较六份实际SURVEY输出中的问题、假设和未解决项；每页保留offset、入口数量和总数，不再附其导航视图。短引用原样保留在调查响应中，模型此时只选调查目标，不要求猜测单元大小或直接选完整源码。选定后，Java从被选问题的实际`candidateEntryRefs/clueRefs`在其原页投影详细导航；只把该题投影交给该题的首轮READING。若两题在同一页，也分别封装各自的投影，不让一题看到另一题的候选并集。READING已有的零正文、有限查询和完整读回继续承担首次选材。不提高容量、不增加模型步骤、不删完整原文。P2g六份SURVEY精确零模型重放后的v3封套实测78,332/160,000字节；P2i真实PRIORITIZE得到两题，第一题首轮读回4个完整Java方法。[实际记录](../../supplements/ontology-recognition-poc-acceptance.md#p2g之后的最小调整与独立重验)

`PRIORITIZE`输入/输出升私有v3。输入的`pages[]`只含页号、入口数、总数及该页完整已验证SURVEY响应；输出的`selectedQuestions[]`保留页号、问题ID、具体问题、理由、未知、该题候选入口及任务种类，**不再有`initialReadRequests`**。候选入口只能取该页该题实际列出的引用；遗漏或未知的入口需在READING查询/搜索。程序核对选中问题身份、引用的页及类别，产出该题专用可逆投影；模型不能用其它题或未显示的引用扩充阅读范围。私有记录仍保存六页来源映射及该题实际投影，映射、Prompt/Schema、输入和模型身份都参与任务匹配。历史PRIORITIZE v2与新版不可互换。

容量已使用P2g六份原始SURVEY响应做**零产品调用**重放，逐页jobKey、请求输入和响应与原记录相同；v3汇总字节预检通过。P2i真实重验显式精确复用六份调查，记录了3次新派发。字节通过不能推断模型上下文、语义或最终原文包必然足够；未进入模型的详情不作为模型已见证据。

线索记录的查询键和原文读取键分开：`ref`用于反查，`readableUnitRef`用于读取它实际对应的完整单元。方法显示由已保存的声明类、方法名及参数类型组成，不把含Javadoc/注解的完整`signature`复制成导航标题；完整声明和正文仍在读回单元内。查询页保留真实的入口路径、处理方法、单元名称和字节数，不能只给U1/U2让模型盲选。查询到的Java方法或XML语句还给`lookupClueRef`，分别绑定实际方法键或语句变体，使首屏之外的单元也能继续反查。其它单元不伪造方法/语句线索。SQL空AST数量按实际记录披露；零个TABLE/COLUMN线索不等于没有表/列。

READING增加以下有限查询请求，落到现有Corpus方法，不新增公共查询CLI：

| 请求种类 | 执行目标 | 返回 |
| --- | --- | --- |
| ENTRY_UNITS | `entryUnits` | 当前入口的完整单元句柄页 |
| METHOD_USES | `methodUses` | 同一方法在其他入口的使用页 |
| STATEMENT_USES | `statementUses` | 同一语句的绑定/入口页 |
| TABLE_STATEMENTS / COLUMN_STATEMENTS | 现有表/列反查 | 实际AST命中页及解析覆盖限制 |
| 字面搜索、完整单元读回 | search/read薄适配 | 实际命中/未命中、原文或具名失败 |

查询键必须来自当前资料中的合法线索/句柄短键；字面搜索另有明确文本及范围，不接受可执行表达式。P2i第二轮实际用包内J1/J4请求METHOD_USES，历史程序以`ONTOLOGY_READING_QUERY_REFERENCE_INVALID`拒绝；本轮按[已读证据反查详细合同](cross-entry-reading-contract.md)只允许类型匹配的已读方法/语句包引用使用其经验证的原始键，直接RED→GREEN及保存响应的零模型回归已通过。**旧P2i仍失败，新代码尚未用产品模型完成这题。**同Service、同表和可选DDL只提供候选线索，不自动成为业务结论。offset/limit仍受配置和真实总数检查。一次决策可返回多项查询，但每项和合计均预检，不自动分页到全部读取；模型决定下一次需要哪页。

本次薄实现给`searchLiteral`增加稳定offset/limit，复用原字符串匹配和顺序，不新增搜索引擎。查询页记录真实total和未显示数量；offset大于实际命中数拒绝，等于total允许空的末页，不能产生负的未读数量。该越界边界由有效RED→GREEN覆盖。

短键`E1/J1/X1/L1`分别是入口、方法、XML、线索的局部引用，类别和页面/视图身份共同限定。Java保存`viewId/pageOffset + shortRef → 原身份/用法`映射；模型不复写64位ID。跨页相同`E1`必须通过对应视图还原，越界键拒绝。原始模型输出保持原样，归一化身份另存。

v2响应中的每个引用使用`{viewId, ref}`，不是裸`E1`字符串。`candidateEntryRefs`、`initialReadRequests[].unitRef`、`queries[].keyRef`和`retainedRefs`均遵循此规则；viewId对应已显示的导航/查询/阅读包，pageOffset保存在该视图记录中。首次读取请求含`purpose`，查询还含`kind/offset/limit/purpose`。只接受实际模型可见视图中的键，新查询结果有自己的viewId；映射和视图内容完整参与私有指纹。不存在的页或类别不匹配不得靠名字猜。

模型viewId使用13字节的`V`＋12位摘要短键；完整privateViewId、可逆映射和完整指纹另存。解析及派发前拒绝同一短键对应不同完整身份/映射的碰撞；重复完全相同的视图可去重，不误报碰撞。短键不是全球身份，也不能跨来源复用。固定R4零模型测量中，完整viewId重复使第二页封套达160,682字节，超过160,000上限。只减少重复导航身份，不删正文或提高上限；probe scope六页复测均通过，最大116,606字节，含Prompt、Schema及20,000字节输出余量。P2g中性scope首请求为110,179字节，不能混用离线与实际请求值。六页实际SURVEY已成功，但真实PRIORITIZE仍超限；后续阅读未执行。

**线索引用不是原文引用。**只看到`L1`不能在最终定义中把它当规则依据；进入EXTRACT/REVIEW的`evidenceRefs`必须对应实际读到的原文单元。

## 5. 选择一个可核对的问题，不按入口数摊材料

### 5.1 SURVEY提出问题，PRIORITIZE说明选择

SURVEY可以提出广泛调查方向；PRIORITIZE须将本轮选中项收窄成可核对目标。每项目标保存：

- 原调查问题及本次具体问题；预期核对一种对象身份、一个操作/规则族、一种计算口径或一个明确联系。
- 哪些导航/线索使它值得核对；当前还不知道什么，不预填正确答案。
- 为什么本轮先做它：证据可定位、目标可分开处理、与其它选题重复与否；不要求给虚构置信分数。
- `candidateEntryRefs`：可能相关的入口；它们不是必需阅读清单，也不是已发现业务成员。
- `initialReadRequests`：模型实际选择的少量完整单元及各自用途；可为空，表示应先查详情。
- 哪些目标或候选入口暂不处理，以及本次实验上限造成的延期。

问题数上限仍来自scope。当前PoC的2题是实验名额，不是全仓只有2类业务；未选问题由程序登记“本轮未选”，不等于不存在。任务类别仍按OBJECT/ACTION/ANALYTIC/RELATE分开；同题多类别不必共享一个巨大包。

入口名不决定内容。例如“账户相关接口”不能自动变成一个涵盖CRUD、账户身份、余额、资金流水与全部规则的提取任务。模型应明确本项究竟核对哪一个问题，其他目标延期或提出后续独立任务。

### 5.2 首批读取与补读

程序只执行`initialReadRequests`，**删除“对candidateEntryRefs逐一自动读取Controller正文”的行为**。选题阶段尚不能选择准确单元时，第一次READING发送问题、实际导航/线索和未读范围，允许没有正文；模型先请求查询/读取。复用同一个READING阶段，不增加独立分类或选材模型层。

当前协调器/readingCheck要求非空包；本次必须显式修改这条前置合同。v2的导航起步输入使用`readingPacket=null`、`packetId=null`，导航/线索视图仍有准确viewId。响应`retainedRefs=[]`，只能请求查询/读取并返回`NEEDS_MORE_MATERIAL`，或以具体缺口返回`UNRESOLVED`；禁止`READY_TO_EXTRACT`。取得正文后才构造真实非空ReadingPacket，不造占位正文绕过门禁。模型选择READY仍须通过实际原文/引用/容量检查。

后续READING看到完整已读原文、实际查询结果、用法和限制，返回：明确保留/移出、有限查询/补读请求、未解决项，以及继续或结束决定。程序执行来源和容量检查，不判断业务充分性。缺必要原文不能进入已审定义。

可以先只读公共Service、Mapper/XML或某个完整实现，不要求先读所有Controller。反查把相关入口保留在候选目录，只有为核对用途差异所需的入口才补读。为理解读过的材料不强制成为对象/操作成员。

### 5.3 容量失败不能通过删原文解决

导航/线索/搜索观察、完整单元、Prompt、Schema和审阅余量分别计量；包字节与模型上下文分别检查。先观察单元实际大小再选择，不按“每入口约10KB”估算。

首批较小不保证最后能容纳。首批已选包超限时，按该题保存round=0的具名INCOMPLETE及实际单元和大小，不向模型发送超限包，也不阻止另一合法选题。后续补读超限时保存当前包、实际决策、请求的单元及大小、未读范围；不丢已有成功记录，不派发超限请求。观察记录使用现有私有阶段保存器，原始PRIORITIZE/READING响应不改写。可提出更窄问题，但它是新的具名问题/任务身份，不能把旧任务悄悄改小后冒充原问题完成。

本次不设计一个问题多包摘要合并，也不改变完整方法/动态XML的原文合同。单个必要单元仍过大时，按[当前容量边界](material-preparation.md#9-容量保存和实际消费者)记录限制。正式紧凑正文/元数据投影及成本已由新材料设计单列，不以本页实验通过冒充正式接通。

## 6. 从实际证据看一条线索，不把人工核查说成程序输出

两份入口文件分别为`entry-6ab675398a5a4aa754a13b438ac1e2dae57d9013b905365e3c8cd75265c89276.json`和`entry-86540e0b60f0d3f4bd04435439d82aa64b3cdc67bb7d0bbefbf55dc470d3e924.json`，均在固定R4的`steps/05-business-flows`目录。共同方法的完整`methodKey`为`method:83bceab501734042a83495b3247ec0d9567599aa6a2fd9574e1f036717f3913a`；共同语句引用为`jshERP-boot/src/main/resources/mapper_xml/MaterialCategoryMapperEx.xml#com.jsh.erp.datasource.mappers.MaterialCategoryMapperEx.getListByParentId`。这些全局键用于Java核对，不要求模型复写。

这个例子可用于字段/反查测试，但通用Prompt不得写入这两个路径、类名、表名或期待答案。

## 7. 保存、匹配和读写链路

沿用`OntologyJobResultStore`，每次决策完整保存实际输入、输出、模型身份、线索/短键映射、查询参数/结果页、原文取回、容量和终态。原始模型响应不改写；程序的查询观察和身份归一化另存。

历史PoC决策保存为`ontology-decision-result-v2`；本次薄实现写私有`ontology-decision-result-v3`，SURVEY/PRIORITIZE/READING输入及响应Schema升v2。旧版本只能按旧合同查询；旧决策不能假装已经看到新线索而被复用。`ontology-job-result-v1`的EXTRACT/REVIEW结果仅在完整输入、映射、Prompt/Schema、阶段顺序和实际模型配置全部匹配时才可复用。目录、批次号和并发不代替语义匹配。

预期消费链：

```text
R4严格reader → Corpus反向目录/导航投影
→ DecisionRunner的SURVEY/PRIORITIZE/READING实际输入
→ ReadingCoordinator执行有限查询/读回并封包
→ TaskRunner的实际EXTRACT/RELATE/REVIEW输入
→ 私有已审结果；正式化后再接O1/O2/O3
```

公共O0–O3、scope/selection及最终四文件版本不因此再加一套查询发布合同。查询页和模型包是内部任务记录，不建设证据平台。
