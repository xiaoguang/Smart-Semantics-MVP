## 1. 结论与责任

Java 完成可机械确定的材料工作：读取、技术索引、范围保留、原文选择执行、去重、调用表投影、短编号、容量检查和保存。模型负责值得调查的业务和语义解释；新LINK由Java围绕已选锚点取得直接技术相关原文，不再强制模型逐项重选。宿主 Agent 不负责临时写业务摘要、补源码或改模型答案。下一版展开、编码和成本的准确规则由[连贯材料设计§5–8](coherent-link-material-design.md#5-输入与锚点程序知道什么不知道什么)拥有；下文v3/v4/v5说明各自现行或历史路径，不代表新v6已实现。

这里有两个不同动作：

- **选择材料**：锚点/范围可以由模型或用户选择，保存selectionMode；新LINK的技术扩展另外保存派生依据和完整纳入/未纳入范围，不能把Java机械取得所有选中原文说成全仓自主发现。
- **准备材料**：按合法选择准确取得源码并生成固定格式输入。无论谁选择，准备阶段业务模型调用数必须为零。

Java能报告技术缺项、实现大小和引用矛盾，不能保证知道所有业务必要材料。只读查询端，不能把建立端标为已核验。新LINK优先通过技术锚点扩展已有建立/映射候选；更多语义必要实现仍须明确提出并有处置，不能无限递归。存在、实际入模、语义正确分别检查。

## 2. 三种数据，不能混用

| 数据 | 内容 | 谁使用 |
| --- | --- | --- |
| 固定证据 | R4 完整入口文件、同 R0 原文、可选 schema evidence；原始工具限制全部保留 | Java 读取器、取材、反查、追溯 |
| 导航 | 入口、共同技术项、完整单元句柄、实际成本、未展示范围；没有模型生成的业务摘要 | 调查/阅读模型，用户检查 |
| 阅读包 | 当前问题、所选完整源码、必要参数/用法/限制，统一短引用 | 本次提取和同原文审阅 |

不把整份入口 JSON 发给模型，不让模型记住全部哈希；也不将导航或宿主 Agent 的理解替换成原文。私有映射/完整观察仍可以查询，移出模型输入不等于删除证据。

## 3. 准入及技术索引

### 输入

- 准确的 R4 index/receipt，按contracts §11.1严格读取历史`entry-evidence-v1`或本轮新增`entry-evidence-v2`家族，PREPARED_V1 来源。三个真实样例使用前端修复后新建的v2发布，不改旧文件。
- 从实际 R4 header 恢复的 R0 及有效排除范围。
- 用户明确配置的同 R0 说明/DDL 文件。不得从客户当前目录、旧 Activity、旧过程或聊天结论补证。

### 处理

1. 复用正式证据读取器，核验发布集合、来源和正文。来源不符/损坏先拒绝，不能等 Provider 启动后才发现。
2. 按已有技术身份建立 `方法→入口用途`、`语句变体→调用/入口`、`实际 SQL AST 表列→语句`、`前端单元→页面实例/请求` 倒排索引。
3. 技术身份与业务用途分开：同一方法正文只存一份索引，但调用实参、页面实例、入口分支分别登记。文本相同不等于对象同一。
4. 记录 SQL 空 AST、动态 XML、候选调用及地址条件；不补写 parser 未返回的节点。
5. 对合法完整单元建立字面搜索。搜索命中不是语义结论；搜索未命中不等于实现不存在。

### 输出及消费者

输出同源 Corpus、完整单元目录、引用映射、技术倒排和资源用量；调查/阅读协调器消费。当前 reader 会物化整个 R4 集合，不能称为已实现低内存随机读取。正式接线先测一次读取成本，不为每轮模型请求重开全仓，也不为此引入新数据库。

## 4. 导航如何减少模型自己找材料的负担

先给**具体共同项的线索页**，再给有界入口/单元页；不要只按 entryId 相邻顺序暗示业务相关。线索页按准确方法、语句或表列身份形成，记录哪些入口使用、哪些参数用途不同、实际扇出及限制。大组继续分页，不能把一个公共 Service 连到的全部入口当成一个业务。

保留独立全入口目录作为未分组范围分母。一个入口可出现在多个线索组，模型产生的问题可以重叠；正文不会因此重复加入同一阅读包。

共同表、同一方法、同字段写/读都是调查信号，不是批准关系的规则。字段写读只使用已保存工具结果；无法确定表限定、动态路径或作用记录时标未知，不新写 Java/SQL 数据流解释器。第一版不增加全入口两两打分平台；按需显示真实共同项、计数和未读范围即可。既有相似度 PoC 不能被解释成已审业务置信概率。

每个可读单元显示：完整正文 UTF-8 字节、默认紧凑投影字节、显式选取调用详情的增量、当前包去重后的实际增量。用同一个投影器测量，不使用原私有记录大小代替成本。导航成本不是 token 精确数，也不是保证整个 REVIEW 能容纳。

## 5. 阅读状态：已选范围不会随保留正文消失

正式协调器用一个不可变阅读状态，至少区分：

| 集合 | 含义 | 更新规则 |
| --- | --- | --- |
| `selectedEntries / selectedClues` | 当前问题已选择调查的入口/线索 | 只通过明确的范围决策增减；不能从已读单元反推 |
| `discoveredHandles` | 实际查询过的合法单元/详情入口 | 并集登记及来源可查；是否在下一屏展示由容量决定 |
| `readHistory` | 确实取得且进入过模型输入的单元及轮次 | 追加记录，不能将被移出的历史改为从未读取 |
| `activeUnits` | 下一次提取/审阅需要发送的正文 | 模型明确保留/移出/补读；移出不删除前面三个集合 |
| `requiredButUnread` | 已提出但尚未取得/超限的必要实现 | 必须由实际取得或显式收窄问题处置，不能因轮次结束清空 |

下一轮默认展示当前问题已选入口的小型目录，以及本轮查询观察；其余完整导航可再查询。财务保存端被读到，不能导致已选的查询端从候选目录消失。

查询、READ、保留、移出各有唯一职责。响应 action 数、分页总项数与轮次上限从同一个配置生成 Prompt、Schema 和执行检查；不再出现格式允许 8 项、执行器只接 2 项的矛盾。重复读取同一身份且内容不变时复用原文，不重新编号或丢导航；若状态没有任何进展，报告实际原因，不无限读同一单元。

首屏可没有正文；此时只能选择查询/阅读或明确未知，不能提取“已确认”定义。必要关系两端是否充分属于语义审阅；Java 只强制已申报的必要单元有处置。

## 6. 完整单元到简洁阅读包

### 业务联系优先的新投影接线状态

`formalV5` 已接通Corpus-v2/projection-rule-v3的正式运行分支，直接测试覆盖读取、冻结、EXTRACT/REVIEW、保存与重开。历史 `formal` v3 或 `formalV4` 的身份和输出不变；新客户模型请求的实际大小及识别质量仍待真实局部验收。

新模型投影使用 `EXACT_ROWS_WITH_USES_V1`：`callRows` 保存相同物理调用及全部投影事实；`callUses` 保存入口E、调用者S、可选调用S、目标S和原始顺序。公共行用包内C键查找，C不是原文引文。位置固定为 `[startOffsetUtf16,lengthUtf16,startLine,endLine]`；CT/CO字典继续保存完整候选及观察。只有实际调用者单元、保存调用观察、所选目标真实身份和公共行完全相同才共享，不按显示名称或位置相同就合并。

直接反例验证了两个入口共享5个调用时保留10个用途；同位置实参改变后增加独立公共行。解码恢复每个有序调用的全部所选投影和入口用途，完整源码单元及CT/CO逐字段等于历史v4，旧格式不改写；悬空行或乱序用途拒绝。这里证明的是所选调用投影可逆，不是所有未选私有记录自动进入模型，也不是实际小窗口验收已经通过。

### 模型可见合同（目标形状，不是现有公共 Schema）

```json
{
  "question": "当前一个具体问题",
  "taskKind": "RELATE",
  "knownObjects": [],
  "units": [{"ref":"S1","kind":"JAVA_METHOD","owner":"实际声明","symbol":"实际名称","text":"完整原文"}],
  "uses": [],
  "callContext": [],
  "limitations": [],
  "unreadRequired": []
}
```

`knownObjects` 是已审上游定义，不是源码，也不意味着关系已确认。每个用途/调用/限制引用包内原文或合法导航键。提取与审阅使用同一个冻结投影；审阅另外收到实际草稿和结构诊断。

当前 v3 包只让模型看到统一 `S1…` 原文引用；私有 canonical input 保存 `S→U→完整身份/入口用途`，以及每个进入`callContext`的完整保存调用、调用者、同入口已选目标和用途映射，并将它们纳入 packet identity。选中的 Java、Vue、XML 与 SQL 单元保持其完整保存内容。默认不展开普通调用 JSON：只有选中单元之间的已确认连接及 CANDIDATES、UNRESOLVED、QUERY_FAILED、NAVIGATION_CONFLICT 的逐位置限制进入 `callContext`；冲突或查询失败候选不成为连接。正常调用仍可经准确 U 读回。

一个`LOCATED`调用只可连接到与调用者同一入口下实际选中的方法。`callContext.selectedTargets`保留该调用的每一个这类目标及其`targetRef`、roles和`argumentAssociations`；单数`targetRef`/`argumentAssociations`只是首个目标的兼容便利字段，不能用它丢弃接口/实现等其它合法目标。调用的`actualArguments`保留为保存的紧凑对象。未知、候选、冲突和查询失败保留位置、状态和有意义观察，但默认不附入正常调用的完整私有 JSON。

正式 v3 投影固定 `callContextEncoding=EXACT_ATOMS_V1`。`callEvidence.targets` 是按完整投影原子 canonical 字节顺序编号的 `CT1…` 键对象，`callEvidence.observations` 同样以 `CO1…` 编号；每个 `callContext` 行只以有序、可重复的 `targetRefs` 和 `observationRefs` 代替原来内联的目标/观察。引用分别只在这两个字典中解开，空字典和空引用数组也保留。每行的入口、位置、状态、detail、实参、已选目标和完整原文均不变；字典不改变调用分类或选择。`CT`/`CO`只是包内技术元数据查找键，不是 `S` 引文、证据引用、对象/关系标识或 ontology 定义。

新增页上下文消费合同已实现，新增3项直接合同和合计52项受影响Corpus/packet直接回归均通过；独立复审确认并由一项两入口反例验证：同一真实上下文在不同入口使用时，每个入口保留独立的`FRONTEND_PAGE_CONTEXT` S记录和自身的请求候选/确定/仅覆盖关联，而私有映射仍回到同一个真实Corpus U。选择一个`FRONTEND_PAGE_CONTEXT`时，仅自动纳入该上下文在同一入口实际保存的完整源码单元，正文仍用S引用。观察和条件中的单元引用映射到这些S，不改写源码、表达式或参数。相关HTTP请求可以只保留原有紧凑请求投影和包内`requestRef`关联；其私有映射保留真实请求、上下文、入口及候选/确定性质。这个请求关联编号不是已读正文的S、不是Rule定义的R，也不能用于最终`evidenceRefs`。未选择的请求正文不因此自动入包，页面默认实例与组件实例仍分别保存；共属页面也不证明回调必然导致保存。包的实际展开正文和关联映射共同参与成本及身份计算。

跨入口的同一页上下文不能因U相同而合并其用法：模型包为每个实际入口保留独立上下文S，私有映射仍回到同一个真实Corpus U；各自的请求候选/确定/仅覆盖性质、条件和实例不互相覆盖。完整前端源码正文仍可以跨入口只保存一次。此规则只区分上下文用法，不新建短号体系或重复发送整份源码；对应两入口反例及53项直接边界已通过，有限独立复审的设计与质量结论均通过。客户固定源码的具名新R1/R4运行和本体真实质量验收仍属于第9步。

### 默认保留

1. 已选完整 Java 方法、前端函数/模板事件完整单元、Mapper statement 和所选依赖原文。正文不截尾、不用业务摘要代替。
2. 本次页面实例、事件绑定、实参/形参、未传参数、HTTP 原表达式及候选/确定性质。共享组件不混实例。
3. 连接选中单元所需的调用位置、实际目标/候选、参数对应；同一目标声明只出现一次。由保存的调用记录投影，不能按同名自行连边。
4. 所选方法中会影响目标可信度的歧义、未知、查询失败等**逐位置限制**，以及明确缺少的 helper 正文。不能只发“存在 3 条警告”而丢掉对应调用是什么。
5. 已选 XML 的动态条件/循环、include/resultMap 依赖、SQL 文本/已有结构与 PARTIAL 限制。原文不能被某次静态 SQL 副本取代。

### 默认留在程序侧

长 ID、哈希、回执、宿主绝对路径、运行/鉴权信息、重复技术声明、重复调用树、完整来源对象、未选单元和与本问题无关的技术明细。保存这些内容的地址、移出原因和读回句柄，用户/模型可以要求查看。

**不默认把所选方法的所有所属调用 JSON 附入输入。** 调用表达式本来就在完整源码中。模型需要某个 helper/参数绑定时，请求相应完整单元或紧凑详情；Java 读取。正常外部边界可汇总，未知/矛盾必须定位到调用点，不能汇总为“没有影响”。

Java 的默认剔除是按字段类别和已选择单元关系，不是读中文猜“这个业务没用”。每次投影保存纳入项、移出项及规则版本。对本问题仍依赖但未提供的 helper，只能标未读/未知，不从方法名称推断它正常返回、抛异常或计算顺序。

财务 PoC 的 10 单元、采购 PoC 的 17 单元是实际人工选择结果，不是程序默认数量。正式输入可以更小或更大，没有“每入口 10KB”“70KB 必然够”之类规则。

## 7. 短 ID 提前提供，不替换稳定身份

采用两层身份；不把完整哈希切前几位当唯一键：

- **保存身份**：既有 entryId/methodKey/statementRef、来源版本和源码范围继续是内部准确身份。
- **证据接口别名**：打开资料集时即分配 `E1/U1/K1` 等短键和可逆目录；调用者/模型不用等正文封包才获得短键。按稳定原身份排序分配；同一资料集重复打开映射不变，版本变化重新分配，禁止跨版本混用。

别名作用域由 CLI/请求记录携带；模型只返回当前任务合法短键，不要求抄长 `viewId`。导航分页不重新从 E1 开始编号；每个任务的允许值按**实际已展示**集合生成。程序知道当前资料集/轮次，因此不让模型承担回填作用域身份的工作。

别名目录采用精确键，不按显示名称分配：

| 键 | 对应身份 | 映射多重性 |
| --- | --- | --- |
| E | Corpus内完整entryId | 一入口，含其所有已保存用法；不是一Controller |
| U | 单元kind＋原身份＋明确变体＋来源文件/范围＋内容摘要 | 一份确切正文；所有入口/页面实例用途另列，不因正文去重合并用途 |
| K | 线索kind＋准确lookupKey及已知限定 | 一个技术共同项，指向所有合法U/用途；结果可分页，不默认把变体并成一份正文 |

方法保留声明/来源身份；XML语句保留namespace/id/databaseId、资源路径及内容变体；同名不同模块/文件不能折叠成同一U。K无法唯一限定时保存候选与未知，只能导航，READ必须选确切U，不能静默取第一个。DDL未解析表列不生成假U/K；来源位置未核实时使用完整文件单位。排序按这些完整键；同Corpus的枚举顺序变化不改变短号。

阅读包再提供统一 `S1…` 原文引用，只保存一次 `包→短键→证据接口别名→稳定身份/用途` 映射。这层映射仍必要：跨入口原文去重、同一单元不同用途、多个资料集的 U1、同题补读后冻结的最终集合都可能不同。不是重新解决“哈希太长”，而是确定**本次模型到底看到哪段原文**。

入口E、完整单元U、技术线索K、本次原文S分别命名，K不与关系定义L混用；对象/关系/操作/维度/度量/指标用O/L/A/D/V/M。不得用E1当业务对象身份。不同任务的O1虽可同名，输入目录会重新分配唯一可见键并保存原任务版本；原任务S1不自动传到下一任务。

旧 R4 不改写、不重跑取证。先在现有证据读取接口/Corpus 输出别名目录；如果以后要把别名也随 R4 导出，另按新生产版本保存旁路目录，历史 v1 仍严格读取。短别名只改善接口和输入，不宣称建立了新的业务关系。

当前别名目录按完整 entryId、unit kind/originalId/完整 canonical 内容和线索 kind/lookupKey 排序。相同正文仅在这些 U 身份相同才去重，`unitUses` 保留每个入口用途；XML 与 SQL 变体保持各自的准确可读 U，bare 变体读取继续拒绝。目录以私有 canonical mapping 保存，不能把当前 `EntryEvidenceReader.Directory` 的 index 摘要误称为正式 R4 receipt/source 准入。

材料模块的`sourceIdentity()`是内容身份，不是正式O0准入身份。正式任务上下文已分别保存`corpusIdentity`（由运行器核验R4/R0、范围、回执和配置后绑定）及`contentSourceIdentity`（本次Corpus与阅读包的内容身份）。任务入口检查阅读包内容身份与后者一致，先前已审结果的正式Corpus身份与前者一致；不能直接比较两个层级不同的字符串，也不能改写旧PoC身份冒充正式准入。绑定只在程序侧保存，不要求模型复写；显式正式运行和历史R4→O0已验证该接线，当前固定样例O0–O3及公开查询也经过实际执行；不据此证明真实自主发现或全仓范围。

SQL AST 表/列线索保存 hash-qualified SQL `unitId`，字面搜索也返回该准确句柄，因而同一 `statementRef` 的多个 SQL 分析不会在 U 读回时退化为 bare 语句。每个 K 同时保存全部可读 U 和其入口用途；`clue()` 的单个展示项不是 READ 目标，调用方必须通过 K 的完整用途集合选择准确 U/E。Corpus 构造期冻结每个单元的 canonical 内容、入口描述和限制；线索目录仍会按 entry 读取，优化去掉的是此前为每个 U 重开和重新编码整份 entry 的重复工作，并非承诺每份 entry 总共只解析一次。它不是可失效缓存，也不改变旧 R4 正文或其准入含义。为了保持 legacy v2/PoC packet identity，`read(entryId, SQL_ANALYSIS, statementRef)` 在该 bare 引用未歧义时仍返回 bare `statementRef`；formal aliases 和显式 `sql:` 句柄继续持有 hash-qualified 身份。

formal v3 的前端请求投影保留页面、实例、请求表达式、参数、调用/封装位置和源单元语境，但不向模型发送 wrapper 的 hash 或私有图 ID；legacy v2 投影不变。异常调用上下文保留候选显示名、roles 和原因，却不制造 `targetRef` 连接。

## 8. DDL：新增可选证据种类，不强制新增 R5

首版字段、完整文件准入、真实SQL表使用的候选关联和保存后消费边界见[schema-evidence](schema-evidence.md)。有限实现及正式R0/R4 fixture的保存、重开、O1/O2消费已通过直接测试；不宣称固定客户dump全部解析或模型已读。

最新成功 PoC 没有 DDL；同 R0 的 SQL 文件只是已经保存的原文。表结构可以补身份/类型/nullable/约束依据，不解释业务顺序、数据实例或执行结果。

首版设计：用户在 `prepare-ontology` 明确配置同 R0 的 schemaSources。Java 使用项目已有 JSqlParser，解析它实际支持的 DDL；O0 同运行可选保存 `schema-evidence.json`。这是可追溯的**结构声明证据**，不是新数据库 Agent，也不是每次必做的第五个技术命令或必需 R5。R0–R4 的含义保持不变。

该文件包含：来源/有效范围、parser 实际版本、每文件处理状态、解析出的表/列/类型/声明主键/唯一约束/外键/索引、准确原文绑定和未支持范围。依据分别标 `DDL_DECLARED`；代码里的用途仍标 `CODE_OBSERVED`，不得混成同一种唯一性证明。

仅做成熟 AST 的有限字段投影，不另写 SQL/DDL 解析器、分号切分器、方言修复器。整份 dump 解析失败时保留原文和诊断，不宣称“全库表结构已取得”。可以读取用户明确提供且同源可核验的完整定义单元；无法可靠定位的 AST 元素只能引用完整文件，不伪造列级范围。数据 INSERT 不默认作为生产实例或进入本体模型输入。

整份失败且没有独立定位时，未解析覆盖只标文件级UNKNOWN；parser错误中的行列保留为工具诊断，不自动变成准确R0语句/列范围。用户明确选择的定义范围必须逐字核验同R0，选择来源记EXPLICIT，不变成“自动全dump解析通过”。

普通索引不是外键；外键声明不证明客户线上已启用/执行约束；没有声明不证明业务没有联系。同一表可承载多对象角色，一对象可跨表。不强迫有 DDL 才能识别本体，缺库级唯一性依据写具体未知。

未来如果确实需要独立缓存/重跑 schema 分析，可以另立并行 RD 操作；本设计不预建该 CLI，也不因为 R0 中有 .sql 就自动调用 parser 或扫描数据库。

## 9. 容量、保存和实际消费者

每次发送前检查实际 Prompt、Schema、导航/原文、已审对象、实际草稿、输出余量。先离线检查最坏合法 REVIEW 余量；草稿返回后再核对实际封套。已有计数器适用则复用，只有字节/保守估算时明示方法，不把字节当 token。

容量是配置能力，不是业务规则。先去重复、去无关字段、拆独立问题；必要完整单元仍超限则报告 `UNIT_TOO_LARGE`，可选择更窄问题或改变配置。首版不自动语义切割巨大方法、拼多包摘要、静默换模型或提高窗口；这些都没有被辅助 PoC 证明。

v3 记录四个实际字节值：已选完整 canonical 单元的 `fullSourceBytes`、最终模型 JSON 的 `modelInputBytes`、私有 canonical input 的 `privateInputBytes`，以及显式选入 `JAVA_CALL` 详情的 `explicitCallDetailBytes`。它们都是 UTF-8/canonical 字节测量，不是 token 估算，不附带固定 70KB 保证；单个必要完整单元超过 `maxUnitUtf8Bytes` 直接报 `ONTOLOGY_UNIT_TOO_LARGE`，绝不截断。

冻结阅读包后，保存准确映射、完整私有观察、投影规则、实际模型输入及 fingerprint；EXTRACT、REVIEW 均引用同包。正式 task key 同时绑定私有 packet identity、实际 `modelInput` 和 `callContextEncoding`，所以仅投影/字典格式改变也不会复用旧任务；这不改写私有 packet identity 或 legacy v2 形状。改变必要材料、Prompt、Schema、模型绑定或范围都产生新任务；输出目录/runId 变化本身不改变内容身份。成功/失败原始响应不可覆盖。

Corpus 输出给识别/关联协调器；协调器输出给 typed task runner；已审结果给确定性 Publisher。宿主 Agent 只通过 `inspect/artifact` 获取这些实际产物，不手动复制片段补给模型。已知缺项保留到最终 coverage，不因投影后看起来简洁而清空。

历史v3采购真实包318,608字节，其中调用上下文和证据147,043字节；该数字不是新v4请求的成本。新v4已实施确定性去重、紧凑调用字典、准确同题对象目录和私有字段移出，并通过完整正文、逐位置用途及限制可逆的直接测试；不裁剪完整选中实现。当前三个样例全部EXTRACT/REVIEW实际成本已经测量；采购最大容量检查额460,216字节，不冒称token兼容，实际数值见验收记录。[具体测量与规则](evidence-stability-and-failure-isolation.md#4-java-如何形成简洁但完整的实际输入)。

统计权限helper的正式补读consumer已接通；直接测试证明保存的候选声明与同R0完整正文进入实际scripted EXTRACT/REVIEW，原未确认调用限制保持。固定客户新O0和实际O1/O2已保存；统计实际EXTRACT/REVIEW均收到完整helper和原限制，正文逐字匹配R0。接口存在或人工读过都不是入模证明。材料确实完整后模型仍误读，另列模型质量；不能因模型可能幻觉而放过材料缺项。

### 9.2 完整辅助单元补读的最小接线（实施合同，直接测试已验证）

补读只使用R4已经声明的准确后端索引及同源R0，不另找客户工作目录。程序经现有`JavaCodeIndexReader`重开R4所绑定的R2发布，按其原owner、receipt、snapshot及内容身份核验；该Reader恢复的是已保存声明，不启动JDT。声明中的准确源码路径和完整范围可用于R0正文读取，不能从类名拼路径或用字符串切函数。

R4已经保存的未确认导航观察可以作为寻找完整声明的线索。程序只按实际保存的声明身份/显示身份和来源范围形成可反查候选；无唯一可靠单元边界时不得静默取第一个方法。候选正文被选中、完整读入，也不证明原调用已经定位：原`NAVIGATION_CONFLICT`、`UNCONFIRMED`、`targets=[]`及入口用途仍保存并入模。补读的用途是让模型阅读被明确选择的实现，不是补造调用边。

每个新补读单元记录R2声明/发布、R0文件摘要、源码路径、完整边界种类及范围、实际正文和入口用途；冻结v4映射包含这些来源。没有可靠方法边界但存在准确合法路径时，可以读取该完整文件；没有合法定位、来源不符、排除或损坏时列具体缺项。不得粘贴人工节选或从方法名推断返回/异常行为。

这个变化产生新的Corpus投影身份和O0记录。旧Corpus按其保存规则恢复，不用当前补读算法重新构造旧别名。短号只在准确Corpus内稳定；验收选单若需从旧Corpus迁移，Java必须按完整旧单元身份核对新映射，不能把旧U字符串直接当成新U使用。新冻结包和模型投影独立写v4，旧v3继续原读取；完整原文、用途、限制及映射的变化都参与任务匹配。

版本选择不增加配置开关。使用本次v2本体policy的`prepare-ontology`写明确的`projectionRuleVersion=ontology-model-projection-v2`；原v1 policy路径保留`ontology-model-projection-v1`及原v3包。重开时必须按**保存的**规则分派：v1恢复原未补读Corpus，v2恢复准确R2/R0补读单元及v4表达，未知规则拒绝。不能因为当前目的policy较新，就把旧O0换成新别名或新正文。该规则及准确来源、别名参与Corpus身份。

O0沿用现有Corpus的内存单元和内容摘要机制：零模型读取R4已有源码引用，以及能够唯一核对的已保存R2候选声明，从同源R0取得完整正文并计算单元身份。它不扫描目录补造新引用，不重新解析Java，也不把整个R0复制进每个入口。新O0发布身份、来源和别名映射；正文由既有证据存储保持，重开按同一明确规则重建。只有阅读任务明确选中的单元进入冻结包和模型请求，未选正文不因存在于Corpus而默认入模。成本检查针对真实冻结包及完整请求。

同一v2入口的已登记单元必须保留同一份已保存`limitationCounts`和入口描述。补全既有`SOURCE_REFERENCE`时，程序先取得该unit的先前记录，再仅替换正文并原样继承其限制和描述；找不到先前记录即拒绝，绝不先写入空元数据。新增补读`JAVA_METHOD`时，程序只从该入口既有单元取得这对元数据，并要求所有既有值完全一致；缺少、分歧或合并计数都拒绝。这样`entryLimitations`仍是准确R4入口限制，而不是补读路径制造的空限制。该约束只影响新v2准备/冻结包和任务匹配；旧O0、R4、R0及v1恢复均不改写。

这个方案不新增惰性读取、描述符或源码缓存平台。现有U编号按完整canonical单元内容摘要区分，因此O0阶段先读取和核对这些已登记单元，与“仅向模型发送被选中的材料”是两个不同动作；不能把前者误写成已经提交模型。原v1仍按原metadata-only规则恢复，新规则不得改写旧O0。

验收须同时证明：辅助正文实际出现在EXTRACT和REVIEW、两阶段使用同一冻结包、补读前的可疑调用仍为可疑、坏模型稿不能修改补读正文；仅能在程序侧查到文件不算入模通过。具名统计helper的保存声明与R0已核实；正式source/runtime直接测试验证完整正文、来源映射、保存重开及实际scripted请求。客户新O0已经零模型准备，三例实际输入已核对；六个O1已审、O2两个已审/一个拒绝，四文件部分发布仍明确INCOMPLETE。本页不将材料核验写成模型语义零错误。

重开保存的R2大索引采用原技术读取器的既有资源上限；不能误用本体模块64MiB上限去拒绝原技术路径允许的索引。固定R2实测132315924字节，原技术256MiB读取器可重开。这个调整只用于准确上游技术索引，不扩大模型输入、单元或本体发布限制。

### 9.3 业务联系材料v5（现行已交付，覆盖和容量部分通过）

v5行与用途解码、正式请求、发布和重开已有验证；客户局部批次已结束，准确边界见正式验收。未形成完整采购链，容量目标部分通过。新LINK材料v6另按[详细设计§6–8、§12](coherent-link-material-design.md#6-java连贯材料算法)实施，不在重开v5时换算法，也不把薄实验当作v6正式验收。

- **共同项与分支：**复用准确方法、Mapper语句、已保存表列和前端用法倒排；新增CONTROL_REFERENCE类K读取保存controls，不解析新语言、不用同名字段假造绑定。模型从具体线索选择一处交接，Java取得完整建立/保存/使用候选，不一次塞入全生命周期。
- **先选调用再去重：**沿用v4的可靠连接、显式选择和逐位置不确定性规则；未选正常私有调用不默认入模。被选调用按物理身份及全部非用途字段精确比较，用callRows保存共同行、callUses保留各E/调用者S/目标S/用途和原顺序。候选、参数、状态或展开观察不同则不合并。解码恢复压缩前已选投影逐字段一致，不要求无关私有记录进入模型。
- **固定列及字典：**callEncoding=EXACT_ROWS_WITH_USES_V1，site列顺序为startOffsetUtf16/lengthUtf16/startLine/endLine；CT/CO仍为机械字典，不是原文S或业务对象。完整字段及示意见[编码合同](business-link-first-design.md#83-跨入口调用精确去重)。每个实际位置的限制必须可解码、可反查。
- **页面上下文：**复用当前context→source的路径/摘要/完整范围/kind匹配，新增source→context反向索引，不复制薄实验的sourceUnitId字符串比较。新Corpus同时读取R4已保存的PAGE_CONTEXT_COVERAGE及完整来源单元；与入口已有物理单元准确重合的页面上下文可作为候选用途，不要求其HTTP请求已匹配。未匹配请求仍为COVERAGE_ONLY/NO_MATCH，无请求页面仍无请求，不改写R4或制造HTTP关联。只展开初始明确选中单元的直接上下文及其完整来源，不递归扩展全部共享页面。同一共享源码的不同页面实例分别保留；多候选让模型选用法，缺观察标未知，不重跑Vue parser。
- **准确成本：**导航增量和EXTRACT/REVIEW使用同一投影，REVIEW再加实际草稿和准确对象目录；冻结和请求都保存完整成本。相同材料才比较压缩收益；bytes不当作token，没有70KB保证。
- **K编号的实际含义：**v5冻结材料保存`visibleClues`，每项包含准确K、种类、实际共同项/控制表达式、总用途数和本包内的E/S用途。模型不只收到裸K编号。重开按准确Corpus重新核对这些字段和映射，不能在保存后给同一K换解释；旧v3/v4材料不增加字段或改变任务身份。
- **来源与版本：**O0写Corpus-v2/projection-rule-v3，冻结包与模型输入写v5；来源R4/R0不变。新规则影响别名/任务身份，旧v3/v4包严格恢复，不在重开时用新算法改造旧结果。

旧薄实验的52单元投影减少23.9%，两题仍约140–166KiB；这些数字不是正式v5收益。新直接测试已验证精确callRows/callUses恢复、初始选中前端单元的直接PAGE_CONTEXT反查及scripted正式请求保存重开；客户实例是否实际入模仍须检查真实请求。准确结果见[正式验收状态](../../supplements/ontology-business-link-formal-acceptance-20261005.md)，不能只凭字段存在或字节下降宣称完成。相关工作由[backlog32](../../supplements/implementation-lessons-and-followups.md#32-业务联系优先与已审对象细化接线)跟踪，第28项硬约束继续有效。
