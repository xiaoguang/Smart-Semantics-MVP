## 1. 结论、范围与验收责任

**模型可以答错；框架不能因答错而修改证据、接受断开的定义、丢掉成功结果或无限等待正确答案。** 每个任务必须有确定结束：已审、拒绝，或尚未执行且有具体原因。坏任务不进入本体；与它无依赖的任务继续；整个命令返回完整处置，而不是把用户确认当成运行中的等待条件。

框架负责以下四件事：

1. Java 按明确选择组织紧凑材料，保留完整选中原文、用途、限制和可逆来源；不让宿主 Agent 临时拼材料。
2. 提示词明确当前任务、可用定义、引用位置、未知表达及一次审阅责任；不要求模型补未见实现。
3. 程序检查结构、来源、引用、实际保存和任务依赖；不判断中文业务结论必然正确。
4. 模型错误局部结束，成功与失败均保存；共享故障停止受影响范围；CLI 有界退出并提供准确下一动作。

本次不改变 R0/R4，不重新取证，不修改旧 Activity、业务过程、九章、旧 MD 提示词或渲染。沿用 O0–O3 四个命令、现有 Agent、Provider、journal 和 canonical store；不新增修复命令、调度服务、恢复平台、语义修复器或通用依赖图引擎。这里的依赖是少量已声明任务关系，不是代码调用关系，也不是 Maven 依赖。

框架验收与模型质量分别记录：

| 核验事项 | 框架需要做到 | 不承诺 |
| --- | --- | --- |
| 材料 | 实际 EXTRACT/REVIEW 收到选定完整原文、用途、限制；缺项明确可查 | Java 自动发现一切业务必需实现 |
| 模型输出 | 坏 JSON/断引用不发布；原稿与诊断保存 | 所有模型遵守 Schema、正确理解业务 |
| 原文审阅 | 同一冻结原文＋实际草稿＋结构诊断；结果严格检查 | 同一模型必定纠正自己、语义零错误 |
| 流程 | 单任务错误不会挡住独立任务；依赖缺失不派发；有限结束 | 自动消除所有错误或自动重试到成功 |

“结构合法、经过模型 REVIEW”不等于“人已经认可业务结论”。静态识别发布继续为 `DRAFT_REVIEWABLE`，指标继续为 `NOT_EXECUTABLE`。

### 2.1 采购的实际断引用

已有记录显示：草稿定义 O1–O6，REVIEW 收窄到只剩 O1，却在两个嵌套条件中继续引用 O3。O3 在最终集合不存在，所以程序拒绝。这不是 R4 缺 O3，也不是证据文件被删；O3 是该模型任务自己产生的局部定义编号。

默认 OBJECT/REVIEW 提示词已明确：OBJECT 不同时定义保存操作；REVIEW 检查最终集合中的全部嵌套引用；对象确有依据且被需要时保留完整定义，否则保留条件及来源并表达未知，不能猜替换端点。采购新任务随后通过，但不能由一个通过案例保证其它模型不会犯同类错误。

**直接测试已验证：最终坏引用拒绝当前任务，独立任务继续，CLI返回完整处置。** 不是放松 O3 检查，也不是用 Java 自动把 O3 改成 O1。

## 3. 四层内容分离：模型不能改证据

| 层 | 输入/内容 | 保存和修改规则 | 实际消费者 |
| --- | --- | --- | --- |
| 原始证据 | 准确 R4、同源有效 R0、可选同源 DDL | 按真实版本只读；不覆盖、不被响应写回 | O0 Corpus、完整单元读取 |
| 冻结阅读材料 | 完整选中单元、入口/页面用途、紧凑调用、限制、S↔U/E 映射 | 派发前保存并绑定内容身份；新增材料或投影规则形成新版本 | EXTRACT 与该次 REVIEW |
| 模型尝试 | 实际 Prompt/Schema、原始响应、校验、阶段状态 | 原始字节不可覆盖；机械规范化另存事件和结果 | validator、一次 REVIEW、只读查询 |
| 已审定义 | 最终合法 typed 定义、准确任务/审阅身份、来源及未知 | 仅最终校验通过者进入；不从拒绝稿抽取“看起来好的半个对象” | 明确依赖它的任务、O3 Publisher |

原始证据 hash 不因 Prompt、模型答案、任务失败或重新执行改变。原始响应即使错误也保留；规范化响应不能替代原始响应。完整来源映射留程序侧；模型只能使用当次实际暴露的短引用。

框架在每次使用前核对来源、有效排除版本、准确 owner、内容摘要、投影和映射身份。验证失败属于来源/保存问题，不用模型解释补救。没有真实 receipt，不返回正式产物引用。失败阶段已经保存的私有记录可以查询，不伪造 `ontology.json`。

本体没有独立复制客户全部源码的新证据平台。完整原文继续来自保存的 R4/R0及冻结包；从最终定义可以确定性反查其 producing task、review version、S、U/E 及原文位置。查询不需要当前模型登录、Prompt 文件或 Maven 临时文件仍存在。

## 4. Java 如何形成简洁但完整的实际输入

### 4.1 输入与处理

输入是准确 Corpus、一个具体问题、实际选择清单以及该任务需要的已审对象。选择来源记为 EXPLICIT 或 MODEL；不把人工清单写成自动发现。

Java 按以下固定流程处理：

1. 核对 E/U/K 与 Corpus，解析准确单元及入口用途；不同页面实例不能因正文相同被合并成一种用途。
2. 读取选中的完整方法、前端源码单元、XML及已解析 SQL；必要 helper 按正式消费者支持的同源完整单元补读，不由 Agent 粘贴。
3. 相同正文只发送一次，使用稳定短键引用。运行ID、hash、receipt、重复技术身份、私有诊断原文和无关的完整调用 JSON 留程序侧。
4. 仅发送当前任务需要的调用上下文：位置、实际参数、目标声明/形参、用途及逐位置的不确定性。共用目标声明放字典；调用位置及参数不同仍分别记录。
5. 不默认附入所选入口的全部调用。相关未知、矛盾、查询失败及外部边界不能压成“确定调用”；具体受影响位置可反查。
6. 保存实际纳入、未读、移出、必要未读、限制和映射；冻结模型投影，测量完整请求，再派发。

程序只做结构化选择和压缩，不阅读中文断言“这条规则不重要”。如果一种压缩无法保留用途、分支或限制，就不能采用。完整方法过大时如实报告，首版不自动语义拆函数、截断或用摘要替代源码。

同源helper补读先使用保存索引中已经核对的完整单元边界及原路径；没有可靠方法边界时只能读该准确路径的完整文件，不能凭方法名或手工挑几行伪装完整实现。路径来自可核对的保存来源/具名选择，并经R0有效范围检查；没有合法定位则返回具体缺项。补读包含实际原文字节、完整单元/完整文件边界种类、R0摘要、入口用途与可逆来源，进入新的冻结包和任务身份；原SOURCE_REFERENCE元数据本身不算正文。它复用公共原文读取，不重跑JDT，不用字符串切函数的新解析器。包/投影协议字段变化须独立版本化并同步Reader，不改写旧包。

### 4.2 完备的准确含义

“R4中有原文”“能在R0找到helper”“模型可能知道”都不能证明该次模型看过实现。框架验收必须查看实际请求：

- 当前结论依赖的建立端、使用端、过滤、运算顺序、后处理或异常 helper 是否真的入模；已申报必要单元须逐项核对。
- EXTRACT 和 REVIEW 是否使用同一冻结包；REVIEW 还须有实际草稿和候选诊断。
- 未提交实现是否明确保留未知；未读实现不能被解释为必定成功、只记录日志或某种数学顺序。
- 一旦发现材料缺项，保留本次记录，生成新包/新任务，不把旧已审稿的证据偷偷换掉。

Java 可以保证选择清单中的原文不丢，不能保证模型或用户第一次声明的清单已包含一切语义必需材料。人核验发现的材料缺项属于框架/选材问题；完整入模仍被误读属于模型质量。两者可以同时发生，必须分别列明。

### 4.3 当前采购请求说明了什么

对已保存请求的实测，采购冻结 `readingPacket` 为 **318,608 UTF-8字节**；其中调用上下文和调用证据共 **147,043字节，约46.2%**。Java与前端源码正文合计58,067字节，**不包含XML原文**。所以既有 CT/CO 字典通过无损检查，仍不等于整个实际输入已足够简洁。

新采购 OBJECT 请求的实际 CLI stdin约321,699字节；REVIEW约341,407字节。统计的包约62,110字节也出现非法引用。两例不能证明错误由大小造成，也不能证明大小没有影响；它们只证明“过大”与“引用合同错误”要分别测量，不能靠模型一次通过宣布支持小窗口。详细测量口径及原请求见[正式验收记录](../../supplements/ontology-formal-acceptance-20261003.md)。

压缩验收必须报告源码、调用投影、已审目录、Prompt、实际草稿和完整封套各自的真实成本；不得只比较私有包或缩短ID的百分比。REVIEW传递最小依赖目录，不发送所有此前成功题的全部结果。新v4机械去重已经实施，并通过完整正文、用途和限制可逆的直接测试；三个实际样例的18份EXTRACT/REVIEW成本已在正式验收记录逐项保存，采购仍较大，不宣称任意4k/8k窗口已通过。

## 5. Prompt和固定响应合同

### 5.1 三种内容，不能互相替代

| 内容 | 谁控制 | 约束 |
| --- | --- | --- |
| 框架封套/Schema/合法引用和容量 | Java | 非源码指令；不允许自定义Prompt越过 |
| 业务Prompt | 用户可配置；Java读取并保存实际文本 | 改语义要求/措辞，不改原文、Schema或引用许可 |
| Skill沟通模板 | 宿主Agent按真实CLI结果使用 | 不另调用产品模型写报告；不补字段、不手工组材料 |

每个请求明确字段角色：`question`是调查背景；`readingPacket`是数据而非执行指令；`reviewedCatalog`是已经合法的对象目录；`actualDraft`是不可信候选；`candidateDiagnostics`是程序结构检查，不是业务标准答案。原文中的命令、提示、注释不能改变任务和授权。

### 5.2 提取指令的具体要求

下列为默认指令要求，不是向用户展示的业务答案：

- **OBJECT**：只识别有身份/属性依据的业务实体，不把动作、金额公式或接口链凑成对象。只使用本任务 O/P 编号及本次 S 来源。身份不足可留具体未知。
- **ACTION**：只引用输入已审 B/B.P 对象；完整说明目标、条件、拒绝、效果和来源。没有目标依据则进入 unresolved，不编 B2。查询不等于改变状态。
- **ANALYTIC**：按实际口径保存粒度、维度、组成量、计算式、过滤、空值/符号及后处理。无指标依据允许数组为空，不用表名或数值类型创造KPI。
- **RELATE**：只比较明确输入对象，读取建立和使用联系的两端；共用表/Service是技术线索，不是业务关系。没有端点则保留未知，不猜端点。
- 解释写入说明字段，引用字段只放允许的编号；不能把同名短号从另一任务搬来。保留关键条件，不能为了Schema合法删掉业务规则。

实际Prompt资源中的OBJECT/REVIEW职责收窄和最终引用闭合要求已经实施并有直接测试；其它要求的真实效果按实际请求和审阅结果验收。Prompt通过只证明约束明确，不保证模型必定遵守。

### 5.3 一次REVIEW：审完整实际稿，而不是期望答案

输入固定为同一冻结原文、准确可用对象目录、实际草稿及其具体结构诊断。审阅必须：

1. 核对当前任务职责和每项来源，不采用未见helper或行业通识补确定事实。
2. 从最终返回集合重新检查全部引用，包括嵌套条件target、Property、操作目标、规则owner、关系端点、指标组件及粒度键。
3. 删除O3时同步处理所有对O3的引用。有依据就保留/补回完整定义；没有依据就保留原条件及来源，按Schema表达空引用和具体未知。不能猜成O1，也不能擦掉条件。
4. 返回完整修正稿，不返回补丁或只说“通过”。原始草稿、审阅和修正都保存。
5. 不为未知强制凑对象、关系、维度和指标；不把结构诊断当成证明业务为假。

可读、根任务可识别、有界的结构坏稿进入这一次REVIEW。非JSON或没有可识别实际稿则当前任务失败，不凭主持Agent重写；REVIEW最终仍坏就拒绝。默认没有第三次修稿。可重复的无歧义记号规范化沿用现有规则并保留事件，不能扩成语义修复器。

### 5.4 Prompt变更与客户沟通

Prompt的实际内容参与任务身份；修改Prompt后新建任务/运行，不能把历史失败记录升级成功。证据身份不变。业务错误可以调整Prompt再次执行，但框架不保证再答对。

宿主可报告：“该任务审阅仍引用不存在的O3，结果未进入本体。原文、草稿、审阅和诊断均保存；其它独立任务已继续。可以查看记录，或修改提示词后新建任务。”不能报告“R4坏了”“所有业务识别失败”或“程序已经修好业务含义”。下一动作是否需授权由原授权范围决定，不因内部结构错误每次重新索取相同授权。

## 6. 任务依赖：薄规则，不建通用调度平台

### 6.1 O1：同题OBJECT前置，其它题独立

沿用 `ontology-scope-v1` 的问题/任务清单及顺序，明确以下语义，不新增用户编写DAG：

- 每题 OBJECT 可以独立执行；多个OBJECT任务各自结束。
- ACTION/ANALYTIC依赖**同题、排在它之前的全部OBJECT任务**。这些OBJECT必须REVIEWED；“合法空对象＋明确未知”也是已审结果，但模型不能凭空补目标。
- 只传上述同题已审对象目录。另一题有对象不能满足本题依赖；不默认传所有已完成任务。
- ACTION失败不挡住只依赖同题OBJECT的ANALYTIC；另一问题的OBJECT不依赖本题失败。
- 未满足依赖的任务为 `UNPROCESSED`，原因 `DEPENDENCY_NOT_REVIEWED`，列准确前置任务。它不初始化Provider，不生成伪 jobKey，也不算模型已读。

该依赖语义写入任务匹配规则版本。历史scope按原版本查看；不能因为字段形状没变便复用新依赖语义下不一致的旧任务。

### 6.2 O2：明选对象来源，不把所有O1绑成一个失败域

新 `ontology-selection-v2` 的每个RELATE问题增加非空 `objectSources`：每项只有准确 `identificationRun` 和 `questionId`。它们必须属于根级 identificationRuns，并且能在保存O1的实际问题范围中核对。QUESTION使用保存的scope.questions；DISCOVERY使用保存的selectedQuestions及其实际taskOutcomes，**不能使用原始scope.questions的空数组**。缺少可核对的实际问题/任务范围就返回无法恢复依赖，不能拿原始导航或最后activeUnits反推。Java从这些问题恢复其实际OBJECT任务及最终已审目录；不由模型填完整任务ID，不按对象名称选依赖。

选中问题的OBJECT必须全部REVIEWED才能派发该RELATE。ACTION或ANALYTIC失败本身不阻断只需对象的RELATE；同一题的未处理义务仍保留在覆盖。另一RELATE依赖的是另一组有效对象时继续执行。`objectSources`及恢复出的实际定义身份参与冻结输入/任务匹配。跨题 B1/B2编号由本次真实目录生成，不复用别题裸O1。

v1选单仍按原合同查看，不能猜它想依赖哪几个问题而升级成v2。明确空关系清单仍可以零模型保存，但不能在失败后偷偷把非空清单改空来宣称原范围完成。

### 6.3 O3：发布有效部分，不抹掉失败分母

O3只用实际REVIEWED完整任务；拒绝稿不进入目录。所选O1/O2即使PARTIAL，也可以确定性发布其中合法部分，同时继承它们的全部声明义务和失败/未处理处置。发布结果为 `DRAFT_REVIEWABLE / INCOMPLETE`，不能称完整识别。

O3显式选取的O1集合必须包含每个所选O2原始声明的准确O1集合；允许额外选择独立O1用于发布。程序逐个O2按其自己的保存请求/selection/receipt核对原完整O1引用，再验证它是O3集合的子集，**不能要求每个O2的O1列表都等于O3全表**，也不能自动补入选单缺少的O1。所有选中O1必须同Corpus，范围及处置均继承；不同O2比较不同题不构成矛盾。缺任一实际语义上游则报告闭合失败。v1历史保留原核验，v2接线同步修改runtime及Reader，不能简单移除原检查。

部分发布仍检查来源和定义闭合。若有效定义之间有断端点或身份冲突，不静默删除一条后称成功：保存具名组装诊断，阻止该次正式发布，保留实际阶段结果可查。O3没有模型调用，也没有“润色到合法”的后门。

v2发布必须检查现有组装器实际返回的结构化`assemblyIssues`，而非只捕获抛出的异常。旧组装器的`IDENTITY_CANONICAL_CONFLICT`会返回冲突定义和INCOMPLETE，不必然抛异常；新门禁在正式安装之前保存该实际诊断并拒绝发布。历史v1结果和旧组装行为不因此改写，不能用一个FAILED生命周期冒充“没有安装冲突定义”。

组装失败的已验证接线是：来源和选择准入通过后先登记O3运行，再在该运行内组装。组装失败保存现有私有PUBLISH诊断，运行转FAILED，查询返回实际错误类别、阶段及零模型调用；没有正式产物时不构造AnalysisRunOutput或正式receipt，也不将output-v10的ontologyPublication改为可空。来源/选单准入本身失败仍在登记前拒绝，不为非法选择伪造运行。具名身份冲突、无receipt及只读诊断查询的直接测试已经通过；这不代表三个真实样例完成。

O3继承处置的准确身份是原运行、问题、任务及原producing身份。覆盖/审阅v2每条继承taskOutcomes明确带原`runId`；不同O1/O2里的同名任务不合并，尤其未准备任务在coverage处置中可能没有producingTaskId、但保存outcome仍可带实际准备身份或null，均以原owner区分。只有完整review身份和完整结果相同的已审定义可去重；拒绝和未处理处置不因裸taskId或bare producer合并。O1/O2原阶段字段和历史字节不因此改变；不用平行数组或裸taskId关联owner。

## 7. 错误分类及准确处理

以下 code 是**目标处置合同中的原因码**，不宣称当前均已有生产异常类。实现需用小型结构化原因类型和直接测试接线，不搭建异常分类平台。

| 情况 | 是否可隔离 | 行为与后续 |
| --- | --- | --- |
| 确认结束的响应非JSON、Schema/引用非法、响应超字节限制 | 单任务 | 保存实际请求/响应或确实取得的失败内容、诊断；REJECTED；继续无依赖任务 |
| 最终审阅引用不存在O3 | 单任务 | REJECTED；不发布、不猜替换；相关下游DEPENDENCY_NOT_REVIEWED |
| 单任务必要完整单元/实际封套超容量、阅读轮次耗尽或已确认无进展 | 单任务 | 未派发任务UNPROCESSED；如已发生读取调用则保存实际状态；列缺项/容量，继续独立任务 |
| 工具能可靠确认请求本身已结束的单请求超时 | 单任务 | 保存超时及实际观察；当前任务结束，不重发原请求；独立任务可继续。仅本地CLI退出不满足该条件 |
| 源版本、映射、receipt损坏或来源身份不一致 | 共享来源 | 停止使用该来源的新任务；已审记录保留；不能用“接受缺口”将错误来源放行 |
| Prompt/Schema加载、配置或模型身份错误 | 共享配置/绑定 | 停止对应范围；返回实际缺项，不换模型/账户 |
| 可靠结构化认证失败 | Provider绑定 | 停止该绑定的新派发；不把它当某题的语义错误 |
| 未能确认进程退出、STARTED结果状态不确定 | Provider绑定 | 保存OUTCOME_UNKNOWN；停止对应新派发，不重叠、不自动重放 |
| 本地CLI已退出，但远端请求结果/取消无法确认 | Provider绑定 | 保存本地终止与远端未知，不宣称远端已取消；保守停止该绑定新派发，命令结束并返回报告，不等远端必定答完 |
| 原因无法可靠分类的Provider故障 | Provider绑定 | 保守停止该绑定，披露未知；不靠错误文本关键词猜测并循环重试 |
| journal/canonical写读失败、不能可靠保存 | 保存范围 | 不再派发；报告确实保存的记录，没有receipt就不报正式产物 |
| 已声明派发上限/授权范围用完 | 本次运行 | 停止新派发，剩余UNPROCESSED；不是模型答案坏，也不能缩小义务分母 |
| Discovery公共调查/选题失败 | 当前调查阶段 | 保留已完成页和问题处置；未形成合法问题的部分不能生成虚构任务。已有明确独立问题只有在实际声明/保存时才可继续 |

“可以隔离”前提是故障确实局部，已有阶段及结束证据。普通RuntimeException、保存一个failure.json或中文描述本身不足以证明。若保存坏响应时再次写失败，升级为保存故障，不能继续以免增加无法追踪请求。

整个实现使用有限清单＋顺序循环＋已审结果/处置映射。任务失败只影响明确依赖它的任务；来源/绑定故障影响实际共享范围。不新增自动排队服务、账户切换、无限退避、语义相似修复或第四模型阶段。

## 8. 进程有界结束：不是只捕获一次异常

### 8.1 每个环节都须有退出条件

| 环节 | 有界条件 | 到达边界后 |
| --- | --- | --- |
| 阅读 | 配置轮次、每轮动作数、必要未读及当前无进展 | 保存观察并结束该任务；不强制READY、不反复读同一包 |
| 派发准备 | 当前实际封套和响应上限、来源检查 | 派发前结束或明确拒绝，不先登录后才发现缺材料 |
| Provider执行 | 配置的整次请求期限，包含启动、写入请求、等待及正式本体结果文件的有界读取 | 确认终止或状态不确定，两者分别记录 |
| EXTRACT/REVIEW | 各至多一次，除非另有明确新运行 | 最终失败局部结束；不等待模型“总有一次答对” |
| 任务循环 | 固定声明任务数、有限阅读及派发许可 | 每个声明任务都有终态处置；不在CLI内等待用户回复 |
| 保存/安装 | 实际原子保存和receipt校验，故障路径不得伪造成功 | 查询确实保存的部分；整体终态不保持虚假RUNNING |

订阅适配器现已把准确Prompt字节保存为私有文件，并使用JDK `ProcessBuilder.redirectInput`提供相同stdin，避免父进程同步写管道被不读stdin的子进程卡住；准备后检查同一绝对deadline，等待及正式本体结果文件的有界读取使用同一期限。4 MiB输入、250 ms期限、不读stdin的子进程用例及旧失败字段直接回归已通过。此验证不承诺操作系统磁盘或启动系统调用可被强制取消。超时仍须终止并确认本地退出，不能为了继续而启动重复请求；v2观察已分别保存本地EXITED和远端UNKNOWN；本体同绑定派发判断已接通并有直接测试，未知状态停止新派发。旧MD输入/Prompt/指纹保持原行为，不新建守护/恢复系统。

当前适配器REQUEST_TIMEOUT的requestEnded=true由本地子进程退出得到，**不是远端模型服务的终止回执**。新报告分别写本地是否退出和远端结果是否已观察；没有回执/实际响应则远端未知，不开发远端取消证明。只确认本地退出的超时不得用该布尔值直接放行后续同绑定请求。结果明确保存后CLI结束，不在后台无限等待确认；这与“模型返回坏引用可局部继续”是两种故障。

进程被外部强制关闭不能承诺程序还能执行finally或写最终报告。下次只读查询按最后真实journal显示未结束/未知，不自动复活或重放。正常异常、坏模型输出、有限读取及可控超时则必须结束，不留一个等用户确认的后台RUNNING任务。

### 8.2 结果必须按身份关联

准备结果、成功结果和失败处置使用准确 `producingTaskId/jobKey` 关联；用户清单标签另保留 `questionId/taskId`。禁止 `prepared[i]` 与 `completed[i]` 配对。

当第二个任务失败、第三个成功时，第三个的阅读包、来源、模型身份、审阅及覆盖必须仍属于第三个。真实未准备任务没有producingTaskId；读取失败和依赖阻断不得伪造它。当前单值problemCode只能做摘要，完整问题存逐任务处置，不能只留下“最后一个失败”。

## 9. 保存、CLI与Skill交接

### 9.1 声明义务和真实模型成员分开

- `taskRecords`只登记实际准备出来的 formal job，按既有身份保存EXTRACT/REVIEW/终态。
- 新 `taskOutcomes`逐项列完整声明清单；至少有questionId、taskId、taskKind、status、实际producingTaskId/jobKey或null、结构化reason及dependencyTaskRefs。
- status沿用REVIEWED、REJECTED、UNPROCESSED。依赖阻断是UNPROCESSED的具体原因，不增加一套相似生命周期状态。
- reason至少含code、category、stage、可公开的结构定位/非法引用及缺少依赖；无实际值为null，敏感Provider输出只给受保护引用。
- 成功阶段立即保存；运行末尾根据真实记录生成PARTIAL/COMPLETED/BLOCKED报告，再登记输出和终态。不能正常return就算整次成功。

### 9.2 一个布尔值不能同时代表三件事

`canContinue`仍只表示**本次声明范围完整满足准入**，不表示授权或语义正确；缺范围时false。另返回结构化`nextActions`，只列实际支持的动作：查询任务/来源、按明确选单使用已审部分、修改Prompt后新建运行、补齐具名材料/配置后新建运行。相应条件、准确范围和是否需要新运行由保存事实生成，不由模型建议决定。

`canContinue=false`不禁止只读查询，不意味着所有独立任务必须被跳过，也不禁止准确选单下的零模型部分发布。它不能授权启动全仓或消费坏稿。nextActions为空不等于流程挂起：该命令已经有终态，Agent向用户说明不能继续的具体原因。

派发统计分别记录预留/调用尝试、确认STARTED、确认结束及状态不确定；没有证据时为未知，不用任务数量推算。预检认证失败不算已确认发送模型请求。费用/调用记录用于审计，不作为模型语义验收标准；授权和配置仍是派发边界。

当前journal在调用委托前写STARTED，单独这一条不证明`codex exec`或实际网络请求已经开始。新计数须使用适配器真实响应/结构化失败或等价实际观察，确认开始/结束是**本地适配调用口径**，不冒充远端服务回执；不足则null。远端结果观察/未知另记录，不由本地requestEnded=true推断，不建设外部服务真实性证明系统。正常完成COMPLETED登记FINISHED；PARTIAL/BLOCKED登记FAILED并保留实际可查询output，含义是声明范围未完成，不是成功项被删除。不能留虚假RUNNING等待用户。

### 9.3 一个完整但非实际运行的调度例子

以下是**设计演示，不是本次模型结果**：

| 清单任务 | 实际前置 | 发生情况 | 保存终态 |
| --- | --- | --- | --- |
| 财务 OBJECT | 无 | 原文齐、最终合法 | REVIEWED |
| 财务 ACTION | 同题OBJECT | 最终合法 | REVIEWED |
| 采购 OBJECT | 无 | REVIEW仍引用已删除O3 | REJECTED，保存原稿/审阅/定位 |
| 采购 ACTION | 采购OBJECT | 依赖不是REVIEWED | UNPROCESSED/DEPENDENCY_NOT_REVIEWED，零调用 |
| 统计 OBJECT | 无 | 合法 | REVIEWED，不被采购失败阻断 |
| 统计 ANALYTIC | 统计OBJECT | 权限helper未提交且申报必要 | UNPROCESSED/REQUIRED_UNREAD；不得归为模型幻觉 |

O1结束为PARTIAL，六项处置均存在，成功和失败都可查。使用财务已审对象的RELATE可以执行；依赖采购OBJECT的RELATE不能执行。O3可保存有效部分，但覆盖必须INCOMPLETE且继承采购、统计缺项，不把它报告成三例全部完成。

### 9.4 宿主Agent行为

任意宿主Agent按同一Skill调用四命令并读真实JSON，不能依赖Codex隐藏上下文。产品模型由既有Provider负责，不让Agent手工代填有效结果。

1. 用户已要求完整既定范围时，无阻断就接续实际支持操作，不每个局部坏稿都停下来询问。
2. 命令非零也读取已保存报告、任务索引及具体记录，说明成功、拒绝、依赖受阻和未执行范围。
3. 本次正常终态即返回给用户；不在运行中等待用户修改Prompt。
4. 已授权同范围内的修复/新运行按实际许可执行；需要新增授权、范围变更或来源选择时才询问。默认不自动追加无限批次。
5. 普通用户可以改Prompt及支持的范围/配置；不能改事实、编号映射或直接导入自己修好的JSON冒充审阅。需要改材料算法才进入明确代码扩展。

## 10. 版本与实施接线

以下为新增目标，不改变已有文件版本或宣称已完成迁移：

| 合同 | 保持 | 新增目标 |
| --- | --- | --- |
| R0/R4/O0 | 现有准确版本及正文 | 不改写；O0的历史结果仍能查询 |
| scope | ontology-scope-v1字段 | 同题OBJECT依赖规则版本进入任务匹配；不新增通用DAG |
| selection | v1历史严格读取 | v2明确O2 objectSources；O3 v2保持既有运行选单字段和完整上游义务 |
| O1/O2阶段 | v1历史严格读取 | identification-v2/relations-v2保存完整taskOutcomes、依赖及问题列表；对应模块producer v2 |
| 覆盖/审阅 | v1历史读取 | coverage-v2/review-v2保留失败原因、依赖、原范围及下一动作依据；Publisher producer v2 |
| 本体定义/来源 | ontology-v1/source-v1 | 结构无变化就不升级，不向模型增添业务字段 |
| 任务查询 | v1历史形状 | task-index/observation-v2区分未准备处置和实际job；不虚构请求记录 |
| typed响应 | candidate/review-v3及严格validator | 不靠放宽端点规则解决流程中断 |

生产者、准确Reader、Schema、artifact policy、runtime、module/step安装与fixture同一交付更新；不能只给payload添加字段或删除严格校验。实际CLI观察须声明新观察版本；历史稀疏记录不能补推“独立任务已执行”。

## 11. 实施顺序与直接验收

先离线跑稳，不用真实模型调控制流。最小修改次序：

1. 以现有真实坏稿写单任务拒绝/后续独立成功的失败测试，保留现有严格validator断言。
2. 改prepared/completed为身份关联，明确同题OBJECT目录及O2显式对象来源；验证失败中间任务不串readingCoverage。
3. 在现有顺序循环隔离局部结果，保存逐任务处置；共享配置/来源/保存/不确定请求仍停。
4. 同步阶段、覆盖、查询、观察版本及PARTIAL准入；验证O3不丢原范围义务。
5. 连接统计具名同源helper的正式完整单元消费；测量实际EXTRACT/REVIEW，不把文件可读当入模。
6. 缩减与当前任务无关的调用和已审目录，保存投影版本；对照实际源码和请求作无损检查。
7. 在已有Provider进程适配器补整次期限；用可控假进程测试阻塞写入、超时确认/未知、退出及零重叠。
8. 更新共享Skill的结果解释和下一动作；真实模型只验证材料可用性及实际质量，不要求它永远正确才验收框架。

直接测试至少包括：

- Prompt变更、坏EXTRACT、坏REVIEW前后R0/R4内容和原始失败响应不变；没有写回证据。
- 可读坏O3草稿一次REVIEW修好，共2次调用；最终仍坏则拒绝，没有第3次。业务条件不被Java删除。
- 非JSON、坏引用及工具可靠确认请求结束的超时不挡独立任务；源码/存储/认证/OUTCOME_UNKNOWN挡对应范围。仅CLI退出的超时不能冒充远端终止，仍停对应绑定。
- 采购OBJECT失败时采购ACTION零初始化/零调用，财务和统计独立任务仍有准确终态；ACTION失败不误阻ANALYTIC。
- 第二个任务失败、第三个成功时，输入/来源/审阅/覆盖按身份仍属于第三个。
- 所有声明任务失败也能结束CLI；partial可查询；零模型发布有效部分不缩小分母。
- 两个O2各依赖不同O1时，O3明确选其并集可发布；缺一个O1拒绝；额外独立O1允许但其义务仍保留。旧v1按原合同读取。
- DISCOVERY O1的原始`scope.questions`为空时，O2-v2必须从实际保存的`selectedQuestions`与`taskOutcomes`恢复所选、已审OBJECT；直接CLI测试需证明准确`objectSources`能派发，并且O2 EXTRACT/REVIEW收到同一恢复目录与reading packet，依赖仍绑定原`(runId, questionId, taskId)`。
- 原文已声明必要却没提交则框架未通过；完整入模而模型解释错单列模型质量。
- 输出超过限制、阅读无进展、请求写入阻塞、超时退出不确定均有限结束，不重叠派发。
- 登录预检失败不伪报confirmed STARTED；实际调用、响应和复用计数可核对。
- 新旧Reader按准确版本分派；旧MD请求、Prompt、指纹、渲染及历史结果保持原行为。

上述完成标准已有直接回归、最终质量及三个局部样例的实际证据/有限结束核验；准确记录见正式验收页。失败隔离通过不表示模型业务零错误或全仓本体通过。

## 12. 可行性推导与明确不能解决的部分

现有底座已经能冻结材料、保存每次请求/响应/校验、拒绝非法最终定义、打开PARTIAL以及确定性局部组装。此次主要增量是准确依赖、身份关联、局部catch、逐任务报告与有界进程，均可在现有深模块接线，不需重写解析器或调度平台。

推导链：坏稿不改变冻结材料 → 坏稿不能成为REVIEWED → 依赖检查只取合法目录 → 独立任务按有限清单继续 → 每项处置保存 → O3只组装合法集合且保留缺口 → CLI结束并可反查。因此模型再产生O3断引用，影响的是一项结果，不会破坏证据或要求整次命令等待模型“答对”。

框架仍不能保证模型自动找齐全部语义材料、识别正确对象、正确区分业务联系或审阅纠正所有幻觉；容量测量也不证明任意模型窗口兼容。完整证据使人工或新的明确任务能够定位和纠正，不保证同模型下一次一定正确。材料缺项、格式负担和生命周期卡住则属于我们应修的框架问题，不能推给模型。
