# 规则核对与业务写作分开的短实验

本轮由用户于2026-09-16明确批准：记住待推理、实现和验证的问题，先复用现有材料做小实验。它是研究实验，不是生产设计修改，也不授权续跑全仓。

## 要验证的问题

1. 模型能否区分同一后台方法在不同业务对象中的用途，正确解释字段、条件及生效范围？
2. 专门核对规则，是否能发现并纠正金额自相矛盾、抵扣适用范围、配置条件遗漏和状态概括错误？
3. 核对后的说明是否足以支撑写作？是否保留对象交接、可选路径、分批处理、具体规则和结果？
4. 写作会不会再次引入错误、丢掉条件，或退回字段清单和技术说明？
5. 即使这个人工选材案例通过，自动选材、跨领域适用和全仓质量仍需另行验证，不能据此认定框架已经可靠。

这些是验证假设。不得提前当成有效架构，也不得为其建立新的生产模块。

## 固定输入与任务

- 保持第一次实验的30份冻结源码与6份已有Activity完整业务字段，不重取材。
- 采用第一次实验的 `reviewed.md` 作为待检查文档。
- 使用相同 Luna/high 和 ChatGPT 登录，最多两次请求，不自动重试。
- `audit`：对照完整原文检查文档事实，仅输出问题、纠正后的完整业务事实和未确认事项，不重写文章。指令要求核对场景、公式、数量、状态、配置以及数值反例，不提供已知错误的正确答案。
- `write`：只读取实际核对结果，写成连贯业务文档；不重新看到整包源码，不使用旧文填补核对结果缺失的信息。这个分离是否丢内容也是实验对象。
- 两次请求均保留输入、原始结果、事件、时间和回执，不人工改写成稿。

## 怎么判定

验收侧按第一轮已记录的问题逐项检查“发现了什么、修正是否正确、正文是否保留”，同时检查其它业务内容有无新增错误。核对表和独立源代码诊断不进入产品模型输入。

通过需要：主线和重要条件仍完整；金额、订金、库存配置及状态解释符合本包原文；核对结果到正文没有语义丢失；正文能够按业务步骤连续阅读。细节未明确时如实写具体未知项。程序只做请求完整性和来源存在等轻量检查，不判断中文业务含义。

出现重要错误则标为本次未通过。两次请求只测一次，不能声称稳定成功；不能将当前改法是否有效与模型/框架普遍能力混为一谈。没有第三次产品请求。
