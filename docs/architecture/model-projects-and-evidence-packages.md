# 模型项目与证据包契约

## 领域层级

```text
零售语义建模（产品）
├── ERP 数据治理（协作空间）
│   └── 管伊佳 ERP 语义模型（模型项目）
│       ├── MySQL 数据库证据
│       └── GitHub 源码证据
└── 零售经营建模（协作空间）
    └── 零售经营语义模型（模型项目）
        ├── 原始人工模型基线
        ├── 数码产品设计文档
        ├── 全渠道经营资料
        └── 集团多存储证据
```

产品只表达产品身份；协作空间负责成员与权限；模型项目负责草稿、申请和 Catalog；证据包负责输入来源。来源版本、资料批次和 Catalog 版本是三套独立编号。

## 兼容与迁移

`guanyijia_erp`和`group_retail_ops`继续作为两个模型项目的稳定编码。`default`、`digital_sales_warehouse`和`omnichannel_retail_ops`只作为证据包的 legacy source code。v2 协作状态复制旧状态后再生效，旧 localStorage 键不删除、不覆盖；旧包内 Catalog 进入包历史，不进入项目 Catalog 序列。无法唯一重连的草稿修改保留为“迁移待确认”。

## 正式模型真相

Catalog 的`workspaceData`和`metricData`是正式对象真相。sidecar 只能补充来源语义，不能覆盖核心对象。正式对象引用必须包含`catalogId`，字段引用必须包含`ownerId`；关系端点、维度目标和指标依赖都使用对象引用。缺少历史 sidecar 时显示覆盖提示，不从最新 Fixture 推断历史资料。

## 页面职责

顶部只选择模型项目和 Catalog。选择模型项目时同步解析其所属协作空间、角色和权限；协作空间仍是后台边界，但不再占用独立选择器。证据包只在 AI 建模的“资料”中出现。左侧时间线记录建模与发布过程并始终保留底部输入框；右侧浏览器是实体、事件、字段、关系、维度、指标及其他语义资产的唯一阅读入口，六个主分类固定为单行。
