# 演示逐步验收

## 演示前提

1. 可打开多个 Linguan Demo 浏览器标签；本轮不承诺多个标签同时修改同一运行的一致性。
2. 本次资料审阅由运行作者完成决定和定版，不需要切换到独立审核者。
3. 数据标准化点击一次“开始资料整理”后，系统会载入固定的数据库快照并自动打开数据库来源文档；每份来源完成后自动收起并依次执行下一来源的“读取 → 分析 → 组织”，新文档就绪后自动打开。用户主动回看历史来源时，新的就绪来源只提示，不强制切换阅读位置。
4. 管伊佳数据标准化使用仓库内固定的预编译正式快照和已提交的内容快照。浏览器本地缓存只是加速层；清空缓存、刷新、重复演示或代码热更新都会从固定资源恢复，不会重新读取数据库、GitHub、文档站点、术语图或调用 LLM。内容快照为 MySQL 提供真实 DDL、为 GitHub 提供固定提交的精确源码节选、为业务资料和制度提供明确标识的演示编写 Markdown、为术语图提供派生资料；它不会改写正式 Claim、Conflict 或 V1。文档内修改仍创建独立 revision，不覆盖基线快照。

管伊佳审阅页的固定设计、用户术语和唯一主操作以[审阅体验设计](design/data-standardization-review-experience.md)为准。

## 从第一步重新开始

1. 以 Administrator 身份点击右上角头像，选择“恢复演示”，再确认恢复。
2. 页面会自动重新加载；这一步会释放当前页面持有的本地资料库连接，再清理本次标准化运行、来源文档修订、差异决定、交付物、审阅位置和预运行来源选择。
3. 恢复完成后保留当前登录和固定来源快照，直接回到“数据标准化”的“开始资料整理”。管伊佳正式 V1、黄金 Artifact 与 Catalog 不会改变。
4. 若页面显示“恢复演示未完成”，点击“继续恢复”。只有本地资料库被其他页面占用时才需要先关闭占用页面；不要使用浏览器控制台清理存储。

## 零售经营 V2

1. 用 Kenan Zhang 登录，选择“零售经营语义模型”；当前正式版本应为 V1。
2. 在“数据标准化 → 来源设置”确认 MySQL、GitHub、Semantica、SharePoint、MongoDB、Elasticsearch、MinIO、Kafka 八个 R2 快照。
3. 点击“生成来源文档”，进入右侧“来源文档”。确认八个来源各有独立九段文档；逐份查看章节摘要，不修改的文档点击“完成本份审阅”，修改章节会产生新版本。
4. 最后一份文档完成后系统自动比较来源。进入“来源差异”，依次打开净销售额退款、机器人流量过滤、营业日三项主要问题，比较来源结论并按需打开依据，然后保存选择；系统在后台保留审计摘要。
5. 进入“输出文档”，选择“来源文档集合”或“合并文档”。Kenan 提交审核；返回时间线后在同一标签切换为 Zhengqing Xiong，执行“审核通过并定版”。
6. 点击“交给 AI 建模”。M4 在后台核对交付物完整性并生成候选，加入 Kenan 的个人草稿。检查新增对象都有`VERIFIED`或`NEEDS_CONFIRMATION`持久状态。
7. Kenan 提交，Zhengqing 审核，Hao 填写中文理由发布。V2 成为当前 Catalog，V1 仍可只读切换。

## 管伊佳 V1

1. 用 Administrator 登录并选择“管伊佳 ERP 语义模型”；顶部应显示`V1 · 正式发布`和`已发布 V1`。
2. 进入“数据标准化”，先打开“运行来源”。左侧按数据库、代码仓库、官方业务文档、ERP 管理制度、术语图显示固定角色；左栏只显示读取状态，异常时才显示待配置、连接失败或缺少可用快照。右侧默认“实例”，可切换到“连接器”：连接器家族先选择具体技术（关系型数据库可选 MySQL 或 PostgreSQL），再创建空白业务实例；实例显示业务名称、技术、环境、脱敏位置和范围。只有已连接实例可拖入兼容角色或点击“添加到…”。已连接但没有可用快照的实例可以选中，但“开始资料整理”会明确阻止。默认实例已预选；运行开始后选择和配置都会锁定。数据库固定快照会先自动打开“数据库建模审阅（真实证据节选）”的“审阅事项”：标题“待确认事项”下是两个独立 Box——“本来源建议”和“来源差异与比较”；其后是逐项“待补充资料”和“已处理事项”。切到“审阅结论”可看到核心结论及默认展开的完整对象目录；不会把内部对象、跨来源事项或 Markdown 标题堆成卡片。标题区唯一动作“核对 1 项建议”会定位到库存单据主表的剧本任务；它不会自动展开来源材料。点击“采用推荐修改”会在任务原位置只打开“业务名称”输入框，预览明确对照业务名称和 Markdown 段落，确认后才生成新版审阅文档。点击“查看来源依据”才会在当前结论下展开真实 DDL 摘录；依据不另设材料阅读区。保留当前结论或确认“库存单据表头（jsh_depot_head）”后，唯一动作变为“完成数据库审阅”。“标准化文档”保持当前 Revision 的 V7 九章业务阅读器；阅读版把可识别的资料不足逐项显示为中文“待补充资料”，切换“Markdown 源文”仍逐字查看同一冻结原文。结论内依据把来源材料、审阅结论和对应 Markdown 段落连起来。`jsh_account` 等数据库结论先展示重点字段结构表，完整字段和带行号的原始 DDL 按需展开。此时正文不应出现尚未准入的 GitHub、官方资料、目标制度或来源差异。
3. 点击“完成数据库审阅”后，数据库来源和四个过程阶段均变绿并自动收起；系统接着读取、分析、组织 GitHub 固定快照，并自动打开 GitHub 审阅事项。GitHub 同样使用“审阅事项／审阅结论／标准化文档”三页签；固定版本共719个文件，本次只选择与业务相关的文件和真实行段，不冒充逐文件人工审阅。“标准化文档”的阅读版按九个业务章节解释代码结论；切换到“Markdown 源文”可逐字查看当前 Revision。每条源码节选都显示业务位置与文件行段，未打入浏览器的完整源码仍仅保留在本地内容快照。GitHub 有一项“建议核对”：可保留当前负库存结论，或采用“租户级负库存控制”并微调说明；界面只显示可改的结论名称和业务说明。确认后，用户输入的名称和说明会原样保留在审阅事项、审阅结论、标准化文档和展开的来源依据中，并在刷新后的运行里恢复。“来源差异与比较”Box 会同时显示负库存互补资料、欠款字段结构差异和“不同版本记录不一致”的单据状态；`introducedConflictIds` 中的正式差异不能只留在时间线，之后打开官方资料、制度或术语图时仍持续可见。“查看双方资料”在卡片下方原位展开已准入材料；欠款字段在 GitHub 建议已核对后立即自动展开为唯一 Primary“保存当前决定”，必须保存后才显示“完成GitHub代码仓库审阅”；负库存和状态9在制度资料准入前明确显示“等待更多来源”。
4. GitHub 完成后系统自动依次准备官方业务文档、ERP 管理制度（演示）和术语图（派生）。官方资料展示“演示编写，非官网原文”的丰富业务资料；不能定位到正式资料的状态 9 含义在“待补充资料”中逐项保留。ERP 管理制度展示“演示制度草案”，待人工确认的目标制度才出现；该来源完成分析后，负库存和状态9来源差异从“等待更多来源”依稳定顺序变为立即可处理的正式差异。用户在 ERP 管理制度的审阅事项中先后保存“登记为缺口”两项决定，才可完成该来源并自动进入术语图。术语图只提供对已确认文档的派生资料，不增加独立证据数量或第四项来源差异；术语图完成后不再出现流程末尾的集中冲突队列。
5. 右栏“来源处理过程”从开始固定列出五个来源，以扁平手风琴显示：未开始来源只显示灰色标题；当前来源按读取、分析、组织、审阅累计显示真实阶段；完成来源自动收起，重新展开后可从展开区次级“查看审阅文档”只读回看精确 Revision。来源标题只控制展开／收起，绝不直接打开文档；用户回看历史来源时，后台当前来源不抢走展开状态，关闭历史项后恢复当前项。Demo 在 `ACTIVE` 阶段后依次停留读取500ms、分析700ms、组织700ms，以便看见真实过程；未来后端用同一 callback 报告实际进度且不施加固定等待。未开始为灰色、当前为蓝色、完成及已保存差异为绿色，红色只表示失败或完整性错误。桌面由页头唯一的“来源资料／收起来源资料”控件开合资料区，内联区没有重复标题或关闭盒；运行开始后“运行来源”只展示已锁定的实例及状态，不允许移除、替换、扫描、测试、冻结或 YAML 操作。
6. 在工作台底部的审阅助手输入区分别询问当前来源、差异、依据、影响对象和未知请求；主审阅区独自滚动，输入区不覆盖正文。打开一个目标并返回，确认草稿、滚动和焦点恢复。生成结构化修改后先“放弃修改建议”一次，再生成并“应用此修改”一次；直接要求助手解决冲突或交付时应只返回边界说明。
7. 五份来源均完成时，所有三项正式差异已经在其成立时保存，工作台自动进入“标准化结果预览”，不是直接生成。预览保留“审阅事项／审阅结论／标准化文档”三页签，三者绑定同一份九章、每章五来源、完整补充资料和三项决定的合并文档，并显示 Preview SHA256；阅读版、Markdown 源文和复制 Markdown 都是同一预览内容。完整正文来自五份用户实际审阅的 V7 业务阅读文档与其保存 Revision；V7 以精确 V6 的冻结证据、Claim、边界和资料缺口为不可变前序，而非简化结构投影。用户修改以绿色标记，可展开查看红删绿增。点击唯一主操作“确认并定版”后，系统重建并校验同一 Preview SHA256、生成结果并作者定版；不一致时拒绝生成。生成成功但定版失败时，页面只显示“继续定版”，不得重新生成。结果页保持当前页签和阅读位置，完整 Markdown 同时保留已确认结论、无法确定项和缺口。原始清单、摘要、内部引用和 JSON 只保留在审计存储，不作为页面内容；页面不显示审批意见、独立审核、审核人或中文决定理由。
8. 定版完成后点击“前往 AI 建模”。交接页显示完整标准化文档、可建模结论数和已排除缺口数；AI 建模只对结构化标记为可建模的结论生成候选，缺口和无法确定项仅保留在资料缺口区。正式 V1 仍未改变；只有 AI 建模既有审核发布流程才能更新正式模型。
9. 重新核对正式 V1：14 个实体、9 个事件、296 个字段、5 个指标、8 个只读规则候选、10 个同义词和 9 条时间语义；完整性校验、对象计数与 draft=0 保持不变。

## 容量与响应式

1. 运行`npm run test:review-window`与`npm run test:e2e:cp8:capacity-errors`：10k 问题／100k Evidence 下，首屏最多 40 条 Timeline、20 个问题、0 条正文，页面最多 50 行、window 最多 80 项、完整 DOM 不超过 300。
2. 运行`npm run test:e2e:cp8:responsive`，覆盖 1440／1024／768／390／320 与 Chrome CDP 真实 200% 缩放；检查 inline／overlay／full-screen、safe-area、虚拟键盘、44px 触控、focus trap、Escape、滚动恢复与零横向溢出。
3. 运行`npm run test:e2e:cp8:story`完成连续资料审阅流程，运行`npm run test:e2e:cp8:protected`确认零售 V1、个人草稿隔离、旧 M3 和手机本体返回不变。每条 runner 的首尾都必须输出`127.0.0.1:5202 closed`。
4. 人工逐张检查`artifacts/cp8-visual/01…20`：不得只更新截图；重点确认真实 200% 可见区、助手 Patch Before／After 与确认动作、三个冲突 Hunk、作者直接定版、标准化文档交接的可建模结论与排除项，以及四张零售保护图。
