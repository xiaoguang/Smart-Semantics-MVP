# 管伊佳数据标准化审阅体验

## 状态与范围

本文件是管伊佳数据标准化审阅体验的当前权威设计。它记录 2026-08-28
用户批准的“即时差异审阅、自动来源流程与完整合并文档”合同；实现、测试和当前事实
文档必须以它为准。此前“未决正式差异可继续下一来源”“手动审阅下一个来源”以及
“最后集中处理来源差异”的设计不再适用于新运行。

本轮不调用 LLM 或其他生成模型。所有文档拼接、修改投影、预览和 SHA 校验均由
冻结 V6 内容、已保存 Revision 和确定性 TypeScript 完成。不得修改 V6、Pinned Bundle、
正式管伊佳 V1、零售 V1/V2、黄金摘要、原始证据或快照；不得调用来源系统、capture、
package、freeze 或 V7 生成器。

## 术语

| 用户语言 | 内部概念 | 说明 |
| --- | --- | --- |
| 本来源建议 | Scripted review task | 用户保留或采用的当前来源剧本化建议。 |
| 来源差异与比较 | Formal conflict / preliminary comparison | 已具备决定条件的正式差异，或仍在等待资料的比较项。 |
| 等待更多来源 | Preliminary comparison | 已看到比较问题、但尚未具备正式决定前提的事项。 |
| 待补充资料 | `GAP` projection | 材料不足的逐项业务记录；不阻断来源推进。 |
| 已处理事项 | Saved review decision | 已保存、继续可读的建议或正式差异决定。 |
| 来源过程 | Read / analyze / organize / review journey | 一个来源从冻结资料读取到用户完成审阅的真实处理阶段。 |
| 合并结果预览 | Complete merged review document | 五份完整审阅后 V6 文档和已保存决定形成的同一份九章文档。 |

用户界面和阅读版不得显示英文 `GAP`。内部枚举、冻结 JSON、Markdown 源文和复制内容
继续保持原样。

“待确认事项”只作为区段标题与总数，不能形成共同的黄色外框。“本来源建议”和
“来源差异与比较”是两个视觉独立、同级的 Box：前者使用提示色，后者使用中性／蓝色
比较样式；没有建议时隐藏第一个 Box。审阅容器宽度大于 959px 时，卡片内容为三列；
959px 及以下为单列。320px、390px 和真实 200% 缩放下，操作可以换行或占满一行，
但页面不得横向滚动。布局仅使用稳定 CSS class，禁止使用中文 `aria-label`。

### 唯一主操作

| 当前情况 | 唯一 Primary |
| --- | --- |
| 本来源建议正在编辑 | 保存修改 |
| 第一项正式差异可以处理 | 保存当前决定 |
| 没有未处理建议或正式差异 | 完成本来源审阅 |
| 下一来源正在读取、分析或组织 | 无 Primary |
| 全部来源完成 | 确认并定版 |
| 已定版 | 前往 AI 建模 |

本来源建议未保存时，正式差异仍可见，但显示“先核对本来源建议”。建议保存后，
第一项正式差异自动展开并获得唯一 Primary。普通差异不再进入独立的流程末尾
冲突层；时间线或右侧来源差异节点只负责定位到所属来源的内联卡片。

## 即时正式差异

比较资料尚不充分时，事项显示为“等待更多来源”，不阻断当前来源完成或后续来源读取。
当决定前提齐全时，运行立即记录 `CONFLICT_FOUND`，并且该差异必须同时出现在：

1. 使它正式成立的来源的“来源差异与比较”或“已处理事项”；
2. 右侧该来源的“审阅”阶段；
3. 审计时间线。

正式差异的稳定顺序为：欠款字段结构冲突、负库存制度与实现冲突、状态 9 业务含义冲突。
Semantica 只追加佐证，不得创建第四项差异。`introducedConflictIds` 是正式差异存在
的唯一权威：每一项必须且只能投影为一个未决卡或一个已处理项。若候选资料无法构造
已引入差异的卡片，显示完整性错误并阻断写操作、来源完成和结果生成；绝不静默隐藏。

新运行的命令门禁如下：

- `MARK_DOCUMENT_REVIEWED` 在存在已引入、未保存的正式差异时拒绝；
- `START_NEXT_SOURCE` 在存在已引入、未保存的正式差异时拒绝；
- `GENERATE_DELIVERABLE` 在存在未保存正式差异或完整性错误时拒绝；
- 来源完成后进入 `ALIGNED`；新运行不以 `CONFLICT_BLOCKED` 推进下一来源；
- 历史 `CONFLICT_BLOCKED` 运行继续可读，并恢复缺失的可处理卡片。

保存差异后，卡片移入“已处理事项”并显示绿色完成标记；右侧对应差异也变绿。
保存决定不会修改来源文字 Revision，除非该来源的独立剧本化修改已经按其自身命令保存。

## 自动来源过程与右侧面板

```text
完成本来源审阅
  → 当前来源全绿并自动收起
  → 自动启动下一来源
  → 上一来源文档保持只读可见
  → 读取 → 分析 → 组织
  → 新来源文档准备完成
  → 自动打开新来源的审阅事项
```

读取、分析、组织和审阅必须对应真实运行边界：

| 阶段 | 完成含义 |
| --- | --- |
| 读取 | 冻结来源资料已经读取并完成身份校验。 |
| 分析 | 编译、候选比较和正式差异前提分析完成。 |
| 组织 | 审阅文档已经注册并绑定精确 Revision。 |
| 审阅 | 文档处于 `DOCUMENT_READY`，等待用户完成建议和正式差异。 |

运行时必须在真实边界向页面报告阶段进度；不得以计时器伪造读取、分析、组织或审阅已经
完成。静态 Demo 可以只在阶段报告为 `ACTIVE` 后增加展示停留，让用户看见真实当前阶段：
读取 500ms、分析 700ms、组织 700ms。`COMPLETE`、`ERROR` 和用户完成审阅均不等待，
展示等待不写入运行事件、Revision 或持久化 Schema。

未来接入后端服务时，同一阶段 callback 由真实处理进度驱动，Demo 展示停留为零；后端
不得继承任何固定 500/700/700ms 延迟。callback 或展示等待失败、取消或页面卸载不能把
来源投影为业务失败。

### 扁平来源过程清单

右侧使用“来源处理过程”扁平手风琴，而不是带竖向连接线的大按钮卡或独立“展开阶段”操作：

```text
来源处理过程
────────────────────────────────────────
✓  数据库                         已完成  ›
────────────────────────────────────────
●  GitHub代码仓库                 审阅中  ⌃
   ✓ 读取                         已完成
   ✓ 分析                         已完成
   ✓ 组织                         已完成
   ● 审阅                         进行中
      ✓ 欠款字段结构冲突           已保存

   查看当前审阅文档
────────────────────────────────────────
○  业务说明                       未开始
○  ERP管理制度                    未开始
○  企业术语图                    未开始
○  标准化结果                     待生成
```

五个来源从运行开始按固定顺序列出。未开始来源仅显示标题和灰色状态，不能展开，也不提前
显示未来阶段。当前来源首次开始时自动展开，并只累计显示截至真实当前阶段的前缀：读取时
只显示读取；分析时显示读取完成和分析进行中；组织时显示前三项；文档就绪时显示前三项完成和
审阅进行中。完成来源必须自动收起；用户重新展开完成来源时，才显示四项全绿和可用的次级
“查看审阅文档”入口。

来源标题行是唯一 disclosure 控件，点击只展开或收起过程，绝不直接打开文档或嵌套另一个
按钮。当前来源可以被用户手动收起，阶段变化不得反复强制展开。用户主动回看历史来源时，
新来源就绪后不抢走该展开状态；用户关闭历史来源后恢复当前来源。来源完成时仍无条件自动
收起，并在下一来源实际开始后自动展开下一项。完成、当前、未开始和错误分别使用绿、蓝、灰、
红；红色只表示真实运行、SHA 或完整性错误。

右侧来源组使用固定状态色：未开始、等待资料和未审阅为灰色；当前阶段为蓝色；来源、
阶段和已保存差异为绿色；红色只用于运行失败、SHA 漂移和完整性错误。

读取、分析或组织失败时，上一来源继续可读，失败阶段显示红色并提供重试；不得跳过来源
或伪造后续绿色阶段。

## 实时建议修改

编辑本来源建议时，输入框下方始终显示本地确定性的修改效果，不再提供“预览修改”按钮。
输入变化后约 250ms 发起权威 Preview SHA 校验。当前输入与原文相同、校验未完成、
Revision 已变化或 SHA 已过期时，“保存修改”禁用。异步返回必须带草稿键，过期草稿
响应不得覆盖当前输入。保存继续使用精确 Revision、CAS 和权威 Preview SHA。

阅读版中的用户修改使用浅绿色背景、绿色边线和“用户修改”标签；可按需展开 GitHub 式
红色删除／绿色新增差异。复制的 Markdown 仅包含最终干净正文，不含视觉标签或删除文本。

## 完整合并结果预览

五份来源均完成、所有正式差异均已保存后，工作台自动进入只读“标准化结果预览”。
它不再需要用户最后集中处理差异，唯一 Primary 为“确认并定版”。该操作内部串行执行：

```text
重新校验 Preview SHA
  → 生成标准化结果
  → 校验 saved mergedDocumentRef 与预览一致
  → 作者定版
```

若生成成功、定版失败，页面显示“结果已生成，尚未定版”，唯一 Primary 改为“继续定版”，
不得重新生成。

最终文档必须来自用户实际审阅的完整 V6 内容：精确内容快照、来源 ID、文档 ID、Revision、
已保存剧本化修改和已保存正式差异决定。正式结构化建模投影继续用于资格和零变化校验，
但不得作为人类阅读 Markdown 正文。

合并 Markdown 固定为九章，章内固定按数据库、GitHub、业务说明、ERP 管理制度、企业术语图
的顺序保留每份来源的完整审阅后正文；不做语义去重、摘要替换或内容压缩。每章相关的正式
决定追加在来源正文之后。缺少任一来源的任一固定章节是完整性错误，不能生成占位内容。

三个结果页签共享同一个不可变身份：

```text
runId + sourceManifest + reviewedSourceManifest + decisionManifest
+ changeManifest + previewSha256
```

每个页签都能呈现完整九章、五来源正文，只改变阅读关注点：

| 页签 | 完整正文 | 额外呈现 |
| --- | --- | --- |
| 审阅事项 | 是 | 相关段落前的待补充资料和已保存决定。 |
| 审阅结论 | 是 | 核心结论、对象目录和来源归属。 |
| 标准化文档 | 是 | GitHub Light 阅读版、Markdown 源文和复制动作。 |

活动页签可以独立渲染以控制 DOM 大小，但切换不得重新构建或改变文档身份。阅读版和源文
使用 GitHub Light 基础色：正文 `#1f2328`、背景 `#ffffff`、工具栏／代码背景 `#f6f8fa`、
边框 `#d0d7de`、链接 `#0969da`、用户修改 `#dafbe1/#1a7f37`、删除差异
`#ffebe9/#cf222e`。长代码块只允许自身滚动，页面不得横向溢出。

## 运行时接口与兼容性

来源准备阶段是 UI 观察接口，不进入持久化 `StandardizationRun` Schema：

```ts
type SourcePreparationStage = 'READ' | 'ANALYZE' | 'ORGANIZE';

type SourcePreparationProgress = {
  sourceId: string;
  stage: SourcePreparationStage;
  state: 'ACTIVE' | 'COMPLETE' | 'ERROR';
  sequence: number;
};

type SourcePreparationObserver = (
  progress: SourcePreparationProgress,
) => void | Promise<void>;
```

`SourcePreparationObserver` 是唯一的展示 seam：Demo adapter 先写入页面状态，再仅在
`ACTIVE` 回调后等待固定展示时长；LIVE adapter 写入同一状态后立即返回。运行时等待 observer
只为了让 Demo 的当前阶段可见，但不把展示等待解释为来源业务处理，也不持久化它。

重载时，`PENDING` 显示全灰，`READING` 显示读取活动，`DOCUMENT_READY` 显示前三阶段
绿色且审阅蓝色，`ALIGNED` 和历史 `REVIEWED` 显示四阶段绿色。

完整来源读取通过 `ReviewedSourceDocumentReader` 提供：它绑定运行、精确 V6 文档和
已保存 Revision，返回原始及审阅后 Markdown SHA、九章结构和逐项 `ReviewedSourceChange`。
交付预览将 `reviewedSourceManifest`、`changeManifest`、完整合并 Markdown 和三页签投影
纳入 Preview SHA；生成复用同一个构建器，并验证实际保存的 `mergedDocumentRef` 与预览一致。

现有历史事件顺序继续可读：

```text
DOCUMENT_GENERATED → DOCUMENT_REVIEWED → CONFLICT_FOUND → CONFLICT_RESOLVED
```

新运行在文档就绪时记录满足前提的正式差异：

```text
DOCUMENT_GENERATED → CONFLICT_FOUND → [CONFLICT_RESOLVED] → DOCUMENT_REVIEWED
```

不新增持久化状态、Schema 版本或命令联合类型；保持现有 CAS、幂等和历史回放边界。

## 设计不变量

- 审阅事项、审阅结论和标准化文档三页签始终存在。
- 所有正式差异都在其成立时审阅，不允许在流程末尾堆积。
- 每个页面或移动层最多一个 Primary。
- 已保存决定、已审阅来源和完成阶段均为绿色；红色仅表示错误。
- V6、Pinned Bundle、正式模型、黄金摘要、原始证据和快照不可修改。
- 普通启动、测试、构建和浏览器故事只读取仓库固定资源，不访问来源系统或模型。
- 多标签并发正确性不在本故事中扩展；既有 Revision/CAS 继续保护写操作。
