# 管伊佳数据标准化审阅体验

## 状态与范围

本文件是管伊佳数据标准化审阅体验的当前权威设计。它记录 2026-08-28 至 2026-08-29
用户批准的“即时差异审阅、自动来源流程、完整合并文档、证据栏与人类可读 V7”合同；
实现、测试和当前事实文档必须以它为准。此前“未决正式差异可继续下一来源”“手动审阅
下一个来源”以及“最后集中处理来源差异”的设计不再适用于新运行。

实施严格分两阶段。阶段一只调整审阅页面：右栏的来源进度与证据支持信息、以及页头对齐；
本阶段不调用 LLM 或其他生成模型，也不创建 V7。阶段一部署后必须由用户审阅页面风格。
只有用户明确批准该页面后，才可以执行阶段二的 V7 候选生成、审阅、冻结和接入；阶段二的
模型输入、验收、两轮改进与停止规则由 scoped `AGENTS.md` 和本文件共同约束。

两个阶段都不得修改 V6、Pinned Bundle、正式管伊佳 V1、零售 V1/V2、黄金摘要、原始证据
或快照；不得重新捕获来源，且不得调用 capture、package 或 freeze。阶段一的所有文档拼接、
修改投影、预览和 SHA 校验继续只使用冻结 V6 内容、已保存 Revision 和确定性 TypeScript。

## 术语

| 用户语言 | 内部概念 | 说明 |
| --- | --- | --- |
| 本来源建议 | Scripted review task | 用户保留或采用的当前来源剧本化建议。 |
| 来源差异与比较 | Formal conflict / preliminary comparison | 已具备决定条件的正式差异，或仍在等待资料的比较项。 |
| 等待更多来源 | Preliminary comparison | 已看到比较问题、但尚未具备正式决定前提的事项。 |
| 待补充资料 | `GAP` projection | 材料不足的逐项业务记录；不阻断来源推进。 |
| 已处理事项 | Saved review decision | 已保存、继续可读的建议或正式差异决定。 |
| 来源过程 | Read / analyze / organize / review journey | 一个来源从冻结资料读取到用户完成审阅的真实处理阶段。 |
| 合并结果预览 | Complete merged review document | 五份完整审阅后文档和已保存决定形成的同一份九章文档。 |
| V7 阅读候选 | Human-readable reader candidate | 仅在阶段二中由冻结输入生成、验证并经用户批准的业务可读阅读投影。 |

用户界面和阅读版不得显示英文 `GAP`。内部枚举、冻结 JSON、Markdown 源文和复制内容
继续保持原样。

### 唯一主操作

| 当前情况 | 唯一 Primary |
| --- | --- |
| 本来源建议正在编辑 | 保存修改 |
| 第一项正式差异可以处理 | 保存当前决定 |
| 没有未处理建议或正式差异 | 完成本来源审阅 |
| 下一来源正在读取、分析或组织 | 无 Primary |
| 全部来源完成 | 确认并定版 |
| 已定版 | 前往 AI 建模 |

本来源建议未保存时，正式差异仍可见，但显示“先核对本来源建议”。建议保存后，
第一项正式差异自动展开并获得唯一 Primary。普通差异不再进入独立的流程末尾
冲突层；时间线或右侧来源差异节点只负责定位到所属来源的内联卡片。

## 即时正式差异

比较资料尚不充分时，事项显示为“等待更多来源”，不阻断当前来源完成或后续来源读取。
当决定前提齐全时，运行立即记录 `CONFLICT_FOUND`，并且该差异必须同时出现在：

1. 使它正式成立的来源的“来源差异与比较”或“已处理事项”；
2. 右侧该来源的“审阅”阶段；
3. 审计时间线。

正式差异的稳定顺序为：欠款字段结构冲突、负库存制度与实现冲突、状态 9 业务含义冲突。
Semantica 只追加佐证，不得创建第四项差异。`introducedConflictIds` 是正式差异存在
的唯一权威：每一项必须且只能投影为一个未决卡或一个已处理项。若候选资料无法构造
已引入差异的卡片，显示完整性错误并阻断写操作、来源完成和结果生成；绝不静默隐藏。

新运行的命令门禁如下：

- `MARK_DOCUMENT_REVIEWED` 在存在已引入、未保存的正式差异时拒绝；
- `START_NEXT_SOURCE` 在存在已引入、未保存的正式差异时拒绝；
- `GENERATE_DELIVERABLE` 在存在未保存正式差异或完整性错误时拒绝；
- 来源完成后进入 `ALIGNED`；新运行不以 `CONFLICT_BLOCKED` 推进下一来源；
- 历史 `CONFLICT_BLOCKED` 运行继续可读，并恢复缺失的可处理卡片。

保存差异后，卡片移入“已处理事项”并显示绿色完成标记；右侧对应差异也变绿。
保存决定不会修改来源文字 Revision，除非该来源的独立剧本化修改已经按其自身命令保存。

## 阶段一：右栏与页头

阶段一只调整信息层级和视觉布局，不改变即时差异、自动来源流程、最终合并内容或运行时
持久化 Schema。右栏没有第二套来源列表：它只由上方的来源进度和下方的证据与支持信息
两个区域组成。

来源进度区位于右栏上方，最多占桌面右栏可用高度约 44%，超过时在本区独立滚动；证据区
占据其余高度并独立滚动。低高度、移动端或真实 200% 缩放时，右栏退化为单一纵向滚动，
不得制造两个无法使用的小滚动窗口。来源标题、阶段累计显示、自动收起、历史回看和颜色
规则继续遵守本文件的“扁平来源过程清单”合同。未选中具体事项时，证据区显示当前来源概览；
选中建议、结论或差异时，显示该事项的证据类型、可读摘要、来源位置、支持范围及双方索引。
已声明却找不到的证据必须显示完整性错误，不能静默留空。

右栏不得铺开源码、DDL、SHA、`sourceId`、`snapshotId`、内部枚举或传输标识。源码、DDL
和原始制度内容只在主阅读区按需展开，并采用 GitHub Light 阅读样式；右栏只提供“在正文
查看技术依据”的定位入口。

页头使用与正文相同的内容左边界。返回箭头绝对定位在左侧 gutter，不占用标题列；标题、
页签和“待确认事项”的左坐标必须一致。页头为“内容区 + 操作区”两列，唯一 Primary 保持
右侧；390px 与 320px 时标题和操作可上下排列，返回按钮仍保有至少 44px 点击区域。

## 自动来源过程与右侧面板

```text
完成本来源审阅
  → 当前来源全绿并自动收起
  → 自动启动下一来源
  → 上一来源文档保持只读可见
  → 读取 → 分析 → 组织
  → 新来源文档准备完成
  → 自动打开新来源的审阅事项
```

读取、分析、组织和审阅必须对应真实运行边界：

| 阶段 | 完成含义 |
| --- | --- |
| 读取 | 冻结来源资料已经读取并完成身份校验。 |
| 分析 | 编译、候选比较和正式差异前提分析完成。 |
| 组织 | 审阅文档已经注册并绑定精确 Revision。 |
| 审阅 | 文档处于 `DOCUMENT_READY`，等待用户完成建议和正式差异。 |

运行时必须在真实边界向页面报告阶段进度；不得以计时器伪造读取、分析、组织或审阅已经
完成。静态 Demo 可以只在阶段报告为 `ACTIVE` 后增加展示停留，让用户看见真实当前阶段：
读取 500ms、分析 700ms、组织 700ms。`COMPLETE`、`ERROR` 和用户完成审阅均不等待，
展示等待不写入运行事件、Revision 或持久化 Schema。

未来接入后端服务时，同一阶段 callback 由真实处理进度驱动，Demo 展示停留为零；后端
不得继承任何固定 500/700/700ms 延迟。callback 或展示等待失败、取消或页面卸载不能把
来源投影为业务失败。

### 扁平来源过程清单

右栏上方的“来源进展”使用“来源处理过程”扁平手风琴，而不是带竖向连接线的大按钮卡、
第二套来源导航或独立“展开阶段”操作：

```text
来源处理过程
────────────────────────────────────────
✓  数据库                         已完成  ›
────────────────────────────────────────
●  GitHub代码仓库                 审阅中  ⌃
   ✓ 读取                         已完成
   ✓ 分析                         已完成
   ✓ 组织                         已完成
   ● 审阅                         进行中
      ✓ 欠款字段结构冲突           已保存

   查看当前审阅文档
────────────────────────────────────────
○  业务说明                       未开始
○  ERP管理制度                    未开始
○  企业术语图                    未开始
○  标准化结果                     待生成
```

五个来源从运行开始按固定顺序列出。未开始来源仅显示标题和灰色状态，不能展开，也不提前
显示未来阶段。当前来源首次开始时自动展开，并只累计显示截至真实当前阶段的前缀：读取时
只显示读取；分析时显示读取完成和分析进行中；组织时显示前三项；文档就绪时显示前三项完成和
审阅进行中。完成来源必须自动收起；用户重新展开完成来源时，才显示四项全绿和可用的次级
“查看审阅文档”入口。

来源标题行是唯一 disclosure 控件，点击只展开或收起过程，绝不直接打开文档或嵌套另一个
按钮。当前来源可以被用户手动收起，阶段变化不得反复强制展开。用户主动回看历史来源时，
新来源就绪后不抢走该展开状态；用户关闭历史来源后恢复当前来源。来源完成时仍无条件自动
收起，并在下一来源实际开始后自动展开下一项。完成、当前、未开始和错误分别使用绿、蓝、灰、
红；红色只表示真实运行、SHA 或完整性错误。

右侧来源组使用固定状态色：未开始、等待资料和未审阅为灰色；当前阶段为蓝色；来源、
阶段和已保存差异为绿色；红色只用于运行失败、SHA 漂移和完整性错误。

读取、分析或组织失败时，上一来源继续可读，失败阶段显示红色并提供重试；不得跳过来源
或伪造后续绿色阶段。

## 实时建议修改

编辑本来源建议时，输入框下方始终显示本地确定性的修改效果，不再提供“预览修改”按钮。
输入变化后约 250ms 发起权威 Preview SHA 校验。当前输入与原文相同、校验未完成、
Revision 已变化或 SHA 已过期时，“保存修改”禁用。异步返回必须带草稿键，过期草稿
响应不得覆盖当前输入。保存继续使用精确 Revision、CAS 和权威 Preview SHA。

阅读版中的用户修改使用浅绿色背景、绿色边线和“用户修改”标签；可按需展开 GitHub 式
红色删除／绿色新增差异。复制的 Markdown 仅包含最终干净正文，不含视觉标签或删除文本。

## 完整合并结果预览

五份来源均完成、所有正式差异均已保存后，工作台自动进入只读“标准化结果预览”。
它不再需要用户最后集中处理差异，唯一 Primary 为“确认并定版”。该操作内部串行执行：

```text
重新校验 Preview SHA
  → 生成标准化结果
  → 校验 saved mergedDocumentRef 与预览一致
  → 作者定版
```

若生成成功、定版失败，页面显示“结果已生成，尚未定版”，唯一 Primary 改为“继续定版”，
不得重新生成。

最终文档必须来自用户实际审阅的完整 V6 内容：精确内容快照、来源 ID、文档 ID、Revision、
已保存剧本化修改和已保存正式差异决定。正式结构化建模投影继续用于资格和零变化校验，
但不得作为人类阅读 Markdown 正文。

合并 Markdown 固定为九章，章内固定按数据库、GitHub、业务说明、ERP 管理制度、企业术语图
的顺序保留每份来源的完整审阅后正文；不做语义去重、摘要替换或内容压缩。每章相关的正式
决定追加在来源正文之后。缺少任一来源的任一固定章节是完整性错误，不能生成占位内容。

三个结果页签共享同一个不可变身份：

```text
runId + sourceManifest + reviewedSourceManifest + decisionManifest
+ changeManifest + previewSha256
```

每个页签都能呈现完整九章、五来源正文，只改变阅读关注点：

| 页签 | 完整正文 | 额外呈现 |
| --- | --- | --- |
| 审阅事项 | 是 | 相关段落前的待补充资料和已保存决定。 |
| 审阅结论 | 是 | 核心结论、对象目录和来源归属。 |
| 标准化文档 | 是 | GitHub Light 阅读版、Markdown 源文和复制动作。 |

活动页签可以独立渲染以控制 DOM 大小，但切换不得重新构建或改变文档身份。阅读版和源文
使用 GitHub Light 基础色：正文 `#1f2328`、背景 `#ffffff`、工具栏／代码背景 `#f6f8fa`、
边框 `#d0d7de`、链接 `#0969da`、用户修改 `#dafbe1/#1a7f37`、删除差异
`#ffebe9/#cf222e`。长代码块只允许自身滚动，页面不得横向溢出。

## 阶段二：人类可读 V7 阅读投影（待阶段一审阅后执行）

阶段二尚未开始。它只能在阶段一远端页面获得用户批准后执行，且先生成并展示数据库来源
样稿；该样稿的语言、信息密度和版式获用户批准后，才可串行生成其余四份来源。五份来源的
最终 Selection 再次获得用户批准前，不得冻结 V7、重新打包 pinned 内容或把 V7 接入新运行。

V7 的目标是业务可读的说明书，而不是技术传输记录。每一份来源仍保留固定九章，但每章首先
说明“是什么、为什么重要、如何使用、有哪些边界或例外”，再按需提供可展开的技术依据。
对象使用对象／业务作用／范围表格，业务活动使用有序步骤，字段、关系与指标使用业务主题
表格，待确认事项逐项列出缺少内容、影响和下一步。正文不显示内部 ID、快照、SHA、传输枚举
或英文 `GAP`，也不得把字段清单、候选解释、实现线索或制度草案冒充为已确认事实。

模型只能产生严格 JSON Schema v2 的 `V7ReaderCandidate`：每一章包含引言、可追溯到已有
`claimIds` 的内容项，以及同样可追溯的待补充资料。确定性 TypeScript 负责九章顺序、来源
身份、用户修改和正式决定叠加、技术依据映射、GitHub Light 样式、干净 Markdown、SHA 与
receipt；模型不得生成文件路径、行号、Evidence Ref、来源身份、正式差异、已保存修改或
Markdown 样式。Demo 读取冻结 V7，浏览器运行时不得调用模型；未来 LIVE adapter 只在真实
`ORGANIZE` 阶段调用相同 Schema 和提示词，且不继承 Demo 的人为展示停留。

V2 的模型输出 Schema 因此只包含 `schemaVersion` 和 `chapters`；`sourceId` 永远由冻结的
来源描述符在确定性边界注入。历史候选若额外携带一个模型生成的 `sourceId`，只能由专用兼容
投影丢弃该字段，并写入新的、追加式 remediation receipt。兼容投影必须绑定原始 Candidate、
原始输出 digest、冻结来源描述符和投影后 digest；不得修改原始输出、Receipt、Claim、Gap、
章节或任何业务文字。它只用于修复“模型错误输出了来源身份”这一结构错误，不能把任意来源
不匹配、事实错误或内容缺失降级为可接受问题，也不调用模型或创建第三份产品内容候选。

该兼容投影只有在父 Candidate 已完成、确实出现 `thread.started`、其 Receipt 与原始输出和
冻结来源身份逐字校验通过，且重新验证后除模型 `sourceId` 外不存在致命错误时才可发布。修复
目录复制父原始输出但绝不覆盖父目录；它以独立 Candidate 引用记录父 Candidate、父 Receipt
摘要、原始输出摘要和确定性投影摘要。Selection 读取此引用时仍必须显示
`LEGACY_MODEL_SOURCE_ID_DROPPED` 告警，不能把它提升为 `IDEAL`，也不得伪造该父调用为
带 Sol 修订的 Round 2。

较早 Receipt 若在 `attempt.modelSessionStarted` 字段引入前创建，可仅在它已经 `COMPLETED`、
拥有通过验证的非空 Luna session ID、并且 Receipt／输入／输出／lineage 均精确匹配时作为
“已启动”的历史证明；不写回该字段。任何显式 `modelSessionStarted: false`、空 session ID、
或 Receipt 绑定不一致仍一律拒绝，不能走兼容投影。

每次生成必须绑定冻结 V6 内容身份、精确来源、九章 Claim／Boundary／Gap／Evidence 映射、
提示词版本和 Schema 版本，并写入不可覆盖的 Candidate 目录与 receipt。提示词把模型限定为
中文 ERP 业务说明书编辑：只使用输入事实，不知道就明确列为边界或待补充资料，先业务解释
后技术依据，自然短句中文。不得自动重试、换模型、重跑无关来源或重写 V6。

### 两候选生成与质量门禁

每个来源最多产生两份产品内容候选：Luna/xhigh 的 Round 1 初稿，以及唯一允许的
Luna/xhigh Round 2 替代候选。Round 2 只可在 Round 1 存在致命错误，或用户明确指出系统性
可读性问题时使用；它必须绑定同一冻结 V6 digest、Round 1 Candidate 与新的提示词版本。模型
在 `thread.started` 前的登录、权限、状态目录预检或服务端输出 Schema 拒绝不消耗内容轮次。
每次都必须保留不可覆盖的诊断 Receipt；修复并测试相应能力后，可以自动重启同一轮，无须再次
要求用户确认。一个来源最多允许在原始预启动失败后进行两次修复性重启；连续第三次仍未出现
`thread.started` 时停止并与用户讨论。已经启动的模型会话即使输出无效或为空，也消耗该轮。
本例外不适用于空模型输出、无效 Candidate JSON、`thread.started` 后的模型／进程失败或任何内容
质量 finding；这些情况都消耗轮次。

Round 1 出现致命错误时，先由 Sol/ultra 对冻结输入、Round 1 Candidate、确定性 finding 和
不可变核心提示词生成一个 receipt-bound corrective addendum；Sol 不能生成产品内容、引入事实、
删除来源边界、修改九章结构或弱化 Claim／Evidence 校验。其输出若不能逐项覆盖 finding、与
核心规则矛盾、扩大事实范围或无法确定性组合，则不执行 Round 2，直接停止并与用户讨论。

`IDEAL` 要求九章完整、有自然业务中文、所有 Claim／Boundary／Gap 可追溯、技术依据由程序
映射且来源边界正确。`REVIEWABLE_WITH_WARNINGS` 要求零致命错误，允许已记录的轻微重复、
密度或措辞告警，但必须经用户批准。伪造或矛盾事实、缺失／重复章节或 Claim／Gap、错误来源、
无效 Schema 或 digest、内部标识泄露、把草案或派生资料写成已确认事实、业务读者无法理解
结论意义均为 `FATAL`。Round 2 后任一 `FATAL` 仍存在时，停止 Candidate、Selection、freeze、
package 与部署；不存在第三份内容候选。

## 运行时接口与兼容性

来源准备阶段是 UI 观察接口，不进入持久化 `StandardizationRun` Schema：

```ts
type SourcePreparationStage = 'READ' | 'ANALYZE' | 'ORGANIZE';

type SourcePreparationProgress = {
  sourceId: string;
  stage: SourcePreparationStage;
  state: 'ACTIVE' | 'COMPLETE' | 'ERROR';
  sequence: number;
};

type SourcePreparationObserver = (
  progress: SourcePreparationProgress,
) => void | Promise<void>;
```

`SourcePreparationObserver` 是唯一的展示 seam：Demo adapter 先写入页面状态，再仅在
`ACTIVE` 回调后等待固定展示时长；LIVE adapter 写入同一状态后立即返回。运行时等待 observer
只为了让 Demo 的当前阶段可见，但不把展示等待解释为来源业务处理，也不持久化它。

重载时，`PENDING` 显示全灰，`READING` 显示读取活动，`DOCUMENT_READY` 显示前三阶段
绿色且审阅蓝色，`ALIGNED` 和历史 `REVIEWED` 显示四阶段绿色。

完整来源读取通过 `ReviewedSourceDocumentReader` 提供：它绑定运行、精确 V6 文档和
已保存 Revision，返回原始及审阅后 Markdown SHA、九章结构和逐项 `ReviewedSourceChange`。
交付预览将 `reviewedSourceManifest`、`changeManifest`、完整合并 Markdown 和三页签投影
纳入 Preview SHA；生成复用同一个构建器，并验证实际保存的 `mergedDocumentRef` 与预览一致。

现有历史事件顺序继续可读：

```text
DOCUMENT_GENERATED → DOCUMENT_REVIEWED → CONFLICT_FOUND → CONFLICT_RESOLVED
```

新运行在文档就绪时记录满足前提的正式差异：

```text
DOCUMENT_GENERATED → CONFLICT_FOUND → [CONFLICT_RESOLVED] → DOCUMENT_REVIEWED
```

不新增持久化状态、Schema 版本或命令联合类型；保持现有 CAS、幂等和历史回放边界。

## 设计不变量

- 审阅事项、审阅结论和标准化文档三页签始终存在。
- 所有正式差异都在其成立时审阅，不允许在流程末尾堆积。
- 每个页面或移动层最多一个 Primary。
- 已保存决定、已审阅来源和完成阶段均为绿色；红色仅表示错误。
- V6、正式模型、黄金摘要、原始证据和快照不可修改；现有 V6 Pinned Bundle 不可改写。
  只有阶段二完成候选审批后，才允许以追加的 V7 和经过批准的确定性重生成更新新运行所用
  的 pinned 内容，历史 V5/V6 运行不得静默升级。
- 阶段一的普通启动、测试、构建和浏览器故事只读取仓库固定资源，不访问来源系统或模型。
  阶段二的生成命令是显式、受审计的离线候选流程，而不是运行时能力。
- 多标签并发正确性不在本故事中扩展；既有 Revision/CAS 继续保护写操作。
