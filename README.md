# 灵光语义建模工作台 V2

这是灵光语义层的前端交互原型，包含数据标准化、AI 建模、本体建模、指标配置、业务规则、同义词与时间语义七个工作区。

## 数据标准化与 AI 建模的职责边界

`数据标准化`（M3）是所有多来源资料的唯一处理入口。连接器配置、文件资料、测试连接、范围发现、证据快照、批次定版、来源结论、来源比较和差异处理都在 M3 完成。管伊佳来源文档固定为“审阅事项／审阅结论／标准化文档”三页签：事项只放待确认、逐项资料缺口和已处理决定；结论只放核心结论与默认展开的完整对象目录；标准化文档以同一 Revision 保持 V6 九章阅读版和只读 Markdown 源文。管伊佳工作台的主审阅区拥有纵向滚动；底部审阅助手输入区是同一工作台的第二行，不使用固定或覆盖定位。右侧“来源资料”由页头唯一的“来源资料／收起来源资料”控件开合：内联区没有重复标题或关闭盒。右栏将每个来源映射到其业务检查点，压缩为来源、差异、结果三类可回看记录；点来源行只定位右栏检查点，不打开文档或改变主审阅区的位置。证据只在所属结论内按需展开。M3 不生成模型对象，也不能直接修改个人草稿。

M3 先为每个来源生成一份独立的九段式来源文档：文档说明、业务目标、业务对象、业务活动、字段与维度、对象关系、指标口径、示例问题、待确认事项。每份文档只陈述本来源能够证明、推断或缺失的内容；章节修改会同步结构化识别结果并创建新版本，旧版本不会被覆盖。管伊佳开始后自动打开第一份数据库文档；之后完成审阅会保留当前文档与阅读位置，审阅者点击唯一主操作“审阅下一个来源”才进入下一份。未决差异和资料缺口不阻断后续来源读取；全部五源读完后，时间线中的差异层依次保存决定，最后一项决定保存前不得生成结果。

管伊佳连续时间线的主区底部提供真实审阅助手。它只从 `StandardizationRun` 在该 Turn 事件时点已登记的精确来源 revision 解释来源、冲突、Evidence 和影响对象，或打开一致的当前目标；source／document／block／section／Evidence／object／timeline 选择必须属于同一事实链。结构化修改遵循“建议 → 真实 Block／Assertion／Markdown Preview → Editor/Admin 明确确认 → 新 document revision”单一路径；自由文本不能直接应用修改、解决冲突、冻结、交付或触发 M4。Turn、Proposal 引用、确认和相邻 `DOCUMENT_REVISED` 都进入同一内容寻址 Run 时间线，初始只展开最近 20 turn 和本页 Proposal，不读取页外完整 Proposal。右侧事实检查器继续只读；待确认 Proposal 存在时主区只有“确认并应用此修改”一个 Primary。

管伊佳五源对齐后由新的 `standardization-deliverable` 深模块生成来源清单、九段合并文档、决定清单、治理附录、独立 Modeling Artifact 与两层 zero-delta 报告。它只读取真实 Run 的五份精确来源 revision 和三项 CP5 决定；演示制度与 Semantica 不会被提升为正式根证据。作者确认全部核心 hash 后交给异人 Reviewer/Admin；确认、审核、Receipt 读取和交接都会将 Run 事件冻结的内容 refs 与 SourceDocument 对账，重算 blocks→assertions→sections→Markdown，再重建九段、Artifact 与 delta。Run 的交付事件只能由该模块的私有 capability 写入；事件追加失败或追加成功但最终 metadata CAS 失败都会保留可恢复 pending 状态。恢复会重查角色，并且只接受严格 Run 前态或带 exact event 的后态，不会复制产物或解冻。

固定故事交给 M4 的是显式 `ZERO_DELTA_MODELING_HANDOFF` Receipt：语义变化为 0，正式 `catalog_guanyijia_v1` 未修改，不创建个人草稿或 V2，只追加资料治理、证据与决定记录。Receipt 精确绑定受保护与新 Artifact、Catalog、semantic SHA 和治理 refs；M4 的这个分支直接进入正式 V1 inspector，不显示“开始建模／加入个人草稿”，切换项目也不会携带前一项目 Receipt。零售与旧资料仍保留原来源文档集合／合并文档兼容路径，不能被管伊佳五源复用。

审核读取固定为“总览 → 问题队列 → 单个问题的来源结论 → 按需证据 → 受影响章节”。总览、问题和结论不读取证据正文；只有用户点击某条来源主张的证据后，Runtime 才读取正文并核对来源、血缘、Locator 与 Checksum。问题和证据默认每页 20 条，搜索与筛选查询完整索引；技术 ID、指纹和 Locator 默认折叠，可完整展开与复制。零售八类来源各自形成一份文档，净销售、机器人过滤和营业日三项阻断必须由用户选择来源结论并填写理由；决定会改变最终语义载荷和 Markdown，而不是只解除流程门禁。管伊佳黄金 V1 的三份来源文档继续投影相同正式结果；仅 MySQL＋GitHub 的未来文档会诚实保留证据缺口，不能伪冻结。

容量合同不随演示数据量变化：10,000 个问题和 100,000 条证据时，首屏仍只读取最多 40 条 Timeline 与 20 条问题索引，正文读取为 0；展开结论后仍不读正文，只有明确打开内容才按 SHA 校验读取。`review-window` 使用绑定 run、epoch、stream、filter 与方向的不透明 keyset cursor，每页最多 50 项，前端窗口最多保留 80 项；100k Evidence 索引留在 IndexedDB／生成式 adapter，不进入 React 数组或 Map。数据标准化完整 surface（含 Portal）DOM 节点预算不超过 300，避免用“分页 UI + 全量后台读取／全量隐藏 DOM”伪装容量能力。

管伊佳 Timeline、Document、Conflict、Assistant Patch、Deliverable 与 Inspector 共用 `review-surface` 导航 seam。它只保存稳定 anchor、相对偏移、焦点 ID、cursor epoch 与助手草稿，不持久化 HTMLElement 或业务正文；React adapter 统一执行 inert、body lock、focus trap、Escape、live region 和关闭后的焦点／滚动恢复。1440px 使用 inline Inspector，1024px 使用 overlay，低于 900px 为 `100dvh` 全屏子页；真实 200% 页面缩放根据 visual viewport 触发同一移动合同，safe-area 和虚拟键盘不会遮挡 composer 或当前 Primary。

`AI 建模`（M4）的普通入口只接收已经登记为`FROZEN`的人工 Markdown或 M3 标准文档，并同时核对 artifact ID、revision 和精确 SHA。普通文档由用户确认“开始建模”后按九段契约识别候选，再经明确操作加入个人草稿。管伊佳 zero-delta Receipt 是独立只读路由，只展示正式 V1 和治理回执，不触发候选、草稿、审核或发布。M4 不提供连接器、YAML、快照、批次或多来源冲突管理；右侧仅有“文档／模型”。详细契约见[数据标准化与 AI 建模交接](./docs/architecture/m3-m4-standardization.md)。

## 产品、协作空间、模型项目与证据包

产品固定为“零售语义建模”。顶部只选择模型项目和 Catalog 版本；切换项目时系统同步切换其所属协作空间与角色权限，协作空间名称只在用户与待办上下文中展示。不同输入资料不会再被伪装成不同模型：

- `ERP 数据治理`协作空间只包含`管伊佳 ERP 语义模型`项目；项目内浏览 MySQL 数据库证据和 GitHub 源码证据。
- `零售经营建模`协作空间只包含`零售经营语义模型`项目；项目内浏览原始人工模型基线、数码产品设计文档、全渠道经营资料和集团多存储证据。

证据包选择只位于数据标准化的“来源”视角。`default`、`digital_sales_warehouse`和`omnichannel_retail_ops`继续保留原 Fixture、Runtime 和历史数据，但只作为零售经营项目的兼容资料来源出现；`group_retail_ops`是零售经营项目的稳定编码，其集团多存储 V1 是当前正式 Catalog V1。来源版本（Markdown v1–v4、数据库快照、Git Commit）、冻结资料批次（R1/R2）、标准建模文档 revision 和正式 Catalog（V1/V2）互不混用。

正式 Catalog 的核心对象来自发布时冻结的`workspaceData`和`metricData`。可选 sidecar 只补充证据、生成说明、原始维度、层级和规则候选，不能覆盖人工修改后的正式对象。旧 Catalog 没有 sidecar 时，页面明确显示“该历史版本未保留来源明细”，不会使用当前 Fixture 猜回历史依据。

数字销售系统遵循固定版本关系：资料 v1 发布模型 V1，资料 v2 发布模型 V2；资料 v3 因维修 SLA 口径不完整而阻断，当前模型保持 V2；资料 v4 修正后发布模型 V3。只有实际发布成功的模型才会进入本体、关系、指标与规则页面。

模型对象按“系统 + 模型版本”隔离。正式模型及其历史版本始终只读；编辑者必须基于当前正式版本创建只对自己可见的个人草稿。发布下一版后，旧版本永久保留，新的修改从新基线重新开始。AI 建模状态在草稿作用域运行，不会直接覆盖正式 Catalog。

版本选择只有一个解释来源：“我的草稿”读取当前用户尚未提交的修订；`V1 / V2 / V3` 通过协作 Catalog 读取对应不可变发布记录。AI 建模、本体、指标、规则、同义词和时间语义都读取同一个选定版本，不再各自选择“最新数据”。所有发布版本都保留对话输入，但不允许上传、审核或修改；上传和建模只发生在个人草稿中。

发布适配遵循以下边界：

- 实体、事件、字段和关系直接进入 Linguan，字段始终挂在所属表下。
- 维度保留到实体或字段的映射；成员层级进入本体页的层级和值定义。
- 单字段 SUM / AVG 指标可继续编辑；比率、半可加、加权平均等复杂指标保留真实公式并只读展示。
- Java 输出的业务规则只形成“待结构化规则候选”，不会冒充可执行规则。
- 有明确资料依据的实体、事件、业务字段、维度、指标和规则同义词进入同事原有同义词页；技术键不生成同义词。
- 数据源与 Schema 未知时显示“待配置”，不编造环境信息。

Linguan 的 hierarchy 表示维度成员层级，例如“大区 → 省 → 市 → 区县”；`entity_hierarchy` 仍表示“库位属于仓库”这类实体间关系，两者不会混用。数字销售资料包含“华东 → 江苏 → 南京 → 玄武区”等成员样例。默认模型空间原有层级和同义词数据保持不变。

四版结果来自 `semantic-snowflake-java-demo` 的本地 `analyze → build → finalize`，核心产物和 `semantic_enrichment.json` 已固化在 `src/features/ai-modeling/fixtures/java/`。浏览器运行时不调用 Java、数据库、HTTP 或大模型。Fixture 生成器只读取 Linguan 内的 Markdown 和这些已提交产物，因此数据链可独立复现。

“全渠道经营资料”是零售经营语义模型下的多来源证据包。它包含 PDF、WPS、Markdown、PNG 和 JPEG，另有 MySQL `retail_core_prod`、Snowflake `retail_analytics_prod` 及 GitHub `retail-platform/retail-analytics@a91f2c7` 三个固定快照。页面中的“连接”只加载已固化结果，不访问真实数据库、GitHub、OCR 或大模型，也不保存二进制、密码和凭据。资料包指纹由来源指纹排序去重后生成，因此加入顺序不影响批次身份。

多来源处理先独立整理各来源，再按问题类型选择权威来源进行互证：正式业务资料负责定义、指标和规则；数据库结构负责表、字段、键和类型；查询样本与代码负责实际关联、过滤和枚举；图片只作为辅助依据。净销售额退款时点和 `CLOSED` 订单状态是两项固定阻断冲突，必须在对话中保留用户、中文理由、影响对象和来源后才能生成模型。最终 120 项审核中，96 项由系统预审，人工项按“冲突、弱依据、系统生成”依次出现。

Markdown 上传按 SHA-256 识别资料。已知 SHA 只使用受信 Fixture 映射确认归属；跨空间操作必须先由用户确认，助手不会猜测 `system_code`。目标空间已经存在同一资料时，确认操作直接打开对应的建模流程或已发布版本，不重复上传和生成；执行失败时确认选项保留并在对话中显示原因。HTTPS/localhost 优先使用浏览器 Web Crypto；普通 HTTP 内网地址没有安全上下文时使用本地标准 SHA-256 兼容实现，所得摘要与已提交 Fixture 保持一致。

AI 建模使用 Codex 式连续时间线完成上传、审核、意见和发布。附件以标签形式位于输入框内部，拖拽、回形针和剪贴板中的真实文件共用同一校验；纯文件名或路径不能冒充文件。普通地址在输入区的“…”菜单中提供“下载下一份示例资料”和带二次确认的“恢复当前空间”；恢复确认会自动定位到对话中的可见位置，确认后回到可重新上传资料的当前建模流程。只有 `?demoTools=1` 时才额外提供未知资料。示例资料可从任意模型空间下载：非数字销售空间从 v1 开始，数字销售空间按当前流程顺序提供下一版资料；上传时仍通过受信 SHA 映射确认并提示切换到正确空间。

状态条只位于左侧对话列；输入框桌面默认两行并可随内容增长，手机保持适合触控的最小高度。发布回执、对话记录和输入框使用“自适应回执＋独立滚动记录＋固定输入”布局，展开右侧检查器或发布记录都不会移走输入框或改变对话滚动位置。右侧“当前生成结果”检查器从工作区顶部贯通到底部；实体、事件、字段、关系、维度和指标始终以单行六项入口阅读完整定义，实体与事件分别承载所属字段，字段入口按实体／事件和所属表分组。检查器可以收回，手机端以近全屏底部结果抽屉呈现。审核在对话和右侧统一分为“待你确认、已采纳、已提出意见”：每个对象都可单独采纳、不采纳、提出意见或改为采纳，两侧使用同一 Runtime 命令并立即同步。重点项排在前面，其余待确认项明确折叠但不会因筛选消失；分组操作只采纳尚未决定的对象，不覆盖已有意见。

多来源场景沿用同一工作区样式，输入区“＋”统一提供上传文件、连接数据源、连接代码仓库和下载资料包。右侧检查器切换为“资料／互证／模型”：资料按业务定义、物理结构、实际使用和辅助证据分组；互证按业务结论展示一致、冲突和弱依据；模型继续展示实体、事件、字段、关系、维度、指标，并增加只读规则候选。新增结果只更新数量提示，不强制切换检查器或改变对话滚动位置。

“集团多存储证据”是同一零售经营语义模型下的多存储证据包，它将“来源家族”“接入协议”和“证据作用”分开表达，页面不按厂商创建专用分支。唯一 Evidence Registry 固定 GR001–GR025 的来源、语义和 Locator；因果故事按 MySQL、GitHub、Semantica RDF/SPARQL、SharePoint、MongoDB、Elasticsearch、MinIO、Kafka 形成 B01–B08，核心证据累计为 4/7/9/12/15/18/21/25。Snowflake、Redis、Milvus 和 Cassandra 只显示为“更多可接入来源”，不会伪装成已经读取。Semantica 的属性图与 RDF 图是两种明确连接模式；本证据包读取 RDF 三元组、命名图、本体和 SPARQL 结果，不把它与属性图边混为一类。

来源接入统一由“数据标准化”管理；AI 建模不再出现来源配置入口。平台目录固定覆盖关系库、数仓与湖仓、文档库、键值库、宽列与时序、属性图／RDF图、搜索、向量库、对象存储、企业内容、代码仓库和事件流 12 类来源；PDF、WPS、Markdown、图片、CSV 和 Parquet 是直接文件输入，不重复算作第 13 类存储。首次接入按“配置 → 测试 → 发现范围 → 激活 → 读取 → 冻结快照 → 冻结批次”推进。缺少的证据覆盖和不能由当前资料支持的业务语义写入标准建模文档的待确认事项，不再强迫用户接齐全部来源。

Semantica RDF/SPARQL、MySQL、GitHub 和 SharePoint 还可进入统一语义证据编译器。RDF 不会先压成普通字符串三元组，而是保留命名图、datatype、language、BNode 作用域、稳定 Statement ID、checksum 和精确 Locator；数据库、代码与制度文档使用同一 EvidenceRecord 信封。编译器再生成来源主张、逐来源互证、实体／事件／字段／关系／维度／指标／规则候选和影响分析。派生自 SharePoint 的 Semantica 图谱仍只计一个独立根来源，未知谓词进入待解释队列，损坏校验和、缺失上游或错误 Locator 会阻止证据包生成。来源中心中 RDF 模式的“企业术语与本体图”提供“建模采集策略”和零售／管伊佳内置示例；示例使用独立临时批次，不修改正式 V1、R2 或个人草稿。结构化`modeling-package.json`是机器真相，Markdown 审阅说明书和 ZIP 只能导出、不能反向导入。详细契约见[语义证据编译器](./docs/architecture/semantic-evidence.md)。

共享连接的页面说明、动态表单和导出 YAML 均来自同一个版本化配置结构。YAML 只保存脱敏配置、读取范围和`credentialRef`，不得包含密码、Token或私钥；导入必须先显示新增、更新、跳过、冲突和错误，再由管理员确认。每次修改生成新的配置 revision，旧证据快照、资料批次和正式 Catalog 不随之改变。零售经营的 8 个代表来源迁为 revision 1 和默认快照；管理员可手动升级 MySQL、GitHub、Semantica，并通过 YAML 批量升级 MongoDB、Elasticsearch、MinIO、SharePoint、Kafka，逐个测试、发现范围、激活、读取后冻结不可变 R2。Snowflake、Redis、Milvus与Cassandra保留为可选模板。管伊佳的 MySQL 与 GitHub 同样使用此模块，但两个协作空间的连接、快照和审计完全隔离。详细契约见[来源配置与证据接入](./docs/architecture/source-management.md)。

来源中心在桌面使用来源列表＋详情双栏，在 390px 手机上切换为列表→详情单页导航并只保留内容区一处纵向滚动。连接／批次／快照技术 ID、配置、读取范围、版本、fingerprint 和 Manifest Locator 均可完整展开与复制，不再把`ellipsis`或鼠标`title`当作读取完整内容的唯一方式。

Elasticsearch 索引和 Semantica 业务本体在本场景中属于派生证据。每条派生结论保留上游 MySQL、MongoDB、对象文件或 SharePoint 文档引用，不能作为独立的第二份业务真相；Semantica 缺少 SharePoint 上游时记录血缘 gap，也不增加独立根来源数。B02、B06、B08 分别产生净销售额退款时点、机器人与压测流量过滤、营业日归属三项阻断冲突，再生成 7 个实体、5 个事件、84 个字段、15 条关系、11 个维度、12 个指标、2 个成员层级、7 个只读规则候选、191 个同义词和 3 项时间语义。候选模型与正式 Catalog 共用 Registry 的对象证据投影；support edge 必须声明结构、字段语义、指标公式、规则逻辑、同义词或时间归属的精确支持面，不能用仅“相关”的 Claim 验证对象。全部可见对象必须绑定当前批次证据，或明确标记为待确认；冲突未解决时禁止发布。

管伊佳 ERP 语义模型复用相同的“资料／互证／模型”检查器，只读取 `modeling-evidence/guanyijia/` 经校验的不可变清单。正式 V1 使用最新 MySQL、固定 GitHub master Commit 和官方核心文档三个真实来源；MySQL 与 GitHub 同时作为来源中心的共享连接，官方文档只作为冻结标准文档的辅助证据。没有真实清单的 SharePoint 与派生 Semantica 继续保持待确认，不进入正式 V1 的批次、Claim 或 Locator。互证固定以部署数据库判断当前表字段事实，以 Mapper、Service、常量、页面术语和官方文档解释关联、生命周期及业务含义。

当前源码 32 张核心表全部存在于数据库；新证据编译器将 95 张部署表唯一归类为 18 张语义建模资产、14 张技术支撑资产和 63 张待归类资产。`jsh_depot_head` 的三个欠款字段在源码与部署结构中不一致，因此正式 V1 排除应收欠款指标，并在决定历史和待确认项中保留原因。管伊佳正式 V1 由最新 MySQL、固定 GitHub Commit 与官方核心文档共同生成完整九段 Markdown，再经 M4 投影为本体、指标、只读规则候选、同义词和有证据的时间语义。后续修改继续使用“个人草稿 → 他人审核 → 发布 Catalog”管线；连接参数、凭据、原始业务行、完整源码和完整证据包都不进入浏览器本地存储。

对象详情以“这是什么、如何使用、需要确认什么”表达业务含义，技术编码、公式和聚合编码默认折叠。字段始终挂在所属表下并保持独立审核状态；来源依据展示文件、章节、行号和原文，单条引用按需展开。AI 建模内的成功、失败、处理中和等待状态使用同一套圆形标记；“已发布”在 AI 建模、指标和规则页面统一使用绿色，蓝色只表示当前选择、处理中状态和主要操作。发布检查只显示“关联可用、字段无冲突、指标可计算、资料可追溯”等客户语言，内部检查编码不出现在产品界面。旧资料版本自动折叠为版本回执，刷新后从已有工作区状态重建业务记录。

系统预审只自动采纳同时满足以下条件的对象：能够精确关联 Java 候选 ID、置信度不低于 95%、具有明确资料依据且建议采纳。自动决定和用户决定分别记录；用户可在发布前用单项决定覆盖系统采纳或既有意见，已发布模型的审核决定不可修改。旧 `linguan:ai-modeling:*:v2` 和 `v3` 状态会复制迁移到 `v4` 命名空间，旧值保留，已有人工决定和 Catalog 不会被覆盖。

## 多人协作体验

未登录时展示独立登录页。“查看体验账号”以一份扁平目录列出九个预置账号，每个账号只出现一次，可复制用户名、复制密码或直接填入。登录前不按 ERP／零售分组，也不把项目角色当成账号全局属性；登录后仅展示当前账号具有成员权限的模型项目，并在项目上下文中显示角色。体验密码存在前端 Bundle 中，只用于浏览器内演示，不代表生产认证。当前 Demo 允许多个浏览器标签进入工作区；同一标签仍可通过右上角“切换用户”完成作者、审核者、发布者和查看者的角色演示。五源的扫描结果、九段 Markdown、识别项、断言和证据定位已经固化为仓库内的预编译 Bundle；浏览器本地只镜像该 Bundle，后续演示不会扫描源头、访问外部网络或调用 LLM。多个标签同时写同一运行状态的一致性不属于本轮承诺，详见[多标签协作写入 TODO](./docs/plans/future-multi-tab-standardization-todo.md)。

固定源输入与编译快照的边界、失效条件和 revision 规则见[管伊佳五源固定扫描快照](./docs/architecture/guanyijia-fixed-source-snapshot.md)。

两个协作工作空间分别是：

- `ERP 数据治理`：只包含管伊佳 ERP 语义模型项目。
- `零售经营建模`：只包含零售经营语义模型项目；不同设计文档和存储来源在项目内作为证据包管理。

普通成员只能看到受邀模型项目；统一管理员账号为 `administrator`，内部稳定用户 ID 仍为 `user_administer`，因此旧 Session、草稿、待办和审计记录可以继续恢复。管理员可访问两个项目。权限由协作执行层在每次操作时重新校验：查看者只能查看正式模型，编辑者维护个人草稿，审核者审核他人的申请，发布者发布已批准申请，管理员拥有管理能力但仍遵守四眼原则。作者不能审核或发布自己的变更，正式基线变化后旧申请会进入冲突状态。

零售经营语义模型形成一条因果连续的多人主线：恢复后只有正式 V1 和来源 Revision 1；Administrator 将实际 8 个来源逐个升级到 Revision 2，完成测试、范围发现、激活和读取后冻结 R2；Kenan Zhang 把这个真实 R2 加入基于 V1 的个人草稿，处理3项冲突并由候选模型生成24项完整变化后提交；Zhengqing Xiong 从待办进入同一 AI 工作区，逐项查看 Before／After、影响对象和证据，无补充意见时可直接审核通过；Hao Xu 查看发布检查，填写中文发布理由后发布不可变 V2；Lexiu Sun 在 V1/V2 之间只读追溯“批次 → 来源 → 主张 → 互证结论 → 模型对象”。未实际配置或附加的来源不会出现在主张和候选模型中。页头“待我处理”只显示要求当前账号继续补充、审核或发布的任务；普通活动草稿只在“我的草稿”出现。管理员菜单中的“恢复协作演示”恢复正式 V1、来源 Revision 1 和无预置变化的干净协作起点，不删除旧系统的原始浏览器键。

草稿提交时冻结完整对象变化集，而不是只保存几行摘要。左侧“草稿审阅档案”作为对话时间线中的一条业务记录，按实体、事件、字段、关系、维度、指标、规则、同义词和时间语义展示新增、修改、删除及风险；输入框始终固定在时间线底部。固定 24 项演示不显示搜索，只有变化超过 40 项时才提供紧凑搜索，每类默认显示 20 项并可继续加载。点击任一变化，右侧模型浏览器定位拟发布对象并展示结构化 Before／After、依据和真实影响对象。建模过程状态不伪装成模型对象变化；旧式不完整变化以不可定位记录只读展示，不能造成整个工作区白屏。正式 Catalog 的资料页只展示本版本实际使用的冻结批次和 8 个独有来源；互证页逐项显示各来源主张、权威等级、证据入口、差异、最终决定及决定人历史。旧 Catalog 没有这些不可变明细时只显示明确的覆盖提示，不能从最新 Fixture 补猜。

正式模型、申请和任务保存在共享 `localStorage`，个人草稿按用户隔离；普通聊天、附件和当前弹层不持久化。底层仍保留 `storage` 事件、`BroadcastChannel` 与 metadata CAS 防线，但本轮 Demo 不承诺多标签同时写同一运行状态；该能力已记录为后续 TODO。旧发布版本迁移为共享只读 Catalog，旧工作副本归入管理员个人草稿；迁移只在新结构验证后写标记，原键始终保留。领域术语见 [协作领域词汇](./COLLABORATION-GLOSSARY.md)。

## 视觉与交互契约

V2 使用当前 RagEasy 前端的视觉语义重构：

- 应用壳采用白色导航与标题栏、浅灰工作区和白色页面 surface。
- 主交互色为深青 `#0078ad`，品牌点缀色为 `#00a5d9`；状态色、文本层级、圆角和阴影与 RagEasy token 对齐。
- 后台信息密度以 12/14px 为主，表格、表单、Tabs、抽屉和弹层统一使用紧凑基线。
- 导航可在 248px 与 72px rail 之间切换；低于 920px 时自动保留图标 rail，主内容继续可用。
- 页面保留原有数据结构、校验、增删改、筛选、预览与确认行为。RagEasy 只作为 UI/UX 依据，不引入其业务字段或接口。
- 每个视觉区域最多一个主动作；行级只常显“查看／编辑”，复制、启停、维护和删除进入“更多”。危险操作不得与主操作并列。
- Tabs只切视图，不承载学习、发布或删除；批量操作只在已有选择时出现。
- 抽屉固定底部“取消／主动作”，手机端使用全屏宽度。技术契约默认折叠，首屏优先说明是什么、影响什么和下一步。
- 600px 以下只保留“数据标准化／AI 建模／本体／指标／更多”五个固定底栏入口，业务规则、同义词和时间语义从“更多”进入；项目和版本始终在 Header 第一层并列可读。
- 数据列表桌面端使用明确列宽和容器内横向滚动，720px 以下使用分页信息卡；卡片与表格必须保留同等字段、状态和操作。同义词默认每页 20 条。
- AI正式态左侧只保留一条发布回执，右侧是唯一模型浏览器；实体、事件、字段、关系、维度和指标数字都能落到真实清单，字段始终携带所属对象。

六类语义对象在全部页面共用同一视觉注册表，颜色只表达对象类型，不与成功、警告和失败状态混用：实体／实体表为蓝色，事件／事件表为紫色，普通字段／属性为灰色，关系为洋红，维度／维度字段为青色，指标／度量字段为橙色。字段列表只显示“普通字段、维度字段、度量字段”中的一个角色标签；基础／复合指标、关系子类型和状态继续使用中性或状态标签。图节点、关系线、指标公式 Token 和规则目标同样读取该注册表。所有颜色标签必须同时保留中文文字，不能只靠颜色传达含义。

本体属性表以“字段、字段分类、语义类型、使用方式、操作”组织：中文名称与英文编码位于同一字段列，编码过长时省略并可悬停查看；“可筛选／可归因”合并为短标签；编辑直接可见，层级、值维护和删除收入“更多”。表格使用固定布局与横向滚动，窄屏不会把中文挤成逐字竖排。

成员层级与值定义不使用会挤压业务文字的宽表格：层级定义以摘要卡片展示名称、关联属性、完整路径、级别数和成员数；值定义以紧凑列表展示属性、字段角色、值结构、维护状态和主操作，数据来源及同步时间按需展开。中文名称保持完整阅读，技术编码使用单行省略并可悬停查看；手机端自动切换为单列信息块。

只有 Runtime 实际发布成功后，AI 回执才出现“查看本体建模”，左侧“本体建模”同时显示一次性绿色圆点。入口保持刚发布的模型空间和 Catalog 版本；进入本体页后圆点消失，刷新不会重复提醒，浏览历史记录也不会产生提示。

样式 token 与全局组件基线位于 `src/index.css` 和 `src/App.css`，应用壳位于
`src/layout/AppLayout.tsx`。新增页面应优先复用这些语义变量，不在业务组件中复制品牌色、阴影或 surface 圆角。

## 独立服务器部署

生产静态文件由 `npm run build` 生成到 `dist/`。当前内部演示环境使用
`deploy/nginx.conf` 启动独立 Nginx 实例，固定监听 `4173`，发布目录位于
`/opt/linguan-prototype-v2`。该实例拥有独立的 PID、日志和配置，不修改服务器
已有 Nginx 主配置，也不占用现有业务端口。

`deploy/linguan-prototype-v2.service` 负责 systemd 自启动和启停管理；部署后可用
`systemctl status linguan-prototype-v2` 查看状态，使用
`systemctl reload linguan-prototype-v2` 在切换发布目录后平滑重载。

静态资源使用内容哈希和长期缓存，`index.html` 禁用缓存；所有前端路由回退到
`index.html`。更新时先上传到新的 `releases/<release-id>`，验证后再切换
`current` 软链接并重载独立实例。
